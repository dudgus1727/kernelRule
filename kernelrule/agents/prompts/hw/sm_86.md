# Hardware facts — do not recall from memory, use what follows

This project got it wrong from memory four times (the meaning of ScaleType,
split-K constraints, swizzle compatibility, the serial partial type). This is
the target hardware.

```
GPU        NVIDIA RTX A6000 (GA102, sm_86)
SMs        84
smem       99KB per block (101,376 B)
threads    up to 1,536 per SM
registers  65,536 per SM
L2         6 MB
effective  116.1 TFLOP/s @1350MHz   729.7 GB/s @7601MHz
ridge      159.1 FLOP/byte
```

**These are effective values.** Not the spec (154.8 TFLOP/s, 768 GB/s) but
values observed with the clocks locked. Without this correction the
memory-bound verdict is off by 25%.

## Execution model

```
CTAs are distributed across SMs, and on the last wave some SMs idle.

A tile computes **everything it covers**, even outside the shape.
  A 128-row tile on M=1 wastes 99.2% of the work.

split-K divides K to create more tiles, at the cost of a reduction.
  serial    round-trips D in fp16 per partition (precision loss)
  parallel  writes M*N*sk partials to DRAM and reads them back

stages=2 (MmaPipelined) and stages>=3 (multistage) are **different kernel
families**. If alignment does not reach 16 bytes, cp.async is unavailable and
only 2 stages are possible.
```

## Limits of measurement — this affects your judgement

```
Time is only recorded in units of the CUDA event timer's tick (1.024 us).
Differences smaller than that **cannot be distinguished by measurement.**

The shorter the kernel, the larger that tick is in relative terms:
  a 14 us kernel   one tick is 7.3%
  0.5 ms           one tick is 0.20%
  1.3 ms           one tick is 0.08%

```

**This is a property of the hardware and the timer.** It appears in the same
form on any GPU (the tick value itself may differ).

**On a short shape the config cannot be pinned down exactly.** A difference
inside one tick may as well not exist, so refining the rule for short shapes
is learning noise. It is better to block **the paths that lose for certain**
on the large shapes.
