## 2. 판정 — 사전 등록의 둘째 갈래

```

실측: 벤더 46 µs 대 우리 12,974 µs  =  ★ 280배

```

## 3. ★ 무엇을 고쳐 쓸 수 있나 — 평가 자체는 µs 다

```
규칙 평가 + argmin (15,015 config)   ★ 297 µs
피처 계산                            12,631 µs   ← 병목의 97%
```

피처 14개는 **전부 벡터화돼 있다**. 그런데 후보 5,775개 · 피처 14개에
5,897 µs 가 든다 = (행,피처)당 **73 ns**. 넘파이 산술의 수십 배다 —
피처마다 pandas DataFrame 에서 **열을 다시 꺼내는** 비용이다.

```
정적 열을 numpy 로 미리 바꿔 봐도 12,954 µs 로 안 줄었다
-> pandas 프레임 자체가 아니라 **피처 함수마다의 열 접근**이 값을 정한다
```

★ **여기서 고치지 않는다.** 측정 결과를 보고 구현을 바꾸는 것은 조건
변경이다. **무엇을 고칠지는 실험 계획서를 따로 쓴다.**

## 4. ★ GBDT 와의 비교 — 원래 주장의 정확한 형태

⚠️ **두 팔의 조건이 다르다.** GBDT 는 `build_xy` 로 **미리 만든** 61열
행렬에 예측만 했고, 우리는 피처 계산을 포함했다.

```
같은 조건 (양쪽 다 피처 준비 제외)
  우리 규칙 평가 + argmin     297 µs
  GBDT 예측                8,483 µs      ★ 우리가 29배 빠르다

피처 준비 포함
  우리                    12,974 µs
  GBDT                   ★ 안 쟀다 (61열을 런타임에 모아야 한다)
```

★ **"GBDT 는 배포가 어렵고 규칙은 싸다" 는 살아남는다** — 다만 근거는
"µs 대 ms" 가 아니라 **"규칙 평가 297 µs 대 GBDT 예측 8.5 ms"** 다.

## 5. 후보 수 — 필터는 **이미 적용돼 있다**

```
카탈로그 (전 형상 합집합)   89,255 조합
★ 그 형상에서 legal        3,465 ~ 17,325 (중앙 15,015)
```

⚠️ 질문은 "필터를 적용하면 몇 개로 줄어드나" 였는데, **우리 후보 집합이
이미 필터 후다.** 표가 그 형상에서 실제로 돈 조합만 갖는다. 카탈로그
전수를 매번 계산하면 79 ms 다.

대표적인 필터(정렬 나누어떨어짐 · split_k 청크 ≥ tile_k · smem · 레지스터)
의 비용은 **1.8 ms** 다 (89,255행 벡터 비교 넷).
⚠️ **kernelTab 의 실제 판정식이 아니다** — 자릿수를 재는 용도다.

## 6. §2 제약 서술에 넣을 문장

```
★ 규칙 평가는 15,000 config 에 297 µs (최악 356 µs) — µs 안이다
★ 지금 파이썬 구현의 선택 비용은 13 ms 이고 그 97% 가 피처 계산이다
★ 벤더(nvMatmulHeuristics)는 46 µs — 우리 구현의 280배 빠르다
★ GBDT 는 예측만 8.5 ms — 우리 규칙 평가의 29배다
```
