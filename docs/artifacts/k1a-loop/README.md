# 개선안 1번 진단 — 좋은 피처를 주면 루프가 그것을 살리는가 (2026-10-03)

## 조건

d190 과 같은 루프 코드 · 설정 (F2 · nkband k=4 · 12 라운드 · gpt-5.6-luna · `--workers 2`),
a6000, fold 4개 x seed 0. 다른 점은 둘뿐이다.

- **라이브러리** — k7-1 (20축) + 손으로 만든 a6000 규칙들의 검증된 시간 모델 피처 16개
  (`stage1-features/`, 지금 계약 · 12줄 이하). d190 의 FeatureWriter 축 8개는 넣지 않는다.
- **씨앗** — K1a (가중치 3개 시간 모델 규칙, `seed/stage2-rule-writer/chosen.json`).
  RuleWriter 는 돌리지 않는다. 가중치는 루프가 fold 마다 train 으로 다시 맞춘다.

재현: `bash docs/artifacts/k1a-loop/campaign.sh` (태그 `k1a-a6000-f{0..3}`, 실행 `-s0`).

## 미리 정한 해석 (결과를 보기 전에 적는다)

출발점 = K1a 를 루프의 적합(u · dim)으로 그 fold 의 train 에 맞춘 것. 견줄 값은 65형상
pooled holdout (루프가 적은 값) 과, 같은 절차 재적합(`a6000_probe --prefix k1a`)의 inner-CV.

```
살린다    최종이 출발점보다 0.005 넘게 나빠지지 않는다
          -> 1번은 실용적인 개선이다. 남는 문제는 그런 피처를 LLM 이 만들게 하는 것(2번)
망친다    0.005 넘게 나빠진다
          -> 문제는 피처가 아니라 탐색 · 적합(항을 덧붙이며 과적합) 쪽이다
```

⚠️ 이 피처들과 K1a 는 a6000 의 65형상을 모두 보며 설계됐다 — a6000 holdout 의 **절대값은
낙관적**이다 (K1a 정직 추정 1.050~1.056). 그래서 출발점 대비 **변화**를 본다.

비교: d190 seed 0 (같은 루프, FeatureWriter 가 만든 라이브러리) fold 별 holdout
1.0929 · 1.1951 · 1.0874 · 1.0779, 65형상 pooled 1.1121.
