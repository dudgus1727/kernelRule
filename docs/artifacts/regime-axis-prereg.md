# 실험 계획서 — **체제 분할 축을 다시 고른다**. LLM 0회 · GPU 0회

**계산 전에 쓴다.**

## 0. 문제

지금 형상을 **SOL 0.5 ms** 로 잘라 가중치를 두 벌 맞춘다.

```
왜 SOL 인가      max(연산 하한, 메모리 하한) — 두 물리를 뭉쳐 **크기**로 만든다
왜 0.5 인가      ★ 근거가 약하다. 문서의 근거는 "그 구간의 측정 분해능이 가장
                 나쁘다" 인데 그것은 A6000 에서만 성립한다
                 (눈금/통계 교차점 A6000 2.33ms · 5090 0.021 · 4090 0.015 ·
                  H100 0.016 — 사용자가 준 값)
GPU 가 바뀌면    ★ 0.5 를 다시 정할 근거가 없다
```

**논문에서 "왜 이 축이고 왜 이 값인가" 에 답할 수 없다.**

## 1. 세 팔 — 같은 규칙, 가중치만 다시

대표값 실행 여섯(`F3rw-p8-nan-s0..5` 의 **r11** 규칙, D-140)을 그대로 쓴다.
**구조를 건드리지 않는다.** 적합기는 파라미터 8 규칙대로 nelder-mead /
재시작 4 / 300 evals (최종 채점 경로와 같다).

```
① SOL 0.5 ms 로 나눠 적합    ← 지금 방식
② ★ roofline 로 나눠 적합    t_memory > t_compute 인가 (regime_of(axis="roofline"))
③ 안 나누고 한 벌로 적합
```

경계 민감도로 **①' SOL 0.25** · **①'' SOL 1.0** 을 함께 낸다.

### 형상 수 — 미리 적는다 (결과가 아니라 조건이다)

```
축            학습(41)              홀드아웃(20)
SOL 0.25      short 24 / long 17    short 10 / long 10
SOL 0.5       short 29 / long 12    short 12 / long  8
SOL 1.0       short 34 / long  7    ★ short 14 / long  6
roofline      mem  12 / comp 29     mem   8 / comp 12
없음          41                    20
```

⚠️ **SOL 1.0 은 학습 long 이 7개로 `MIN_PER_REGIME`(8) 미만**이다 — 그
체제의 가중치는 믿기 어렵다. **결과에 그렇게 적는다.**

★ `is_memory_bound` 와 `arith_intensity` 가 **형상 수준 값**임을 확인했다
(한 형상 안에서 고유값 1개 — D-142 에서 확인, `vendor_shapes.py` 가 인용).

## 2. 재는 것

```
최종 채점 = 체제별로 splits.train 에 재적합 -> splits.val 20형상 regret@1
6실행의 중앙과 범위
★ 체제별로 나눠서도 낸다:
   ② 에서 mem 체제 / comp 체제의 regret
   ③ 에서 **같은 형상들을 그 구분으로 봤을 때**의 regret
   -> "안 나누면 어느 쪽이 무너지나" 가 보인다
```

### ★ 재현 검증 — 팔 ① 이 알려진 값과 같아야 한다

`canonical_score` 는 `("short","long")` 과 `regime_of(axis="size")` 를
하드코딩한다. 축을 갈아 끼우려면 **그 절차를 실험 스크립트 안에서 다시
구현**해야 한다. 그래서:

```
★ 팔 ① 의 6실행 중앙이 대표값 1.0886 과 같아야 한다
   다르면 재구현이 틀린 것이다 — 팔 ②③ 을 보고하지 않고 멈춘다
```

## 3. 판정선 — 미리 박는다

원칙 7: 여기서 새로 정하지 않는다. `delta = 0.0516`,
완충대 `0.0516 ~ 0.0589` (D-141 §2 와 같은 규칙).

```
② 가 ① 보다 0.0516 이상 좋다     ★ 축을 roofline 으로 바꾼다
② 와 ① 이 구분 불가              ★ 그래도 ② 로 바꾼다 — 아래 이유
③ 이 ①·② 와 구분 불가            ★ 나눌 이유가 없다. 설계에서 뺀다
③ 이 0.0516 이상 나쁘다          나누는 것 자체는 정당하다
```

### ★ "구분 불가면 ② 로 바꾼다" 를 **결과 전에** 정하는 이유

성능이 같다면 **설명이 쉬운 쪽**이 낫다.

```
① SOL 0.5 ms   ★ 임의 상수가 하나 있고 GPU 마다 정할 근거가 없다
② roofline     ★ 임의 상수가 없다. t_memory 와 t_compute 를 비교할 뿐이다
               ★ GPU 가 바뀌면 peak·bw 가 바뀌어 **자동으로 따라간다**
               ★ 물리적 의미가 한 문장으로 나온다
```

**이것은 결과를 보고 정하는 선택이 아니라 결과 전에 정한 선호다.**

## 4. ③ 이 나오면 — 82/18 실험과의 관계

"나눠야 한다" 의 현재 근거는 §30.5 의 학습 구성 실험이다
(짧은 82%/긴 18% 에서 검증 격차 +2.629 · 전체 1.390, 69/31 에서 +0.009 ·
1.143). **그것은 "학습 분할에 어느 체제를 몇 % 넣을까" 실험이지 "가중치를
나눌까" 실험이 아니다.**

★ ③ 이 구분 불가로 나오면 **두 실험이 다른 것을 재고 있었다**는 뜻이므로
`decisions.md` 에 그 사실을 적는다. ⚠️ **82/18 실험을 지우지 않는다.**

## 5. 중복 우려 (미리 답)

```
휴리스틱이 이미 p.is_memory_bound 로 코드 안에서 분기한다
-> "같은 축으로 또 나누면 중복 아닌가"
```

층위가 다르다: **코드 안 분기는 항 하나를 다르게 쓰고, 체제별 가중치는
여덟 개 전부를 다르게 맞춘다.** 오히려 "규칙이 그 축을 중요하다고 이미
말하고 있으니 가중치도 나눈다" 가 자연스럽다.
⚠️ **이것은 논증이고 실측은 §2 가 답한다.**
