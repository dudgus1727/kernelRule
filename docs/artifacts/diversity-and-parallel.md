> **상태**: 측정만. **아무것도 안 고쳤다**
> **재현** `python3 experiments/diversity_audit.py` ·
> `python3 experiments/round_profile.py` — **둘 다 LLM 호출 0회**

처방을 만들기 전에 잰다 — **겹침이 작으면 다양성 장치가 불필요하다.**

## 1. Analyst — ★ 겹치지 않는다. 장치가 필요 없다

44실행, 라운드 479개, 같은 라운드 안의 가설 쌍 3,575개.

```
measurable_with 자카드   중앙 0.00   평균 0.09   완전 일치 0%
affected_regime 동일     0%
claim 어휘 자카드        중앙 0.05
```

**세 축 모두 거의 안 겹친다.** 한 응답 안에서 서로 다른 축을 말하라는
지시가 프롬프트에 이미 있고(§30.10 "서로 다른 실패 모드를 다뤄라"),
그것이 듣고 있다.

```
-> ★ "measurable_with 가 겹치는 가설 둘을 내지 마세요" 를 넣을 이유가 없다
   이미 0% 다. 넣으면 없는 문제를 고치는 것이고 조건만 늘어난다
```

## 2. RuleWriter — ★ 여기는 겹친다

한 캠페인의 10개가 쓰는 f 피처 집합의 자카드(쌍별 중앙):

| 캠페인 | n | 피처 자카드 | 항 수 | 학습 점수 최소~중앙~최대 |
|---|---:|---:|---|---|
| `f1pipe-F1-K-k1` | 10 | **0.50** | 6~8 | 1.1794 / 1.2339 / 1.3801 |
| `f1pipe-F1-free-roofline` | 10 | **0.67** | 7~8 | 1.1551 / 1.2776 / 1.5032 |
| `f1pipe-F3-arch24` | 10 | **0.70** | 7~8 | 1.1077 / 1.1550 / 1.1866 |

**사람 24개 라이브러리에서 자카드 0.70 이다** — 열 번 뽑아도 같은 피처
일곱 중 다섯을 공유한다. 항 수도 7~8 로 붙어 있다.

### 점수 격차가 "다양성" 이 아니었다

```
사람 24개   최소 1.1077  중앙 1.1550   격차 0.047
```

**구조는 0.70 으로 겹치는데 점수는 0.047 벌어진다.** 즉 그 격차는
**다른 접근이 만든 것이 아니라 같은 접근의 운의 폭**이다.

D-84 가 "씨앗이 하류 전체를 규정한다" 를 보였으므로 **여기가 값하는
자리다.** 다만 아직 안 고쳤다 (처방은 §5).

## 3. 부모 종류별 중복률 — ★ 못 쟀다

`llm_calls/*.json` 에 `prompt` 가 **비어 있다.** `dump()` 는 남기게 돼
있는데 옛 실행에는 없다 — 부모 종류(`parent=exploit|explore|cross`)가
프롬프트 문자열에만 있어서 **이 축으로는 못 가른다.**

```
대신 본 것 — 라운드별 채점률 (부모 종류는 못 가른다)
  f1pipe-F1-K-k1-s0..s5   85~93%
```

**다음 실행부터는 잴 수 있다** — `reqs` 의 `prompt` 에 이미 종류가
들어간다. 옛 자료로는 못 한다는 사실만 남긴다.

## 4. ★ `cross` 는 두 번째 부모를 버리고 있다

```
archive.parents 가 cross 에 Elite 둘을 준다     True   (rng.choice(size=2))
run_round 가 실제로 쓰는 것                     ['ps[0]']
RuleEditor 프롬프트의 부모 자리                  {parent_code} 하나뿐
```

**`cross` 는 `explore` 와 같다.** 두 부모를 뽑는 코드는 도는데 두 번째가
프롬프트에 도달하지 않는다. §13 의 "교차" 설계가 **구현된 적이 없다.**

⚠️ **D-42(앙상블 실패)와 관련이 있을 수 있다** — 아카이브의 다양성이
결합된 적이 없다면, "다양성이 표면적" 이라는 진단의 원인이 다양성 자체가
아니라 **결합 경로의 부재**일 수 있다.

**아직 안 고쳤다.** 고치면 조건이 바뀌므로 사전 등록이 필요하다.

## 5. 가설 배정 — 앞쪽 편중은 **나머지 연산의 부산물**이다

`hyps[i % len(hyps)]`, 부모 12개:

| 가설 수 | 배정 횟수 | 최대/최소 |
|---:|---|---:|
| 4 | 3 3 3 3 | 1.00 |
| **5** | **3 3 2 2 2** | **1.50** |
| 6 | 2 2 2 2 2 2 | 1.00 |
| **7** | **2 2 2 2 2 1 1** | **2.00** |
| **8** | **2 2 2 2 1 1 1 1** | **2.00** |

**Analyst 가 낸 순서가 그대로 배정 빈도가 된다.** 스키마가 2~8개를
허용하므로 5·7·8 이 실제로 나온다.

그리고 **부모 종류와도 상관된다** — `i=0~5` exploit / `6~8` explore /
`9~11` cross 이므로, 가설 수에 따라 "어떤 가설이 어떤 부모에 가는가" 가
고정된다.

```
가설 5개면  H0 -> exploit x2 + explore x1,  H3 -> exploit x1 + cross x1 …
★ 이것은 설계가 아니라 12 % 5 다
```

## 6. ★ 병목은 `fit_weights` 다

### LLM 대기 (실제 실행 기록)

동시성 6 이므로 `합/6` 이 LLM 벽시계의 **하한**이다.

```
luna / lunaNAMES (12라운드)   32~39%
d75run4 / verify (4~6라운드)  15~24%
```

### LLM 밖 (MockLLM 한 라운드)

```
라운드 벽시계 28.2s   제안 12  채점 5
  진단 리포트   0.1s    1%
  정적 검사     0.0s    0%
  샌드박스      0.9s    3%
  fit_weights  27.1s   96%   ★
  채점         0.1s    0%
```

**후보당 `fit_weights` 5.4초.** 이번 목 라운드는 중복이 많아 5개만
채점됐다 — **12개가 다 채점되면 65초**다.

```
★ 중복이 많을수록 이 구간이 싸 보인다.
  D-89 에서 Analyst 를 끈 팔의 채점률이 28% 였는데, 그때 라운드가
  빨랐던 것은 "효율" 이 아니라 **일을 안 한 것**이다 (원칙 29).
```

### 그래서 병렬화가 값한다

```
LLM 대기        벽시계의 15~39%
fit_weights     나머지의 96%
-> 전체의 대략 60~80% 가 fit_weights 다
```

**다만 이 두 수치는 다른 실행에서 나왔다** (LLM 대기는 실제 실행,
구간별은 MockLLM). 한 실행에서 둘을 다 재려면 LLM 호출이 필요하다 —
그 사실을 여기 적는다.
