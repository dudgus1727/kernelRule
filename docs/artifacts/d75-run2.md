## ★ 먼저 — 세는 단위를 실행으로 바꾼다

1차 보고(D-79)에서 **제안 규칙 하나를 표본 하나로 셌다.** 틀렸다.

```
한 실행의 제안 48개는 같은 씨앗에서 나오고 서로의 자손이다.
한 실행이 습관을 하나 가지면 그 습관이 48개에 전부 찍힌다.
-> 제안 단위 Fisher 는 n 을 16배 부풀린다.
```

**아래는 전부 실행 단위로 다시 셌다.** 제안 단위 수치도 함께 적되,
결론은 실행 단위로만 낸다.

## 1. ★ 경로는 돈다

```
요구 2건 -> FeatureWriter 2회 -> 검증 통과 2/2 -> 등록 2/2
되돌아간 Analyst 가 그 축을 언급  2/2
아카이브에 쓰임                  s0 2/7 규칙, s1 3/7 규칙
최선 규칙에 들어감                s1 예 / s0 아니오
상한 초과로 버린 요구             0건
```

**만들어진 축 둘이 303건 요구의 상위 주제와 정확히 겹친다.**

```python
split_k_wave_idle_delta            # split-K 의 **이득** (옛 요구 48건)
  "split-K가 추가하는 CTA 병렬성으로 SM 유휴와 마지막 wave 손실이 얼마나 주는지"

output_tile_aspect_misalignment    # M/N 비대칭 (옛 요구 13건)
  "출력 형상 M/N 종횡비와 타일 종횡비가 얼마나 정렬되는지"
```

`split_k_wave_idle_delta` 는 **"우리 피처는 비용만 재고 이득을 안
잰다"** 를 정확히 메운다. 둘 다 물리에서 유도했고 표 정보가 없다.

### 요구 문장 누출 0/2

```
[s0 r0] OK  split-K가 추가하는 CTA 병렬성으로 ...
[s1 r2] OK  출력 형상 M/N 종횡비와 타일 종횡비가 ...
```

옛 303건도 누출 0/303 이었다. **Analyst 는 리포트를 다 보면서도 요구는
물리 언어로만 쓴다** — 조건 1 의 설계가 모델의 습관과 어긋나지 않는다.

## 2. ★ 그런데 요구 빈도가 눌렸다 — 내 프롬프트 개편 탓이다

같은 조건(F3 사람24) · 같은 모델 · **같은 라운드 구간(r0~r3)** ·
**1차 Analyst 응답만** (옛 실행은 라운드당 Analyst 가 한 번이었다).

| 실행 | 요구/가설 | |
|---|---:|---|
| 옛 arch24-s0 | 2/16 | 12.5% |
| 옛 arch24-s1 | 4/18 | 22.2% |
| 옛 arch24-s2 | 4/20 | 20.0% |
| 옛 arch24-s3 | 4/17 | 23.5% |
| 옛 arch24-s4 | 3/18 | 16.7% |
| 옛 arch24-s5 | 4/19 | 21.1% |
| **새 d75run2-s0** | 1/17 | **5.9%** |
| **새 d75run2-s1** | 1/20 | **5.0%** |
| **새 d75run2-s2** | 0/17 | **0.0%** |

```
옛 6실행 12.5~23.5%   새 3실행 0~5.9%   ★ 범위가 겹치지 않는다
Mann-Whitney U  p = 0.0119   (6 vs 3 에서 최소 가능 p = 0.0038)
제안 단위 Fisher  21/108 vs 2/54   p = 0.0074
```

**실험 계획서에 적은 판정선("0~3건이면 억눌린다")에 걸린다.**

### 억제 문구를 뺐는데도 눌렸다

이번 실행 전에 `"한 라운드에 한둘. 정말 없는 축일 때만"` 을 **뺐다.**
그런데도 0~5.9% 다. **남은 원인은 프롬프트 개편의 다른 부분이다.**

옛 조건과 지금의 차이:

```
1  필드 이름/설명   needs_new_feature "그 물리량의 **이름**"
                  -> physical_requirement "그것이 무엇인지 **한 문장**"
2  ⛔ 예시 추가     "사례 #7 에서 ..." 같은 것은 쓰지 마라
3  ★ "그 사람은 이 리포트를 못 봅니다.
      사례 번호·점수·형상 목록을 쓰면 **전달되지 않고 버려집니다**"
4  남은 억제 문구   "정말 기존 피처로 못 재는 것일 때만 채우세요.
                  있는 것으로 잴 수 있으면 measurable_with 를 쓰는 편이 낫다"
```

**3번이 가장 유력하다** — "버려집니다" 는 채우는 것의 위험을 알린다.
4번은 내가 억제 문구를 빼면서 **다른 억제 문구로 바꾼 것**이다.
옛 문장("대부분의 라운드에서는 null")과 강도가 비슷하다고 봤는데,
`measurable_with` 를 **권하는** 문장이라 방향이 더 세다.

★ **교락 1(요구 수준 상향)은 실행 전에 배제했다** — 옛 303건의 90.1%가
이미 문장이었다(길이 중앙 49자).

**아직 안 고쳤다.** 결과를 보고 프롬프트를 고쳐 다시 돌리면 그것은
표에 맞추는 것이다 (§12.3d). **무엇을 고칠지는 사람이 정한다.**

## 3. ★ D-78 — 리터럴은 확실히 돌아왔다

같은 조건 · 같은 구간(r0~r3) · **실행 단위**.

| | 옛 6실행 | 새 3실행 | |
|---|---|---|---|
| **비교에 숫자 리터럴** | 0 0 0 0 0 2 % | **35 69 12 %** | **실행 단위 Fisher p = 0.0476** |
| `np.isfinite(` | **52** 2 0 0 0 0 % | 0 0 0 % | p = 0.50 |
| `np.square(` | 0 12 8 2 2 4 % | 48 52 4 % | p = 1.00 |
| `np.sqrt(` | 0 10 4 19 31 4 % | 10 12 21 % | p = 0.36 |

**리터럴 비교는 6실행 중 5실행이 0% 였다가 3실행 전부 12~69% 가 됐다.**
범위가 겹치지 않는다. 쓴 값도 `[1]` 하나에서 `[0, 1, 4, 8]` 로 늘었다.
**예산이 물리 상수를 막고 있었다.**

### ⚠️ "우회가 사라졌다" 는 **주장할 수 없다** — 앞선 보고를 정정한다

D-79 에서 `np.isfinite` 우회가 9.7% -> 0% 라고 썼다. **실행 단위로
보면 그것은 한 실행(arch24-s0)의 습관이었다.**

```
arch24-s0   25/48 = 52%
나머지 다섯  1, 0, 0, 0, 0 건
```

**한 실행의 습관을 모집단 비율로 읽은 것**이다. 실행 6개 중 2개만
한 번이라도 썼고, 새 3실행이 0인 것은 p = 0.50 — 아무 말도 못 한다.

`np.square` 가 4.9% -> 34.7%(제안 단위)로 뛴 것도 같다. 실행 단위로는
옛 5/6 실행도 쓰던 것이고 p = 1.00 이다. **씨앗에는 없으므로 진화 중
실행 안에서 번진 것**이고, 3실행으로는 못 가린다.

## 4. 실험 계획서 대비

```
✅ 검정력을 미리 계산했다 — 0건이면 결정적, 0~3건이면 억눌린다
✅ 1차/2차 Analyst 를 나눠 셌다
✅ 라운드 구간을 맞춰 비교했다 (r0~r1 / r2~r3 / r0~r3)
❌ ★ 세는 **단위**를 안 정했다 — 제안 단위로 세면 n 이 16배 부풀려진다
   실험 계획서에 "표본의 단위" 를 적었어야 했다
```

**이것이 이번 실험 계획서가 놓친 것이다.** 검정력은 계산했는데
**독립성**을 안 봤다.
