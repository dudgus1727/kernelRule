## 1. D-75 경로 — **한 번도 안 돌았다**

```
가설 10건 중 physical_requirement 가 채워진 것  0건
새 축 요구 0 -> FeatureWriter 호출 0 -> 만든 축 0
```

### 파싱 문제가 아니다

원본 응답 10건 전부에 **키가 있고 값이 `null`** 이다. 모델이 스스로
"필요 없다" 고 한 것이지 우리가 떨어뜨린 것이 아니다.

```
'physical_requirement' in h   10/10
값이 채워진 것                 0/10
```

### ★ 이 실행은 경로를 **시험하지 못했다**

같은 조건(F3 사람24) · 같은 모델(`gpt-5.6-luna` medium) · 같은
라운드 구간(r0~r1)의 옛 실행 6개와 견주면:

```
옛 조건 r0~r1   10/56 = 17.9%
새 조건 r0~r1    0/10 =  0.0%
Fisher 정확검정  p = 0.34        ★ 구분 불가
```

**17.9% 에서 10번 연속 안 나올 확률이 14% 다.** 우연으로 충분히
설명된다. **"경로가 안 돈다" 도 "억눌렸다" 도 이 자료로는 말할 수 없다.**
표본이 10건뿐이다.

### ⚠️ 내가 만든 교락 둘 — 억눌렀을 수 있다

```
1  필드 이름과 요구 수준을 바꿨다
   needs_new_feature "그 물리량의 **이름**"
   -> physical_requirement "그것이 무엇인지 **한 문장**"
   ★ 이름 한 단어보다 한 문장 쓰는 것이 문턱이 높다

2  안내문에 상한을 적었다
   "한 라운드에 만들 수 있는 축은 한둘입니다.
    정말 없는 축일 때만 채우세요"
   ★ 억제 문구를 내가 새로 넣었다
```

**둘 다 이번 실행 전에 내가 넣은 것이고, 검증되지 않았다.**
결과를 보고 이 문구를 고치면 그것은 표에 맞추는 것이므로(§12.3d)
**고치지 않았다.**

## 2. ★ D-78 — 리터럴이 돌아왔다

> ## ★ 2026-08-28 정정 — 아래 표는 **제안 단위**로 셌다
>
> 한 실행의 제안 24~48개는 같은 씨앗에서 나온 서로의 자손이다. 제안
> 단위 Fisher 는 표본 수를 16배 부풀린다. **실행 단위로 다시 세면**
> ([d75-run2.md](d75-run2.md)):
>
> ```
> 리터럴 비교      옛 6실행 0 0 0 0 0 2 %  ->  새 3실행 35 69 12 %
>                실행 단위 Fisher p = 0.0476   ★ 결론 유지
> np.isfinite   옛 6실행 52 2 0 0 0 0 %  ->  새 0 0 0 %
>                ★ 한 실행의 습관이었다. p = 0.50 — **아무 말도 못 한다**
> ```
>
> **"우회가 줄었다(방향은 맞다)" 는 서술을 철회한다.** 6.9% 는 모집단
> 비율이 아니라 한 실행(arch24-s0, 25/48)이 만든 값이었다.

같은 조건·같은 모델·**같은 라운드 구간**(각 실행의 앞 24개 optimize
호출 = r0~r1)으로 견줬다.

| | 옛 조건 (합산 예산) | 새 조건 (분기 상수 면제) | Fisher |
|---|---:|---:|---:|
| 제안 규칙 | 144 | 24 | |
| **비교에 숫자 리터럴** | **1/144 = 0.7%** | **3/24 = 12.5%** | **p = 0.0094** |
| `np.isfinite(` | 9/144 = 6.2% | 0/24 = 0.0% | p = 0.36 |
| `np.sign(` | 1/144 = 0.7% | 0/24 = 0.0% | — |
| 정당한 용도 없는 우회(위 둘) | 10/144 = 6.9% | 0/24 = 0.0% | p = 0.36 |
| `np.sqrt(` | 14/144 = 9.7% | 0/24 = 0.0% | p = 0.22 |
| `np.square(` | 5/144 = 3.5% | 2/24 = 8.3% | — |

**리터럴 비교가 0.7% -> 12.5% 로 올랐다 (p = 0.0094).** 예산이 상수를
막고 있었다는 것이 확인된다 — 풀자마자 쓴다.

**우회가 줄었는지는 아직 못 가린다.** 방향은 맞지만 n=24 로는
`10/144 -> 0/24` 가 p=0.36 이다. 기대값이 1.7건이라 0 이 나오는 것이
전혀 이상하지 않다.

### ⚠️ 검사기와 프롬프트를 **함께** 바꿨다 — 분리 불가

원칙 26 이 그렇게 하라고 한 것이다(모델은 프롬프트를 믿는다). 그래서
"예산이 풀려서" 와 "프롬프트가 예시를 보여줘서" 를 **설계상 나눌 수
없다.** 나누려면 검사기만 풀고 프롬프트를 그대로 두는 팔이 필요한데,
그것은 모델이 제약이 풀린 줄 모르는 팔이라 **아무 일도 안 일어난다.**

## 3. 실험 계획서 판정 적용

```
"요구 0건 -> 경로는 만들었으나 안 도는 것. 그것도 결과다.
 프롬프트를 고쳐 다시 돌리지 않는다"
```

**프롬프트를 안 고쳤다.** 다만 실험 계획서가 **"0건이면 안 도는 것"** 이라고
쓴 것은 **표본 크기를 안 따진 것**이었다. 10건으로는 17.9% 를 0% 와
구분할 수 없다. 판정을 이렇게 정정한다:

```
0/10 은 "안 돈다" 의 증거가 아니다. **아직 시험하지 못했다** 가 맞다.
경로를 시험하려면 가설 50~60건이 필요하다 (옛 조건에서 10건이 나온 규모).
```

**정정 자체를 기록한다** — 결과를 보고 기준을 무르게 한 것이 아니라,
실험 계획서가 놓친 것(검정력)을 적는 것이다.
