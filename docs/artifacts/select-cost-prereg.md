# 실험 계획서 — **선택 비용** (µs). LLM 0회

**측정 전에 쓴다.**

## 0. 왜

§2 의 첫 제약이 **"µs 안에 골라야 한다"** 이고, 그 제약으로 GBDT 를
배제해 왔다. **그런데 우리 쪽 수치가 없다.** regret 만 쟀다.

## 1. 세 팔 — 같은 기계, 같은 방식

```
A 우리    형상 하나의 후보 전부에 대해 피처 계산 -> 규칙 평가 -> argmin
          ★ 지금 구현 그대로 (pandas/numpy 벡터 경로)
          ★ 피처 계산을 **포함**한다 — 미리 계산해 두고 빼지 않는다
B 벤더    nvMatmulHeuristics 호출 한 번 (같은 형상)
          ★ 파이썬 바인딩을 거친다 — 우리와 같은 조건이다
C GBDT    학습된 모델로 그 형상의 후보 전부 예측 -> argmin
```

★ **GPU 를 안 쓴다.** 셋 다 CPU 예측이다.

## 2. 후보 수 — 두 줄로 낸다

```
전수    카탈로그 (kernel_id x split_k x mode) 합집합 89,255
필터 후 그 형상에서 legal 한 것         3,465 ~ 17,325 (중앙 15,015)
```

⚠️ **우리 후보 집합은 이미 필터 후다** — 표가 그 형상에서 실제로 돈 조합만
갖는다. 그래서 "필터를 적용하면 줄어든다" 가 아니라 **"이미 줄어든 것을
쓰고 있다"** 가 맞는 서술이다.

**필터 비용을 따로 잰다.** 카탈로그 정적 배열에 대한 벡터 비교
(정렬 나누어떨어짐 · split_k 청크 ≥ tile_k · smem 상한 · 레지스터 상한)로
**대표적인 필터**를 만들어 그 비용을 잰다.
⚠️ **kernelTab 의 실제 판정식이 아니다** — 비용의 자릿수를 재는 것이고,
그 사실을 결과에 적는다.

## 3. 측정 방법 — 미리 박는다

```
워밍업 5회 -> 측정 50회
★ 중앙값과 **최악값** 둘 다 낸다 (배포는 최악이 기준이다)
형상마다 따로 낸다. 형상 전체의 중앙/최악도 낸다
셋 다 같은 프로세스, 같은 파이썬, 연속 실행
```

## 4. 판정 — 미리 정한다

```
필터 후 우리 비용이 벤더와 **같은 자릿수(µs)**
   ★ "µs 안에 돈다" 를 그대로 쓸 수 있다
한 자릿수 이상 느리다
   ★ 그 제약 주장을 고친다 -> "GBDT 는 XX ms, 우리는 XX µs" 로 구체화
```

**어느 쪽이든 §2 의 제약 서술에 숫자를 넣는다.**

⚠️ 판정은 **중앙값과 최악값 둘 다**로 한다. 하나만 통과하면 그렇게 적는다.

## 5. 안 하는 것

```
[ ] 우리 쪽만 유리한 조건으로 재지 마라 — 파이썬 오버헤드는 양쪽 다
[ ] 피처를 미리 계산해 두고 그 시간을 빼지 마라
[ ] 중앙값만 내지 마라
[ ] 판정선을 결과 보고 정하지 마라
[ ] GPU 를 쓰지 마라
```
