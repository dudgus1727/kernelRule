# 실험 계획서 — **대표값 재측정** (`__import__` 결함 수정 뒤, n=6)

**LLM 호출 전에 쓴다.**

## 0. 왜 다시 재나

D-135 가 `compile_rule` 의 결함을 고쳤다 — 규칙이 `log(음수)` · 0 나누기 ·
overflow 를 한 번이라도 만들면 `KeyError: '__import__'` 로 **점수도 못
받고 버려졌다** (제안의 2.0%). 이제 그 제안들이 채점된다.

**조건 변경이다.** 지금 대표값(`F3rw-p8`, 1.0787)은 그 결함이 있는 코드로
나온 값이므로, 앞으로의 재측정과 나란히 못 놓는다 (원칙 4).

## 1. 조건 — 하나만 다르다

```
태그        ★ F3rw-p8-nan   (아래 §6 참고 — 옛 디렉토리를 **안 옮긴다**)
표          A6000 dev · 분할 nk11008 (학습 41 / 홀드아웃 20)
시드        n=6 (seed = 100+s)
라운드      24 · patience 0 (조기 종료 끔, D-132)
파라미터    8  -> 적합기 nelder-mead / 재시작 4 / 200 (`fitter_for`)
목적함수    regret@1
씨앗        `--seed-from runs/F3rw-p8-old` — 코드 해시 d5ee6da863
            (`F3rw-p8` · `F3rw-p8-p3` 와 **같은 씨앗**임을 확인했다)
모델        gpt-5.6-luna
트레이스     켠다 (`LoopConfig.trace` 기본값) — 6실행에 trace.jsonl
★ 다른 것    `compile_rule` 의 np.errstate 방어 **하나뿐이다**
```

## 2. 재는 것

```
최종 채점 = 체제별로 학습 분할에 재적합 -> 홀드아웃 20형상 (변경 없음)
비교 대상 = F3rw-p8 (같은 조건 · 결함 있는 코드) 중앙 1.0787
```

## 3. 판정선 — **0.0516 을 그대로 쓴다**

`campaign-spread.md` 가 방금 확인했다: 같은 조건 두 캠페인의 차이가 시드
산포만으로 기대되는 폭과 같고 (실측/기대 = 1.0배), 캠페인 성분을 넣어도
판정선은 0.0516 -> 0.0518 이다. **여기서 새로 정하지 않는다** (원칙 7).

## 4. 해석 — 미리 박는다

```
|새 - 1.0787| < 0.0516          ★ 구분 불가. **새 값을 대표값으로 삼는다**
                                  (조건 통일이 우선 — D-131 과 같은 규칙)
새가 0.0516 이상 좋다            결함 수정이 닿았을 수 있다. ⚠️ 캠페인 쌍이
                                  하나이므로 **"닿았다"로 확정하지 않는다**
새가 0.0516 이상 나쁘다          ★ 예상 밖. 멈추고 왜인지 본다 — 대표값을
                                  갱신하기 전에 원인을 적는다
```

⚠️ **이것은 실험이 아니라 조건 변경 + 대표값 갱신이다.** 캠페인 하나로는
결함 수정의 효과를 가르지 못한다 (`campaign-spread.md` §4 — 자유도 1).

## 5. 결과와 무관하게 기록하는 것 (LLM 0회)

```
1. 거부 사유별 수 — ★ `__import__` 가 **0** 이어야 한다 (되돌려 확인의 실전판)
2. trace.jsonl 이 6실행에 다 생기는가 · 첫 줄의 config 가 config.json 과 같은가
3. 라운드별 곡선이 r23 에서 아직 오르고 있는가 (D-134 의 질문)
4. 죽은 항 (`read_logs.py` §3, 묶는 방식) — 결함 수정 뒤에도 그대로인가
5. 옛 프롬프트가 맞춘 라운드마다 앞선 관측(`campaign-spread.md` §5)이
   이 캠페인에서도 보이는가  ★ 관측으로만 적는다. 판정 안 한다
```

## 5-2. ★ 추가 사전 등록 — **새 프롬프트가 느린가** (§16.3)

사용자가 §5 의 5번을 질문으로 격상했다. **캠페인이 끝나기 전에 적는다.**

```
관측 (campaign-spread.md §5)
  옛(옛 프롬프트) r11 에 간 곳(1.0762)을 새24(새 프롬프트)는 r23 에 간다
  r11 에서 새24 - 옛 = +0.0359
비용 (§16.3)
  라운드 12 -> 24 = LLM 2,800 -> 5,600 호출
★ 프롬프트 정리가 수렴 속도를 절반으로 만들었다면 그것은 개선이 아니다
```

**`F3rw-p8-nan` 의 r11 을 옛 1.0762 와 비교한다.** `nan` 도 새 프롬프트다
(`__import__` 수정만 새24 와 다르다).

```
nan r11 - 옛 r11 >= +0.018 (관측치 0.0359 의 절반 이상)
   ★ 재현됐다. 다음 질문은 "프롬프트 정리 중 무엇이 느리게 만들었나"
|nan r11 - 옛 r11| < 0.018  또는 부호가 반대
   ★ 재현 안 됐다 — 새24 의 +0.0359 는 캠페인 뽑기였다
```

⚠️ **판정이 아니라 재현 확인이다.** 캠페인 하나로 0.036 을 판정선
0.0516 위로 올릴 수 없다 (`campaign-spread.md` §4). 부호와 크기만 본다.
0.0516 을 넘더라도 **캠페인 쌍이 둘뿐이므로 유보를 유지한다.**

★ 산출물: 세 곡선(옛 / 새24 / nan)을 라운드별로 나란히.

## 6. ⚠️ 태그 규칙에서 **일부러 벗어난다**

D-128 §7 은 "대표값은 깔끔한 태그(`F3rw-p8`), 폐기는 접두/접미" 다.
그 규칙대로면 지금 `runs/F3rw-p8-s*` 를 옮기고 새 캠페인이 `F3rw-p8` 을
받아야 한다. **안 옮긴다.**

```
옮기면   round_curve.py GROUPS · canon-p8.md · log-reading.md ·
         campaign-spread.md 가 가리키는 대상이 **조용히 바뀐다**
         (canon-p8.md 의 재현 줄이 이미 그렇게 어긋나 있다 — F3rw-p8 로
          적혔지만 그 캠페인은 지금 F3rw-p8-p3 다)
안 옮기면 대표값이 `F3rw-p8-nan` 이라는 덜 깔끔한 이름에 앉는다
```

**문서가 가리키는 대상이 바뀌는 쪽이 더 나쁘다.** 이름을 양보한다.
`runs.md` 와 glossary 에 "지금 대표값 = `F3rw-p8-nan`" 을 적는다.
