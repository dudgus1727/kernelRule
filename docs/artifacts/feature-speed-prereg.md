# 실험 계획서 — **피처 파이프라인 최적화**. LLM 0회 · GPU 0회

**고치기 전에 쓴다.** 이것은 실험이 아니라 **구현 변경**이고, 성능
수치(regret)를 **한 자리도 바꾸면 안 되는** 변경이다.

## 0. 무엇이 문제인가 (D-142 실측)

```
규칙 평가 + argmin (15,015 config)   ★    297 µs   ← 방법이 요구하는 비용
피처 계산                            12,631 µs   ← 병목의 97%
합계                                12,974 µs
```

피처 14개는 **전부 벡터화돼 있다.** 그런데 (행,피처)당 **73 ns** 다 —
넘파이 산술의 수십 배. 피처 함수마다 pandas DataFrame 에서 **열을 다시
꺼내는** 것이 값을 정한다. 정적 열을 numpy 로 미리 바꿔도 안 줄었다
(12,954 µs) — 프레임 자체가 아니라 **접근 패턴**이다.

## 1. 목표 — 미리 박는다

```
15,015 config x 14 피처 = 210,675 값
조밀한 numpy 라면 200~500 µs 대여야 한다
★ 목표: 피처 계산 12,631 µs -> ★ 1,000 µs 미만
★ 그러면 선택 전체가 약 1.3 ms 가 된다
```

```
달성    피처 < 1,000 µs        ★ 성공
부분    1,000 ~ 4,000 µs       ★ 그대로 적는다. 실패가 아니다
미달    > 4,000 µs (3배 미만)   ★ 접근이 틀렸다 — 원인을 적고 멈춘다
```

## 2. ★ 결과를 어떻게 쓸지도 **미리** 정한다

최적화해도 **벤더와 자릿수가 다르다.**

```
낙관적으로   피처 500 µs + 평가 297 µs = 약 0.8 ms
벤더                                      46 µs
★ 여전히 17배
```

**그것은 구현이 아니라 알고리즘의 차이다.**

```
벤더   ★ 후보를 다 안 본다 — 해석적으로 하나를 지목한다
우리   ★ 후보 전부에 점수를 매긴다
```

**그러므로 최적화 뒤에도 "벤더만큼 빠르다" 를 쓰지 않는다.** 쓸 문장을
여기 미리 박는다:

```
★ "선택에 약 1 ms 가 든다. 벤더(46 µs)보다 느리고 GBDT(8.5 ms)보다 빠르다.
   후보 전부에 점수를 매기는 구조라 벤더의 해석적 지목과 자릿수가 다르다."
```

⚠️ 숫자는 실측으로 채운다. **위 문장의 형태만** 미리 정한 것이다.

그리고 그것이 **다음 연구 항목**이 된다 — 싼 대리로 후보를 수백 개로
줄이고 거기에만 규칙을 쓰는 방식. **이 계획서는 그것을 하지 않는다.**

```
         피처 함수에 그 배열 묶음을 넘긴다 (지금은 함수마다 df 에서 꺼낸다)

  ★ 피처의 정의 · 수식 · 이름 · 등록 순서
  ★ 규칙 코드 · 가중치 · 적합기 · 채점 절차
  ★ 프롬프트 (LLM 이 보는 것이 달라지면 조건 변경이다)
```

## 4. ★ 통과 조건 — **수치가 한 자리도 바뀌면 안 된다**

```
1. 모든 형상 · 모든 피처에서 옛 배열과 새 배열이 ★ 비트 단위로 같은가
   (np.array_equal, nan 은 nan 자리까지)
2. 644개 시험이 그대로 통과하는가
3. 대표값 최종 채점이 ★ 1.0886 그대로인가
```

**하나라도 어긋나면 되돌린다.** 속도를 얻자고 수치를 바꾸지 않는다.
