# ★ 생성 축을 쓰는 규칙이 옮겨지나 — 기술 확인

> **재현**: `python3 -m experiments.transfer_generated` (약 40분, **0 LLM 호출**)
> **원자료**: `transfer-generated.json`
> **출처 실행**: `cap1` (F2 · 1시드 · 12라운드 · **fold 0** · 커밋 `2392169`)

⚠️ **성능 비교가 아니라 기술 확인이다.** 출처 규칙은 **fold 0** 에서 나왔고
대상은 `nk11008` 분할이다. 숫자는 참고로만 읽는다.

⚠️ **D-157 의 전이 수치와 나란히 놓지 않는다.** 그때는 양쪽이 같은 사람 27개를
썼고, 여기서는 **규칙과 함께 축을 옮긴다.** 조건이 다르다.

## 1. 무엇을 옮겼나

```
규칙   cap1 최종 아카이브 최고 — regret 1.0339 · 가중치 52 · 셀 [0,2,2]
축     ★ 29개 = known5 5 + stage1 14 + ★ 루프가 만든 10
대상   5090 · 4090 · H100
방식   (a) 그대로 옮긴다 (출처에서 적합한 가중치) · (b) 대상에서 재적합
```

## 2. ★ 기술 — 셋 다 통과했다

```
표      레지스트리 재구성   행렬     형상수준 뒤집힘   새로 상수가 된 축   정적 검사
5090         396초         36초          0                 0            통과
4090         384초         35초          0                 0            통과
h100         724초         65초          0                 0            통과
```

★ **걱정한 두 실패 모드가 하나도 안 났다.**

```
(a) 형상 수준 판정이 표마다 갈릴 수 있다 -> ★ 29축 전부 그대로였다
(b) 대상에서 상수가 되는 축이 있을 수 있다 -> ★ 0개
```

출처(A6000)에서 형상 수준인 축은 셋(`roofline_ratio` ·
`output_aspect_ratio_deficit` · `vector_alignment_deficit`)이고 그중
`vector_alignment_deficit` 하나가 학습 형상에서 상수인데, **대상 셋에서도
똑같이 상수**였다. 즉 갈라지는 자리가 표를 옮겨도 같았다.

## 3. 비용 — 예상보다 훨씬 싸다

```
예상(지시서)   축당 16.6초 x 30 = 표당 약 500초
★ 실측         표당 35~65초 (축당 1.2~2.3초)
```

D-161 이 행 변환을 형상마다 한 번으로 바꾼 뒤 열 하나의 비용이 14.9초에서
1.5초로 떨어졌기 때문이다. **행렬은 병목이 아니다.**

⚠️ **레지스트리 재구성이 384~724초로 훨씬 비싸다.** `detect_shape_level` 을
축마다 따로 부르면서 매번 전 형상 행렬을 짓는다 — D-163 이 `load_generated`
안에서 고친 그 자리와 같은 모양인데, 이 스크립트의 known5/루프 축 경로는
아직 한 번으로 안 묶였다.
