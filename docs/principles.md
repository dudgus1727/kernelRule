# 반복해서 밟은 것

**새 세션은 이 문서부터 읽어라.** 이 프로젝트가 **두 번 이상 같은 자리에서
넘어진 것**만 모았다. 각 항목의 상세와 사례는 `decisions.md` 의 번호를 보라.

여기 있는 것은 전부 **실제로 밟은 것**이다. 예방적 조언이 아니다.

---

## 1. 조용히 아무것도 안 하는 장치 — 그리고 그 쌍둥이

장치가 있는데 안 도는 것이 **네 번 이상** 있었다. 에러가 안 나므로 잘 되고
있다고 읽힌다.

```
정의만 되고 안 쓰인 상수 / 주석에만 있는 기준 / 통째로 스킵되는데 초록불
```

**쌍둥이가 더 위험하다 — 조용히 *한쪽으로 판정*하는 것.**

```python
except (OSError, TypeError):
    return True          # 기본값처럼 보이지만 **주장**이다
```

`inspect.getsource` 가 `exec` 함수에서 항상 실패하는데 `True`("hw 를 쓴다")로
떨어져서, 하드웨어를 안 쓰는 **정상 피처가 전부 기각**됐다. F1 의 결론이
뒤집힐 뻔했다.

```
판정할 수 없으면 판정하지 마라 — 예외를 내라.
특히 그 기본값이 "더 안전한 쪽" 으로 보일 때 위험하다.
except 블록이 값을 반환하면 물어라 — 관측인가 추측인가.
```

→ D-37, D-38, §26.4, §26.4b

## 2. 같은 판정이 여러 곳에 있으면 갈린다

**세 번** 밟았다.

```
is_reference()   두 곳에서 다르게 판정
top_k / 동률     채점기와 앙상블이 다르게 정렬
모델 상수        실험 5개가 각자 들고 있었다
피처 렌더링      RuleWriter 만 정의를 받고 RuleEditor 는 이름만
```

**출처를 하나로 모으고, 두 번째 경로를 남기지 마라.** 남기면 다시 갈린다.

→ D-34, D-41, D-45

## 3. 동률은 예외가 아니라 기본 상황이다

이 표는 **29/66 형상이 최적에서 정확히 동률**이다 (타이머 눈금, 최대 84중).
같은 뿌리의 버그가 **세 번** 나왔다.

```
채점기 sorted([(score, time)])   점수가 같으면 시간으로 정렬 — 정답을 훔쳐본다
정답 집합 vs 단일 최적            명제가 뒤집힌다 ("stages=2 는 최적 0회" → 6/41)
argsort(argsort(x))              동률에 서로 다른 순위 — 가짜 결론이 나올 뻔
```

```
순위를 매길 때마다 동률 처리를 **명시하라.**
argsort / rankdata / sorted 를 쓰기 전에 "동률이면 무엇으로 가르는가" 를 답하라.
보존은 np.unique(x, return_inverse=True)[1], 가르는 것은 CandidateSet.top_k 하나로.
```

→ D-30, D-41, §30.7

## 4. 절차가 안 붙은 숫자는 비교하지 마라

두 숫자를 나란히 놓기 전에 **다섯**을 확인한다.

```
같은 절차 / 같은 분모 / 같은 집계 / 같은 데이터 / ★ 같은 모델
(엔드포인트와 reasoning_effort 도 "모델" 축이다)
```

이것을 안 지켜서 결론이 **세 번** 뒤집혔다. 정적 top-1 1.394(덮개 산물),
벤더 1.088(status 필터), 그리고 `1.0680` 이 `physics_seeded` 가 아니라
`evolved` 의 값이었던 것.

**숫자를 결론의 근거로 쓸 때는 재현 명령을 같이 적어라.**

→ D-31, D-46, §30.8b

## 5. 좋은 결과가 나오면 선택의 자유도부터 세라

"벤더를 넘었다" 를 **세 번** 썼고 세 번 다 틀렸다. 이유가 매번 달랐지만
형태는 같았다 — **어딘가에 고를 자유가 있었다.**

```
형상 선택   홀드아웃 19 중 11이 학습 형상이었다
시드 선택   시드 3개짜리 값이었다
묶음 선택   N개 중 최소를 골랐다
규칙 선택   아카이브에서 무엇을 골랐나
지표 선택   geomean 인가 승패인가 체제별인가
```

**각각이 낙관 편향을 만들고, 겹치면 곱해진다.**

```
"이 숫자를 얻기까지 내가 고른 것이 몇 개인가."
하나라도 있으면 그 선택을 고정하고 **새 데이터**에서 다시 재라.
```

→ D-36, D-40, D-46, D-50

## 6. "홀드아웃" 은 하나가 아니다

파이프라인의 **단계마다 학습하는 것이 다르다.**

| 학습하는 것 | 누가 | 그것의 홀드아웃 |
|---|---|---|
| 구조 | RuleEditor / Analyst | `splits.val` |
| 가중치 | `fit_weights` | 어떤 분할이든 그 안에서만 |
| 프롬프트·피처 설명 | **사람** | `splits.test` (봉인) |

홀드아웃 19형상 중 **11이 루프의 학습 형상**이었다. 구조는 그것들을 보고
진화했으니 **가중치만 홀드아웃**이었고, 그 값으로 "관문을 넘었다" 고 썼다.

**숫자를 낼 때 "이 홀드아웃은 무엇을 안 봤는가" 를 한 줄로 적어라.**

→ D-36, §10.2b, §12.3d

## 7. 판별력이 하한이다 — 못 재는 차이를 보고하지 마라

```
kernelTab   타이머 눈금이 config 순위를 가린다
kernelRule  시드 분산이 조건 차이를 가린다
```

구조 홀드아웃 표준편차가 **0.0274** 다 (`gpt-5.6-luna` 6시드).

```
차이 0.06   시드 4~5개
차이 0.03   시드 15개
차이 0.02   시드 30개 이상   ← 사실상 불가
```

**지금까지 재려던 것 대부분이 마지막 줄에 있다.** 실험을 더 해서 풀리지
않는다. **차이를 보고하기 전에 폭을 먼저 재라.**

### ★ 그리고 하한은 시드 폭만이 아니다 — **무작위 바닥**도 하한이다

`(a)` 규칙이 "정답 집합 원소를 상위 5% 안에 넣는 형상 비율 45%" 를 냈다.
미리 정한 기준이 "50% 근처면 위험하다" 라 **"위험하다 쪽"** 이라고 썼다.
그러고 나서 무작위 바닥을 재니 **47%** 였다.

```
"위험하다"       -> 틀린 서술
★ "무작위와 같다"  -> 옳은 서술. 훨씬 강한 진술이다
```

**바닥을 모르면 지표의 값을 읽을 수 없다.** 그리고 그 바닥을 **한 번만
뽑아서** 60% 로 적었다가 20번 평균 47% 로 고쳤다 — **바닥도 표본이다.**

```
지표를 보고하기 전에 무작위 바닥을 함께 내라.
★ 바닥도 여러 번 뽑아 평균을 내라. 한 번 뽑기는 바닥이 아니다.
```

→ D-40, D-53, D-99

## 8. 실패는 인프라 → 검사기 → 피험자 순서로 의심하라

**세 번** 겪었고 셋이 로그에서 **똑같이 보였다.**

```
검사기(inspect)   "LLM 이 피처를 못 만든다"     ← 실제로는 우리 버그
검사기(섭동 축)    "같은 제안을 16번 반복한다"    ← 실제로는 우리 버그
인프라(크레딧)     "거부 스키마 144건"          ← 호출이 안 갔다
```

**거부 사유가 한 종류로 몰릴 때** 특히 그렇다. 가장 싼 확인은
**거부된 것 하나를 손으로 읽어 보는 것**이다.

→ D-37, D-38, D-43, D-49

## 9. 문서와 코드가 어긋나면 — 어느 쪽이 틀렸는지 먼저 정하라

세 형태를 다 겪었다.

```
코드가 틀림   consumer_contract §9 가 옳고 구현이 틀렸다
문서가 틀림   설치 안내가 pydantic-ai 를 빠뜨렸다 (우리 환경엔 깔려 있었다)
수단이 없음   "기록하라" 고 적어 놓고 기록 코드가 없었다  ← 가장 조용하다
```

세 번째가 위험하다. **문서가 틀리면 언젠가 누가 따라 하다 걸리는데,
수단이 없으면 아무도 안 하고 아무 일도 안 일어난다.**

그리고 **없는 상태를 실제로 만들어 봐야 확인이다.** 흉내가 정확하지
않으면 검증이 아니다 (`import 하면 예외를 내는 모듈` ≠ 미설치).

→ D-48, D-51

## 10. 사용자가 정한 것을 실험 편의로 바꾸지 마라

모델을 대조용으로 한 번 바꿨는데, 그것이 **결정 없이 기본값으로 승격**됐다.

```
1. "대조로 한 번만" 쓴다        ← 일회성으로 보인다
2. 그 대조가 유익했다
3. 다음 실험도 그것으로 돈다     ← 아무도 결정하지 않았다
4. 열 개 실험 뒤, 기준선이 바뀌어 있다
```

결과: **그 위에 쌓은 결과를 전부 잃었다.** 절차가 틀려서가 아니라
**정하지 않았어야 할 것을 정해서**다.

**대조군은 일회성이어야 한다.** 승격은 물어라.

→ D-52

## 11. 계산 단계마다 "아무것도 안 했는가" 를 검사하라

가중치 적합기는 24회 중 13회를 **초기값 그대로** 돌려줬다. 예외도, 경고도,
로그 한 줄도 없었다. 그 위에서 우리는 "구조를 비교한다" 고 말하고 있었고,
절반은 사실 LLM 이 준 초기값을 비교한 것이었다 (D-54).

실패는 소리를 낸다. **아무것도 안 한 것은 소리를 내지 않는다.** 그래서
단계마다 "움직였는가" 를 자기가 신고하게 만든다 — `FittedRule.moved`,
`FittedRule.invariants()`, 라운드 요약의 `적합이동 2/12`.

이건 1번(조용히 아무것도 안 하는 장치)의 확장이다. 1번은 **장치가 안 도는** 것,
여기는 **장치는 돌았는데 결과가 그대로인** 것이다. 후자가 더 안 보인다.

**감시도 감시하라.** "안 움직임" 을 세는 계측을 처음 짰을 때, 감싼 함수에
적합 이후의 민감도 탐침이 섞여 들어와 "적합기가 더 나은 점을 버린다 5/24"
라는 없는 결함을 만들어 냈다 (D-55 정정). 감시가 무엇을 세고 있는지도
세어야 한다.

그리고 **항상 울리는 경고는 감시가 아니다.** `평가 상한에 닿았다` 는 24회
전부에서 뜬다 — 그건 경고가 아니라 상태다. 그 사실 자체가 발견이었지만
(수렴하지 못하고 예산을 다 쓴다), 신호로는 쓸 수 없다.

**★ 그리고 늘 켜진 경고에 시험이 기대고 있었다** (2026-08-28, D-76).
`test_fit_weights_warns_about_its_own_invariants` 는 "최소 한 건은
경고해야 한다" 를 확인했는데, 그 한 건이 늘 뜨는 상한 경고였다. **시험은
통과하고 있었지만 아무것도 지키지 않았다.** 늘 켜진 경고는 감시를 잃는
데서 그치지 않고 **그것에 기대는 시험까지 무력화한다.**

원인을 팠더니 **두 겹**이었다. 다듬기 평가를 상한과 견주고 있었고(세는
법), 고쳐도 재시작 일정이 예산을 설계상 전부 써서 여전히 늘 참이었다
(정의). **첫 겹만 고치고 "고쳤다" 고 보고할 뻔했다.** 늘 참인 것을
고칠 때는 **고친 뒤에도 늘 참인지 다시 재야 한다.**

```
경고가 늘 뜨면 사람만 무시하는 것이 아니다.
그 경고에 기대는 테스트가 아무것도 안 지키게 된다.
"이 경고가 뜬다" 를 검사하는 테스트를 쓸 때는
"안 뜨는 경우도 있는가" 를 함께 고정하라.
```

## 12. 검증 경로를 만들면 검증 대상의 결함이 드러난다

`runs/` 없이 점수를 다시 계산하려고 규칙을 파일로 내보냈다. 목적은 "내가
부정하지 않았음을 남이 확인할 수 있게" 였다. 그 과정에서 나온 것들:

- `W_FITTED` 가 **적합된 가중치가 아니라 초기값**을 쓰고 있었다. 내보내기가
  없었으면 거짓말하는 파일을 커밋했을 것이다.
- 내보낸 12규칙 x 2체제를 다시 적합시키자 **절반이 안 움직인다**는 것이
  처음 보였다 (D-54). 루프 안에서는 한 번도 보이지 않던 사실이다.
- ruff 가 커밋된 규칙을 **우리 스타일로 고쳐 쓰려** 했다. 그러면 커밋된
  코드가 실행된 코드와 달라져 검증이 무의미해진다 (`extend-exclude`).

그리고 **검사가 검사 대상의 결함에 의존할 수 있다.**

`render_features(registry=None)` 이 조용히 사람 24개로 떨어지는 폴백이
있었고, `test_diagnose_prompt_carries_the_report` 는 **그 폴백 덕분에
통과**하고 있었다. 테스트가 확인하던 것("Analyst 프롬프트에 피처 목록이
들어간다")은 사실이었지만, 들어간 목록이 테스트가 넘긴 것이 아니었다.
결함을 고치자 테스트가 깨졌고, 그것이 결함의 증거였다.

```
테스트가 깨졌을 때 물어라 — 코드가 틀렸나, 아니면 테스트가
틀린 것에 기대고 있었나. D-39 와 같은 부류인데 이번엔 테스트 쪽이다.
```

검증 경로는 결과를 확인하는 장치이기 전에 **파이프라인을 밖에서 한 번 더
실행해 보는 장치**다. 안에서는 안 보이던 것이 밖에서 보인다.

## 13. 채점이 틀렸으면 그 위의 진화는 무효다

재적합은 **최종 산출물만** 고친다. 진화 궤적은 못 되돌린다. 부모 선택,
아카이브 갱신, 조기 종료 — 12라운드 x 12제안이 이미 그 점수로 걸러졌다.
그렇게 나온 것은 "이 파이프라인이 만들 수 있는 것" 이 아니라 **다른
파이프라인이 만든 것**이다.

```
"확인이 안 되니 안 한다" 와 "틀린 채로 둔다" 를 혼동하지 마라.
시드 폭 때문에 개선을 확인 못 하는 것은,
틀린 값을 조건 달고 써도 된다는 근거가 아니다.
```

무효가 된 수치는 **지운다.** 폐기 배지를 붙여 남기면 다음 사람이 배지를
놓치고 수치를 쓴다 — 이 저장소가 이미 겪었다(프롬프트에 "이 내용을
뺐습니다" 라고 적었는데 그 문장 안에 내용이 그대로 있었다). 교훈은
**현상으로** 남기고 숫자는 뺀다. git 이력이 정정 이력을 대신한다.

kernelTab 은 드리프트 5% 로 226,211행을 버렸다. **같은 프로젝트가 같은
기준을 두 번 다르게 적용하면 안 된다.**

## 14. 계측을 붙이면 계측 자체가 결함을 만든다

```
발견이 나오면 "그것이 계측의 산물인가" 를 먼저 확인하라.
```

## 15. 기준이 재려던 것과 실제로 재는 것이 다를 수 있다

"적합기가 제 일을 했는가" 를 재려고 **이동률**(w != w0 인 비율)을 기준으로
박았다. 그런데 초기값이 이미 최적이면 안 움직이는 것이 정답이다. 실제로
정지 9건 중 8건이 그랬다 — 무작위 400점이 초기값을 못 이겼다.

```
이동률은 "적합기 품질" 이 아니라 "초기값이 나쁜 비율" 을 재고 있었다.
```

**측정 대상이 아니라 측정 도구가 틀렸다.** 갈라야 하는 것은 과정과 결과다.

```
이동률   출발점에서 벗어났는가              과정
도달률   손 닿는 곳보다 나쁜 데서 끝났는가   결과   <- "제 일을 했는가" 의 정의
```

그리고 새 지표도 자기 조건을 달고 다녀야 한다. 도달률은 무작위 탐색과의
비교일 뿐이다 — 8차원에 4000점은 성기고, 표본 범위가 실제 최적을 덮는다는
보장도 없다. **"적합기가 최적을 찾는다" 가 아니라 "무작위 N 점보다 나쁜 데서
끝나는 경우가 x% 다"** 가 정확한 서술이다.

**기준은 사전에 박되, 그 기준이 무엇을 재는지도 사전에 따져라.** 이번 건은
결과를 보기 **전에도** 잡을 수 있었다 — "이동률 90%" 를 제안하면서
**"안 움직인 것이 나쁜가"** 를 아무도 묻지 않았다. 물었으면 반례가 바로
나왔다: 초기값이 최적이면 안 움직이는 것이 정답이다.

```
기준을 박기 전에 물어라
  이 지표가 낮으면 정말 나쁜가 — 반례를 하나 대 봐라
  이 지표가 높으면 정말 좋은가 — 속일 방법을 하나 대 봐라
```

그리고 결과를 보고 기준을 바꾸는 것은 D-50 이 금지한 행위이므로, 결함을
발견해도 **스스로 교체하지 말고 결함으로 기록하고 승인을 받아라.**
(이번에는 그렇게 했고, 교체가 승인됐다.)

→ D-56

## 17. `finally` 는 모든 종료 경로를 덮지 않는다

D-33 에서 "중간에 죽어도 산출물을 남긴다" 며 `try/finally` 를 넣었다.
**SIGTERM 에서는 안 돈다** — 기본 핸들러가 스택을 안 풀고 즉시 죽는다.

실측으로 확인했다. `timeout 25` 로 죽이니 증분 append 한
`proposals.jsonl` 만 남고 `summary.json` 은 안 써졌다.

```
1차 방어선   증분 append — 값비싼 것(LLM 호출)은 만들자마자 디스크로
2차 방어선   try/finally — 파생물(요약, 집계)을 남긴다
그리고       신호를 예외로 바꿔야 2차가 실제로 돈다
```

**KeyboardInterrupt(SIGINT)는 되고 SIGTERM 은 안 되는 비대칭**이 함정이다.
Ctrl-C 로만 시험하면 통과한다.

## 18. 기준을 못 넘었으면, 기준이 아니라 **전제**를 물어라

사전 기준은 결과를 보고 바꾸면 오염이다 (D-50). 그런데 **못 넘었을 때
할 수 있는 질문이 하나 더 있다.**

```
기준을 바꾸지 마라.  "그 기준이 전제한 조건이 아직 유효한가" 를 물어라.
```

적합기 도달률이 83.3% 로 90% 에 미달했다. 실패 4건을 조건별로 갈랐더니
**넷 다 `lunaNAMES`(피처 설명 없음) 쪽**이었고, 설명 있는 12건은
**전부 도달**했다.

기준은 "A/B 두 조건으로 재실행한다" 를 전제하고 세워졌다. 그런데 A/B 는
이미 "구분 불가" 로 결론이 났고, 피처 설명은 기본으로 반영됐다.
**재실행을 단일 조건(설명 있음)으로 설계하면 실패가 0/12 다.**

```
이것은 기준을 낮추는 것이 아니다.
기준이 재던 대상(두 조건 혼합)을 안 쓰는 것이다.
```

**구분하는 법:**

```
기준 낮추기   90% -> 80% 으로 바꾼다                    ★ 오염
전제 바꾸기   실패가 몰린 조건을 실험에서 뺀다            정당
              단, 그 조건을 뺀 이유가 실패 때문이 아니어야 한다
```

마지막 줄이 핵심이다. 여기서는 A/B 를 안 하는 이유가 **"이미 결론이
났으니까"** 이지 "거기서 적합기가 실패하니까" 가 아니다. 순서가 반대면
그것도 오염이다.

**그리고 미달 사실은 그대로 기록한다.** "통과했다" 가 아니라
**"미달인데 우회 가능하다"** 다.

→ D-59, D-60

## 20. 자동 검사는 "같은 말" 을 잡지만 "같은 뜻" 은 못 잡는다

역할 파일 사이에 30자 이상 같은 줄이 있으면 실패하는 검사를 붙였고,
붙이자마자 하나 잡았다 (원칙 2 가 실재한다는 증거다).

**그런데 `role/architect.md` 는 예산 규칙을 자기 문구로 다시 설명하고
있었고 그 검사를 통과했다.** 문장이 달랐기 때문이다.

```
같은 말   문자열 비교로 잡힌다
같은 뜻   ★ 안 잡힌다. 사람이 전문을 읽어야 한다
```

그래서 **최종 문자열을 눈으로 읽는 절차를 빼면 안 된다.** 자동 검사는
회귀를 막는 장치이지 리뷰를 대신하는 장치가 아니다.

부분적으로는 대리 검사를 만들 수 있다 — "Architect 프롬프트에 `regret` =
정의가 있으면 실패" 처럼 **역할별 금지 목록**을 박는 것이다. 의미상
중복을 일반적으로 잡지는 못하지만, **한 번 발견한 것이 다시 들어오는
것**은 막는다.

→ §30.10.2b, 원칙 16

## 21. 생성 전략을 고치기 전에 프롬프트를 먼저 정리하라

FeatureWriter 산출물이 한 축에 몰렸다 (`split_k_*` 3개, `cta_*` 5개).
진단은 **"20번 자유롭게 만들라는 전략이 방향을 안 준다"** 였고, 그래서
영역을 먼저 나누고 영역별로 만들게 하는 장치를 붙였다.

**틀렸다.** 교락을 없애려고 프롬프트만 바꾼 조건을 따로 돌렸더니:

```
프롬프트 개편 (전략 그대로)   엄격 재발견 0 -> 6   ★
카테고리화   (프롬프트 그대로)              6 -> 3
```

편중도 프롬프트 개편만으로 사라졌다. **원인은 나쁜 예시 하나와 규칙
얘기로 부푼 공용 블록이었다.**

```
"어떻게 물어보나" 보다 "무엇을 주나" 가 크다.
전략을 바꾸기 전에 프롬프트에서 **필요 없는 것을 빼고**
**예시를 제대로 주었는지** 먼저 확인하라.
```

그리고 이 결론은 **(나)를 따로 돌렸기 때문에** 나왔다. (가)와 (다)만
비교했으면 "카테고리화가 재발견을 줄인다" 는 반대 결론이 나왔을 것이다
(D-31).

→ D-63, §30.10

## 22. 쓸 수 없는 필드를 목록에 올리지 마라

`field_block` 이 `p.dtype` 을 원시 필드로 보여줬다. 그런데 그것은
**문자열**이고, 바이트가 필요한 roofline 을 만들려면
`np.dtype(...).itemsize` 가 필요한데 샌드박스 허용 목록에 없다.

LLM 은 `산술_대역폭_압력` 영역에서 **세 번 연속 거부**됐고, 그 영역은
건너뛰어졌다. 기록에는 "원시 값으로 표현하기 어렵다" 로 남았다.

```
★ 그것은 사실이 아니었다. dtype 은 있었고 바이트로 바꿀 길이 없었을 뿐이다.
```

```
목록에 올린다는 것은 "쓸 수 있다" 고 말하는 것이다.
쓸 수 있는지 실제로 확인하고 올려라.
그리고 유도값이 필요하면 유도해서 노출하라 — 유도값은 새 정보가 아니다.
```

`p.bytes_per_element` / `p.acc_bytes_per_element` 를 노출했다. `dtype`
에서 계산되므로 정보가 늘지 않는다.

**발견 경로가 중요하다.** 이것은 "LLM 이 무엇을 못 만드는가" 를 스스로
말하게 한 장치(영역 나누기 + 영역별 실패 기록)가 찾아냈다. 자유 생성만
했으면 LLM 이 그냥 다른 축을 만들고 넘어갔을 것이다.

→ D-63, §30.11

## 23. 한 자리에서 고쳤으면 다른 자리를 전수 조사하라

```
결함을 하나 발견하면 "같은 종류가 어디 또 있나" 를 검색하라.

```

### ★ 이 원칙을 쓴 직후에 같은 형태로 재발했다

`load_generated(table=...)` 를 만들고 **`--extend-from` 경로에만

```
빠뜨릴 수 있는 인자에 기본값을 두지 마라.
`table` 을 필수 키워드로 만들면 빠뜨린 호출부가 TypeError 로 죽는다.
정말 필요 없으면 `table=None` 을 **명시**하게 하라 —
그러면 "빠뜨린 것" 과 "일부러 안 쓴 것" 이 구분된다.
```

전수 조사는 사람이 하고 사람은 놓친다. **놓칠 수 없게 만드는 편이 낫다**

### 그런데 그 검사에도 한계가 있다

`test_no_prompt_hardcodes_a_registry_feature_name` 은 **등록된 이름**만
잡는다. 등록 안 된 물리 개념을 자연어로 지목하는 것은 못 잡는다.

```
"메모리 바운드 형상에서는 트래픽이 중요하다"   ★ 안 잡힌다
```

## 24. 능력이 "없다" 를 보고하기 전에, 세는 방법이 한 형태만 세는지 보라

한 세션에서 세 번 밟았다. **세 번 다 "LLM 이 못한다" 로 보고할 뻔했다.**

```
D-55   민감도 탐침이 계측에 섞여 "적합기가 더 나은 점을 버린다 5/24"
D-67   형상 수준 피처를 안 넘겨 "p.* 분기 0/10"
D-68   if / np.where 만 세어 "형상 수준 피처를 안 쓴다"
```

세 번째가 가장 미묘하다. **분기는 세 가지로 표현된다.**

```python
if p.<형상값>:                      # 이산
    s = s + f.<이름> * w[3]
s = s + np.where(p.<형상값>, A, B) * w[3]   # 이산, 항의 내용을 바꾼다
s = s + f.<이름> * p.<형상값> * w[3]        # ★ 연속, 실효 가중치를 바꾼다
```

셋 다 "형상마다 다르게 판단한다" 를 표현한다. `if` 만 세면 **세 번째를
쓰는 규칙이 "체제를 안 나눈다" 로 잘못 읽힌다.**

```
어떤 능력이 없다고 말하기 전에 물어라 —
그 능력이 **내가 세는 형태로만** 나타나는가.
그리고 실물을 눈으로 하나 읽어라 (원칙 16, 20).
```

이것은 원칙 8(인프라 → 검사기 → 피험자)의 계측 판이다. 피험자를
의심하기 전에 **세는 자를 의심하라.**

→ D-55, D-67, D-68

## 26. 검사기와 프롬프트가 갈리면 **모델은 프롬프트를 믿는다**

```

사람에게는 코드가 이기지만 LLM 에게는 프롬프트가 전부다.
제약을 풀거나 조일 때 검사기와 프롬프트를 반드시 함께 고쳐라.
```

이 저장소의 다른 곳에서는 **"문서와 코드가 갈리면 코드가 이긴다"** 가
맞다 — 실행되는 것이 코드이므로. **LLM 에게는 반대다.** 모델은 검사기를
읽지 않는다. 프롬프트에 적힌 것이 모델이 아는 제약의 전부다.

그대로 뒀다면 모델은 제약이 풀린 줄 모르고 계속 우회했을 것이다** —
`np.sign(x)` 로 1 을 만드는 짓을. 그리고 `architect.md` 에는
**"가중치 8개를 쓰려면 숫자를 하나도 쓰지 마세요" 라는 이제 틀린 문장**이
남아 있었다. 그것을 지우지 않았으면 완화가 아무 효과도 없었다.

반대 방향도 같다. 제약을 **조일** 때 프롬프트를 안 고치면 모델은 왜
거부당하는지 모르고 같은 실수를 반복한다 — `weight_reuse_message` 와
`literal_budget_message` 를 LLM 경계로 뺀 이유가 그것이다.

→ D-78, D-35, §30.10

```

```

```
유의해지는 관측 수 k 를 적는다 — "k 이하면 X, k+1 이상이면 구분 불가"
```

비슷해도 중간 크기의 효과는 여전히 있을 수 있다.

## 28. 표본 하나가 **무엇인지** 먼저 정하라 — 한 실행의 제안들은 독립이 아니다

```
사전 등록에 "표본의 단위" 를 적어라.
한 실행 안의 제안 48개는 같은 씨앗에서 나온 서로의 자손이다.
제안 단위로 세면 표본 수가 16배 부풀고, 한 실행의 습관이
모집단 비율로 읽힌다.
```

D-79 에서 "우회가 9.7% -> 0% 로 줄었다(방향은 맞다)" 고 썼다.
실행 단위로 다시 세니 **9.7% 는 한 실행(25/48 = 52%)이 만든 값**이고
나머지 다섯 실행은 0~2% 였다. 진화가 습관을 자손에 퍼뜨리므로
**제안은 독립 표본이 아니다.**

원칙 27(검정력)과 짝이다. 검정력을 계산해도 **단위가 틀리면 그 계산이
틀린 n 위에서 돈다.**

```
실행 단위로 세면 결론이 남는 것과 사라지는 것이 갈린다.
D-80: 리터럴 증가는 남았고(0/6 -> 3/3, p=0.048),
      우회 감소는 사라졌다(p=0.50).
```

### ★ 그리고 한 단계가 더 있었다 — **캠페인** (D-82)

실행 단위로 고쳤는데 또 틀렸다. **한 캠페인의 6실행은 2단계가 만든
씨앗 규칙 하나를 공유한다.** `stage3` 이 같은 씨앗으로 6번 시작한다.

```
씨앗에서 오는 성질은 캠페인당 **한 번만** 뽑힌다.
6실행을 독립 표본으로 쓰면 그 성질에 대해 실효 n 이 1 이다.
```

실제로 밟았다: 기준선 캠페인의 씨앗은 피처 12개를, 새 캠페인의 씨앗은
6개를 쓴다. 그리고 44실행에서 **"규칙이 쓰는 피처 수"와 "새 축 요구율"이
rho = +0.566 (p = 0.0001)** 로 붙어 있다. 두 캠페인이 그 축의 양 끝에
있어서, 요구율 차이를 프롬프트 탓으로 읽을 수 없었다.

```
제안 단위(D-79)  ->  실행 단위(D-80)  ->  캠페인 단위(D-82)
두 번 틀렸다. 매번 "무엇이 공유되는가" 를 안 물어서다.
```

### ★ 그리고 캠페인 위에도 층이 있다

```
제안  ->  실행  ->  캠페인  ->  표  ->  모델
```

두 캠페인을 견주는 것도 **표와 모델 층에서는 1 대 1** 이다. 이
저장소의 모든 수치가 A6000 번들 하나와 `DEFAULT_MODEL` 하나 위에
있으므로, "이 표에서" 와 "이 모델에서" 를 뗀 문장은 쓸 수 없다.

```
표본 단위를 정할 때 위로 어디까지 공유되는지 **끝까지** 물어라.
각 층에서 "이것이 공유되면 그 효과에 대해 n 은 얼마인가" 를 답하라.
두 번 틀린 것은 그 질문을 **한 층에서만** 했기 때문이다.
```

사전 등록에 **"공유되는 것" 목록을 끝까지 적는다.** D-83 의 등록이
첫 사례다.

## 29. **거부율이 낮은 것이 좋은 신호가 아닐 수 있다**

```

                      (D-54)
"요구가 0건이다"       필요 없어서일 수도, 눌려서일 수도 (D-79 ~ D-84)
```

**"나쁜 일이 안 일어났다" 는 관측은 언제나 두 가지를 뜻한다** — 잘 되고
있거나, **아무 일도 안 일어나고 있거나.**

```
그래서 "안 일어났다" 를 볼 때마다 **짝이 되는 양의 지표**를 함께 보라.
  거부율      <-> 채점된 제안 비율          (D-89)
  경고 발화   <-> 그 조건을 일부러 만들었을 때 뜨는가   (D-76)
  적합 이동   <-> 도달률 (무작위 탐색 대비)   (D-56, D-77)

```

**오른쪽 열이 없으면 왼쪽 열은 읽을 수 없다.** 네 사례 모두 왼쪽만 보고
한 번씩 잘못 읽었고, 오른쪽을 붙이고 나서야 갈렸다.

```
어느 구간을 쟀는지와  그 구간이 전체의 몇 %인지를  함께 적어라.
★ 그 두 번째 숫자가 없는 속도 향상은 전체에 곱할 수 없다.
```

증상도 미리 보였다. 라운드 시간이 117초에서 1013초까지 **8.7배**로
흔들렸다 — 계산이 병목이면 그렇게 안 흔들린다.

→ D-96, D-95

## 33. 표본을 줄일 때 **중앙값만 보지 마라** — 꼬리가 무너진다

5090 가중치를 학습 41형상 대신 k형상으로만 맞춰 봤다.

```
k=4 (9.8%)   중앙 손실 +0.0276   ← 이것만 보면 "10% 면 된다"
             ★ 최악 2.3488       최적의 2.3배를 고른다
             ★ 8번에 1번이 1.15 를 넘는다
```

**평균이 조금 나빠지는 것이 아니다. 대부분은 괜찮고 몇 번에 한 번
크게 망한다.** 꼬리가 접히는 지점은 중앙값이 접히는 지점보다 훨씬
뒤에 있다 — 중앙은 k=4 에서 이미 쓸 만한데 파국은 k=12 까지 남는다.

```
표본 크기를 줄일 때는 **파국 비율과 최악**을 주 지표로 놓아라.
중앙값은 보조다.
```

이것은 §30.4(geomean 이 소수 형상에 끌린다)의 다른 얼굴이다 — 그때는
**형상 축**이었고 이번엔 **뽑기 축**이다. 같은 함정이 축을 바꿔 다시
나왔다.

→ D-98, §29.5, §30.4

## 34. 실행 상태를 **그 명령의 다음 줄로** 확인하지 마라

```
ruff check X && nohup python3 X > log 2>&1 &  echo started
```

ruff 가 한 줄을 잡아 `&&` 가 끊겼는데 **`echo started` 는 그대로
찍혔다.** 한 시간 뒤에야 로그 파일이 없다는 것으로 알았다.

```
"명령을 냈다" 와 "돌고 있다" 는 다르다.
★ 로그 파일과 프로세스로 확인하라.
```

같은 자리에서 두 번째다. `pkill -f <패턴>` 이 **자기 셸의 명령줄에도
그 패턴이 들어 있어서** 자기를 죽인 적이 있고, `until ! pgrep -f X`
감시가 **자기 자신을 세느라** 영원히 안 끝난 적이 있다. 셋 다
**"명령줄 문자열로 상태를 판정" 했다가 그 문자열이 자기를 가리킨**
경우다.

→ D-98, 원칙 1(조용히 아무것도 안 하는 장치)

## 35. 한쪽이 특정 조건에 몰려 있으면 **통째로 본 값이 뒤집힌다**

파국(홀드아웃 > 1.15)의 원인이 과적합인지 적합 실패인지 가르려고
`fit_regret` 을 견줬다.

```
통째로     파국 1.0145  나머지 1.0256   ★ 파국이 더 잘 맞는다 (p = 0.0296)
k 로 층화   k=2  1.0094 vs 1.0083      ★ 파국이 더 **못** 맞는다
           k=4  1.0252 vs 1.0189      방향이 전부 뒤집힌다
           k=8  1.0394 vs 1.0271
```

파국은 **낮은 k 에 몰려 있고**, 낮은 k 는 형상이 적어 원래 적합값이
낮다. 심슨의 역설이다. 통째로 본 `p = 0.0296` 을 그대로 읽었으면
맞는 결론(과적합)에 **틀린 근거**를 붙일 뻔했다.

```
두 무리를 견줄 때 한쪽이 특정 조건에 몰려 있는지 먼저 보라.
층화해서 각 층 안에서 견줘라.
★ 그리고 물어야 할 것이 수준(level)이 아니라 격차(gap)일 때가 많다.
```

실제로 답을 준 것은 격차였다 — 모든 k 에서 파국의 적합→홀드아웃 격차가
나머지의 2~4배였고(0.14~0.21 대 0.03~0.08), 파국 34건의 적합 regret 은
중앙 1.0145(최소 1.0000)로 **자기 표본에서는 거의 완벽**했다. 그것이
과적합의 서명이다.

→ D-98, 원칙 4

## 36. 기본값을 바꾸는 것은 **호출부 전부를 바꾸는 것**이다

`fit_weights(objective=...)` 의 기본을 `"regret"` 에서 `"rank"` 로
바꿨다. 한 줄이다. 그런데:

```
kernelrule/core/canonical.py   ★ 정준 채점 경로 — 이 프로젝트의 모든 수치
experiments/*.py                20개 파일 24곳
```

**전부 조용히 다른 것을 재게 됐다.** 아무도 그 파일들을 안 고쳤는데
동작이 바뀌었다.

```
새 인자를 **명시적으로** 넘기게 하는 것보다 기본값을 바꾸는 것이 위험하다.
호출부가 변경 없이 의미만 바뀌므로 diff 에 안 보인다.
★ 기본값을 바꿀 때는 호출부를 전수 조사하고, 옛 조건을 재현하는 곳은
  **명시**하게 하라. 그리고 그것을 시험으로 고정하라.
```

원칙 23("한 자리에서 고쳤으면 다른 자리를 전수 조사하라")의 특수형인데,
**"고친 자리" 가 없다는 점이 다르다** — 고친 것은 기본값 한 줄뿐이다.

→ D-101, D-103

## 37. "잘 됐나" 를 재는 지표는 **재는 대상과 같은 것**이어야 한다

16차원 적합기를 순위 손실로 다시 쟀다. 도달률이 **0%** 로 나왔다.

```
적합    objective="rank"
탐침    ★ prob.regret 로 고정돼 있었다
-> 순위 손실로 맞춘 결과를 regret 으로 견줬다
```

**"순위 손실로도 16차원은 안 된다" 로 보고할 뻔했다.** 탐침을 맞추니
100% 였다.

```
품질 지표(도달률·이동률·수렴)가 **목적함수를 하드코딩**하고 있지
않은지 보라. 목적함수가 하나뿐일 때는 안 보이고, 둘이 되는 순간
조용히 어긋난다.
```

원칙 15("기준이 재려던 것과 실제로 재는 것이 다를 수 있다")의 한
형태이고, 이번에는 **목적함수 축**에서 났다.

→ D-103

## 이 문서를 쓰는 법

여기 넣는 기준은 **"두 번 이상 밟았는가"** 다. 한 번 겪은 것은
`decisions.md` 에 시간순으로 남기고, **같은 자리에서 두 번째로 넘어졌을 때**

10개를 넘기면 무엇이 중요한지 알 수 없게 된다. 새 항목을 넣을 때는

## 38. 검사가 **통과했다**는 것과 검사가 **작동한다**는 것은 다르다

```python
def test_rule_writers_get_the_budget():
    assert "8" in body
```

이 시험은 예산이 16 으로 바뀌어도 통과한다 — 8 은 피처 설명에도 나온다.
`--rule-budget 16` 캠페인 하나(12라운드 x 3시드)가 8 로 돌았고, 시험은
내내 초록이었다.

```
조건을 검사하는 시험은 **조건을 바꿔가며** 돌려라. 한 값에서만
돌린 검사는 그 값이 갈린 것을 못 본다.
```

같은 자리를 여러 번 밟았다: `layer` 전략이 아무 것도 안 하고 있었고,
노이즈 관문이 fail-open 이었고, `except Exception: return set()` 이
자기 배선 오류를 삼켰다. 전부 **"검사가 있다" 와 "검사가 뭔가를 거른
적이 있다" 를 혼동한 것**이다.

실무: 새 검사를 넣을 때 **일부러 틀리게 만들어 한 번 떨어뜨려 보라.**
안 떨어지면 그 검사는 없는 것이다.

원칙 15("재려던 것과 실제로 재는 것이 다를 수 있다")를 **시험 축**에
적용한 것이다.

→ D-105
