# 반복해서 밟은 것

**새 세션은 이 문서부터 읽어라.** 이 프로젝트가 **두 번 이상 같은 자리에서
넘어진 것**만 모았다. 각 항목의 상세와 사례는 `decisions.md` 의 번호를 보라.

여기 있는 것은 전부 **실제로 밟은 것**이다. 예방적 조언이 아니다.

---

## 1. 조용히 아무것도 안 하는 장치 — 그리고 그 쌍둥이

장치가 있는데 안 도는 것이 **네 번 이상** 있었다. 에러가 안 나므로 잘 되고
있다고 읽힌다.

```
정의만 되고 안 쓰인 상수 / 주석에만 있는 기준 / 통째로 스킵되는데 초록불
```

**쌍둥이가 더 위험하다 — 조용히 *한쪽으로 판정*하는 것.**

```python
except (OSError, TypeError):
    return True          # 기본값처럼 보이지만 **주장**이다
```

`inspect.getsource` 가 `exec` 함수에서 항상 실패하는데 `True`("hw 를 쓴다")로
떨어져서, 하드웨어를 안 쓰는 **정상 피처가 전부 기각**됐다. F1 의 결론이
뒤집힐 뻔했다.

```
판정할 수 없으면 판정하지 마라 — 예외를 내라.
특히 그 기본값이 "더 안전한 쪽" 으로 보일 때 위험하다.
except 블록이 값을 반환하면 물어라 — 관측인가 추측인가.
```

→ D-37, D-38, §26.4, §26.4b

## 2. 같은 판정이 여러 곳에 있으면 갈린다

**세 번** 밟았다.

```
is_reference()   두 곳에서 다르게 판정
top_k / 동률     채점기와 앙상블이 다르게 정렬
모델 상수        실험 5개가 각자 들고 있었다
피처 렌더링      Architect 만 정의를 받고 Optimizer 는 이름만
```

**출처를 하나로 모으고, 두 번째 경로를 남기지 마라.** 남기면 다시 갈린다.

→ D-34, D-41, D-45

## 3. 동률은 예외가 아니라 기본 상황이다

이 표는 **29/66 형상이 최적에서 정확히 동률**이다 (타이머 눈금, 최대 84중).
같은 뿌리의 버그가 **세 번** 나왔다.

```
채점기 sorted([(score, time)])   점수가 같으면 시간으로 정렬 — 정답을 훔쳐본다
정답 집합 vs 단일 최적            명제가 뒤집힌다 ("stages=2 는 최적 0회" → 6/41)
argsort(argsort(x))              동률에 서로 다른 순위 — 가짜 결론이 나올 뻔
```

```
순위를 매길 때마다 동률 처리를 **명시하라.**
argsort / rankdata / sorted 를 쓰기 전에 "동률이면 무엇으로 가르는가" 를 답하라.
보존은 np.unique(x, return_inverse=True)[1], 가르는 것은 CandidateSet.top_k 하나로.
```

→ D-30, D-41, §30.7

## 4. 절차가 안 붙은 숫자는 비교하지 마라

두 숫자를 나란히 놓기 전에 **다섯**을 확인한다.

```
같은 절차 / 같은 분모 / 같은 집계 / 같은 데이터 / ★ 같은 모델
(엔드포인트와 reasoning_effort 도 "모델" 축이다)
```

이것을 안 지켜서 결론이 **세 번** 뒤집혔다. 정적 top-1 1.394(덮개 산물),
벤더 1.088(status 필터), 그리고 `1.0680` 이 `physics_seeded` 가 아니라
`evolved` 의 값이었던 것.

**숫자를 결론의 근거로 쓸 때는 재현 명령을 같이 적어라.**

→ D-31, D-46, §30.8b

## 5. 좋은 결과가 나오면 선택의 자유도부터 세라

"벤더를 넘었다" 를 **세 번** 썼고 세 번 다 틀렸다. 이유가 매번 달랐지만
형태는 같았다 — **어딘가에 고를 자유가 있었다.**

```
형상 선택   홀드아웃 19 중 11이 학습 형상이었다
시드 선택   시드 3개짜리 값이었다
묶음 선택   N개 중 최소를 골랐다
규칙 선택   아카이브에서 무엇을 골랐나
지표 선택   geomean 인가 승패인가 체제별인가
```

**각각이 낙관 편향을 만들고, 겹치면 곱해진다.**

```
"이 숫자를 얻기까지 내가 고른 것이 몇 개인가."
하나라도 있으면 그 선택을 고정하고 **새 데이터**에서 다시 재라.
```

→ D-36, D-40, D-46, D-50

## 6. "홀드아웃" 은 하나가 아니다

파이프라인의 **단계마다 학습하는 것이 다르다.**

| 학습하는 것 | 누가 | 그것의 홀드아웃 |
|---|---|---|
| 구조 | Optimizer / Analyst | `splits.val` |
| 가중치 | `fit_weights` | 어떤 분할이든 그 안에서만 |
| 프롬프트·피처 설명 | **사람** | `splits.test` (봉인) |

홀드아웃 19형상 중 **11이 루프의 학습 형상**이었다. 구조는 그것들을 보고
진화했으니 **가중치만 홀드아웃**이었고, 그 값으로 "관문을 넘었다" 고 썼다.

**숫자를 낼 때 "이 홀드아웃은 무엇을 안 봤는가" 를 한 줄로 적어라.**

→ D-36, §10.2b, §12.3d

## 7. 판별력이 하한이다 — 못 재는 차이를 보고하지 마라

```
kernelTab   타이머 눈금이 config 순위를 가린다
kernelRule  시드 분산이 조건 차이를 가린다
```

구조 홀드아웃 표준편차가 **0.0274** 다 (`gpt-5.6-luna` 6시드).

```
차이 0.06   시드 4~5개
차이 0.03   시드 15개
차이 0.02   시드 30개 이상   ← 사실상 불가
```

**지금까지 재려던 것 대부분이 마지막 줄에 있다.** 실험을 더 해서 풀리지
않는다. **차이를 보고하기 전에 폭을 먼저 재라.**

→ D-40, D-53

## 8. 실패는 인프라 → 검사기 → 피험자 순서로 의심하라

**세 번** 겪었고 셋이 로그에서 **똑같이 보였다.**

```
검사기(inspect)   "LLM 이 피처를 못 만든다"     ← 실제로는 우리 버그
검사기(섭동 축)    "같은 제안을 16번 반복한다"    ← 실제로는 우리 버그
인프라(크레딧)     "거부 스키마 144건"          ← 호출이 안 갔다
```

**거부 사유가 한 종류로 몰릴 때** 특히 그렇다. 가장 싼 확인은
**거부된 것 하나를 손으로 읽어 보는 것**이다.

→ D-37, D-38, D-43, D-49

## 9. 문서와 코드가 어긋나면 — 어느 쪽이 틀렸는지 먼저 정하라

세 형태를 다 겪었다.

```
코드가 틀림   consumer_contract §9 가 옳고 구현이 틀렸다
문서가 틀림   설치 안내가 pydantic-ai 를 빠뜨렸다 (우리 환경엔 깔려 있었다)
수단이 없음   "기록하라" 고 적어 놓고 기록 코드가 없었다  ← 가장 조용하다
```

세 번째가 위험하다. **문서가 틀리면 언젠가 누가 따라 하다 걸리는데,
수단이 없으면 아무도 안 하고 아무 일도 안 일어난다.**

그리고 **없는 상태를 실제로 만들어 봐야 확인이다.** 흉내가 정확하지
않으면 검증이 아니다 (`import 하면 예외를 내는 모듈` ≠ 미설치).

→ D-48, D-51

## 10. 사용자가 정한 것을 실험 편의로 바꾸지 마라

모델을 대조용으로 한 번 바꿨는데, 그것이 **결정 없이 기본값으로 승격**됐다.

```
1. "대조로 한 번만" 쓴다        ← 일회성으로 보인다
2. 그 대조가 유익했다
3. 다음 실험도 그것으로 돈다     ← 아무도 결정하지 않았다
4. 열 개 실험 뒤, 기준선이 바뀌어 있다
```

결과: **그 위에 쌓은 결과를 전부 잃었다.** 절차가 틀려서가 아니라
**정하지 않았어야 할 것을 정해서**다.

**대조군은 일회성이어야 한다.** 승격은 물어라.

→ D-52
