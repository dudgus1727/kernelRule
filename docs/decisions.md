## F-1. ✅ 해결 — 정본은 "status 전체 + 합집합 덮개" 다

착수 시 §30.6 의 `정적 top-1 = 1.394` 가 재현되지 않아 보고했고, 설계 문서가
§30.5 / §30.5b / §30.6b 로 갱신됐다. **정본 절차가 확정됐다.**

`baselines/static_topk.py` 가 세 절차를 전부 계산한다. 실측 (a888 61형상):

| 절차 | 후보 config | k=1 | k=3 | k=8 | 덮개 |
|---|---:|---:|---:|---:|---:|
| `ok` 만 + 개별 전덮개 | **3/17,325** | 1.394 | 1.383 | 1.383 | 100% |
| `ok` 만 + 합집합 덮개 | 17,325 | 1.194 | 1.046 | 1.007 | 98.4%(k=1) |
| **전체 + 합집합 (정본)** | 17,325 | **1.115** | **1.031** | **1.006** | 100% |

문서의 정본 값(1.115 / 1.021 / 1.164 / 1.031 / 1.006)을 **셀 단위로 재현**했고
`test_baselines.py` 가 회귀로 고정한다. 옛 값 1.394 도 그 원인(후보 3개)과
함께 고정해 두었다 — 그래야 나중에 같은 숫자를 다시 정본으로 착각하지 않는다.

> `ok` 만 + 합집합의 k=1 이 문서는 1.394, 우리는 1.194 다. 그 조합에서는
> 61형상을 전부 덮는 단일 config 가 없어서(덮개 98.4%) 값이 절차 정의에
> 민감하다. 정본이 아니므로 덮개율과 함께 병기만 한다.

## F-2. 형상별 "최적 config" 는 tie-break 의 함수다

66형상 중 **29개가 최적시간에 정확한 동점**이고 최대 **84중 동점**이다
(타이머 양자화). 그래서 축별 최적 분포가 절차마다 달라진다.

| 절차 | `ext_warp_m` | `ext_stages` |
|---|---|---|
| `idxmin` (표 행 순서), ok+high_outlier | `{64:48, 32:10, 16:8}` | `{3:54, 4:4, 5:3, 6:3, 2:2}` |
| 결정론 tie-break `(kernel_id, split_k)`, ok only | `{64:44, 32:12, 16:10}` | `{3:52, 5:5, 4:3, 7:2, 6:2, 2:2}` |

버킷당 최대 4형상이 이동한다. `ext_stages=7` 은 한쪽에서 0회, 다른 쪽에서 2회다.

**결정:** `PerfTable` 은 `best_config` 를 **제공하지 않는다**. 정의 가능한
것은 `best_time`(스칼라, tie-break 무관)과 `answer_mask`(집합)뿐이다.
축별 분포를 리포트에 넣을 때는 "tie-break 의존 관측" 이라고 표시한다.

`§18.3` 의 결론들은 이 영향을 받지 않는다: `warp_m=128` 최적 0회,
`split_k_mode` 66/66 serial, 3의 배수 split-K 34.8% vs 축 비율 37.5%(농축 없음)
— 전부 재현됐고 tie-break 에 무관하다.

## D-1. `status` 정책 — `high_outlier_frac` 를 포함한다

`§7.1` 은 `status != "ok"` 를 후보에서 제외하라고 했으나, 착수 지시가
"`high_outlier_frac` 도 유효한 측정" 이라고 명시했고 §2 의 확인된 사실도
그 정책에서 재현된다.

**`PerfTable.from_bundle(ok_only=False)` 가 기본이다.** 값은 `meta["ok_only"]`
에 기록되며 `RunConfig` 로 넘어간다. 관문 리포트는 F-1 때문에 **양쪽을 다 낸다.**

## D-2. 노이즈 계수는 번들에서 읽고 **불일치를 에러로** 만든다

kernelTab 에 노이즈 진입점이 둘이고 성격이 다르다.

```
kerneltab.core.noise.noise_floor(t)   모듈 전역 상수 (A6000 값이 박혀 있다)
Bundle.noise_floor                    번들 계수 + tick 부재 시 경고
```

그리고 **`kerneltab.core.table.answer_set()` 은 전자를 호출한다.** 지금은
개발용 번들이 A6000 이라 값이 같아 문제가 없지만, 4090/H100 번들에서는
`answer_set()` 이 A6000 눈금을 **경고 없이** 쓴다 (`Bundle.tick_ms` 를 안
거치므로 그 경고도 안 난다). §30.8 이 말한 "조용히 아무것도 안 하는 안전장치" 다.

kernelTab 은 수정하지 않는다(범위 밖). 대신 `kernelrule.core.noise.NoiseModel`:

- 계수를 **번들에서만** 읽는다
- 모듈 전역 상수와 대조하고 **다르면 `NoiseMismatchError`**
- `tick_ms` 부재를 `tick_is_fallback` 로 기록하고 경고를 다시 낸다
- 정답 집합은 `PerfTable.answer_mask()` 로 계산한다 (`answer_set()` 대신)
- 계산 불가 시 **1.0**(=100%, 아무것도 구분 못 함)을 낸다. 0 이 아니다

개발용 번들 실측: `schema_version 1`, `tick_ms` 없음 → A6000 관측치
0.001024ms 로 대체 + 경고. `BUNDLE.json` 의 모델 문자열도 구버전
(`sigma_rel(t) = sigma_abs_ms/t + sigma_rel`, `max()` 없음).

## D-3. 채점 인터페이스 — 시간이 닿을 수 없는 자료구조

```
order_fn(p: Problem, cand: CandidateSet) -> 순열        임의의 랭커 (벤더/GBDT)
score_of(p: Problem, cand: CandidateSet) -> 점수 배열    규칙 (빠른 경로)
```

`CandidateSet` 에 시간 필드가 **없다**. `sorted(..., key=(score, time))` 이나
`idxmin()` 을 쓰려면 없는 속성이 필요하므로 `AttributeError` 다 (§30.7).
시간은 `evaluate` / `evaluate_scores` 안에서 **순서가 정해진 뒤** 인덱싱에만
쓰이고, `times_of()` 가 돌려주는 배열은 읽기 전용이다.

동점은 `(kernel_id, split_k, split_k_mode)` 의 사전순 정수 순위로만 갈린다.
이 순위는 `np.unique(return_inverse=True)`(사전순)로 만들며 **표의 행 순서에
의존하지 않는다** — `pd.factorize` 는 등장순이라 쓰면 안 된다.

## D-4. 채점 비용 — 부록의 수정으로도 부족했다

부록 ★수정 1 은 피처 행렬 사전 계산으로 "라운드당 0.4초" 를 예상했다.
실측은 달랐고, 두 곳을 더 고쳐야 전제가 성립했다.

| | 처음 | 고친 뒤 |
|---|---:|---:|
| `PerfTable.from_bundle` (980,915행) | 1.7s / 3.7GB | 1.5s / 2.1GB |
| `FeatureMatrix` 25피처 벡터화 | 1.9s / 196MB | 1.9s / 196MB |
| 채점 1회 (66형상 x 15,015후보) | **2.70s** | **0.010s** |
| 가중치 적합 200 evals | **14.5s** | **1.28s** |
| → 라운드당 12규칙 적합 | 174s | **15.4s** |

두 원인:

1. **`make_tiebreak` 가 15,000개 튜플을 파이썬 `sorted` 로 정렬**했다.
   `np.unique` + `np.lexsort` 로 벡터화.
2. **상위 k개만 필요한데 매번 전체를 정렬**했다. `CandidateSet.top_k` 를
   추가 — `np.partition` 으로 k번째 점수를 찾고 그 이하만 정렬한다.
   전체 정렬과 **결과가 정확히 같다**(테스트로 고정). 동점은 여전히
   tie-break 로만 갈린다.

메모리는 형상 그룹핑을 `groupby(...).indices` 로 벡터화하고, 표 전체에서
값이 하나인 메타 컬럼(`bundle_id`, `cutlass_commit` 등)을 `meta` 로 옮기고,
반복 문자열을 category 로 바꿔 3.7GB → 2.1GB 로 줄였다. **로드 순간 피크는
3.8GB** 로 남는다 (kernelTab `Bundle.ranking()` 의 `df.copy()`).

## D-5. 가중치 적합에 **재시작이 필요하다**

`§29.2` 대로 regret 은 `argmin` 을 거쳐 계단 함수이고, 단순 Nelder-Mead 는
평평한 지대에서 심플렉스가 수축해 **초기값에서 한 발도 못 움직이는 경우가
실제로 나왔다** (regret 7.19 에서 그대로 정지).

`fit_weights(n_restarts=4)` 가 기본이다. 재시작마다 심플렉스를 다시 부풀리고
(`0.6 * 0.5**r`), 2회차부터는 현재 최적 주변의 무작위 출발점을 쓴다.
시드가 고정(`_RESTART_SEED`)이라 **결정론적**이다.

`FitError` / 기각 경계 (§26.4):
- 어떤 가중치에서 점수가 비유한 값 → 그 **점(point)만** 실행 불가 (구조 기각 아님)
- **모든** 평가에서 실패 → 구조 기각
- `Split.role != "train"` → `SplitError`. 형상 리스트를 그냥 넘겨도 에러

## D-6. 합성 생성기 (§22)

**격자는 실제 번들에서 가져오되 `load_for_ranking` 만 쓴다.** 생성기가
실측 시간을 볼 수 있는 경로가 없다(테스트로 고정). 실제 alignment 구조와
커널 정적 속성이 공짜로 따라온다. 번들이 없을 때를 위한 열거 경로
(`Grid.enumerate`, kernelTab `shapes.py` + `backends/sm80.py`)도 있으며,
그 경우 빌드 속성은 해석적 모델이고 그 사실이 `BUNDLE.json` 에 남는다.

`features/` 를 import 하지 않는다(§28, AST 로 검사). 물리는 같되 구현이 다르다 —
wave 항을 피처 쪽은 `tail_waste`, 생성기 쪽은 `ceil(w)/w` 로 쓴다.

### 벌점은 roofline 의 **연산 쪽에만** 곱한다

부록 §22.2 스켈레톤은 `t_sol = max(compute, memory)` 를 만든 뒤 벌점을 곱한다.
그렇게 하면 **형상 x config 상호작용이 거의 사라진다** — 실측했더니 고정
config 하나가 모든 형상에서 최적에 가까워 정적 top-1 이 1.03 까지 내려갔고,
그런 표에서는 규칙이 배울 것이 없다.

```
t_compute *= (config 벌점 전부)     # 연산량과 연산 효율
t_memory  *= (거의 config 무관)      # 대역폭은 타일 모양을 모른다
t = max(...) + 런치
```

이러면 §22.2 의 구조 #4(메모리 바운드에서 config 영향이 약함)가 **부과되는
대신 자연히 나온다.**

### 심은 구조

```
#1 wave quantization    #2 smem 압력      #3 스필         #4 (자연 발생)
#5 split-K 리덕션        #6 stages 워밍업   #7 타일/warp 연산 강도(포화 있음)
#8 2단 파이프라인        #9 명령어 수       #10 레지스터 압력
#11 ★ 부분 타일 낭비 — M=1 에 128행 타일이면 일의 99.2% 가 버려진다
```

`#11` 이 형상 x config 상호작용의 주 동인이고, `#7` 이 난이도의 주 동인이다.
`#7` 에 **포화**를 둔 이유: 안 두면 256x256 이 공짜 이득을 받아 스필 벌점을
상쇄해 버리는데, 실측에서 256x256 의 `rel` 중앙값은 17.9 로 가장 나쁘다.

### 보정 결과 (`normal`, 실측 대비)

| 지표 | 실측 | 합성 |
|---|---:|---:|
| 난이도 중앙 | 1.670 | 1.597 |
| p90/best 중앙 | 2.811 | 2.355 |
| max/best 중앙 | 24.68 | 23.18 |
| 정적 top-1 (`ok_only=False`) | 1.115 | 1.208 |
| 정적 top-3 / top-5 / top-8 | 1.040 / 1.033 / 1.028 | 1.037 / 1.030 / 1.028 |
| `distinct_time_frac` 중앙 | 0.200 | **0.102** |

`distinct_time_frac` 이 실측의 절반이다 — 합성 커널들이 실제보다 서로 덜
다르다. 눈금 충돌이 실제보다 심하다는 뜻이므로 **보수적인 방향**이지만,
분해능 관련 결론을 합성 표로만 내리면 안 된다. 남은 불일치로 기록한다.

실측의 긴 꼬리는 **전적으로 스필**이다: 전체 행의 7.4% 가 스필이고 그들의
`rel` 중앙값이 13.6(최대 37.2), 비스필은 중앙 1.54 / p90 2.58 / 최대 8.6.

### 프리셋

`easy > normal > hard > null` 순으로 난이도가 낮아진다(테스트로 고정).
`null` 은 `struct=0` 이라 벌점이 **정확히 1** 이고 시간이 config 와 무관하다.
양자화는 `null` 에도 적용한다 — 동점이 대량 발생할 때 tie-break 가 정답을
보는지 시험하기 위해서다.

산출물은 `SYNTHETIC` 이 `bundle_id`, 디렉토리명, `env_hash` 접두어(`5y47he71c`)에
박히고, `BUNDLE.json` 에 "성능 수치를 보고하지 마라" 경고가 들어간다.
`schema_version 2` 로 내보내므로 `tick_ms` 가 실려 있다.

# 2단계 (D, F, G, H, I, J) — 결정과 발견

## F-3. ★ 크기 전이 실패 — GBDT 의 1.011 은 짧은 형상을 안 본다

§30.5 의 새 발견(크기 층화가 난이도 층화보다 5배 더 갈린다)을 베이스라인에
적용하니 **관문의 해석이 달라진다.**

`M > 2048` 블록 분할의 홀드아웃 11형상은 **전부 t_best >= 0.5ms 다.**
즉 널리 인용되는 GBDT 1.011 은 **여지가 가장 적은 체제**에서만 측정됐다
(그 구간의 정적 top-1 이 1.021 이다).

같은 GBDT 를 크기로 갈라 다시 재면:

| 학습 | 시험 | regret@1 |
|---|---|---:|
| 긴 20형상 | 짧은 41형상 | **1.1181** |
| 짧은 20형상 | 짧은 21형상 (표본 수 통제) | **1.0458** |
| 짧은 형상 5-fold (~33형상 학습) | 짧은 41형상 | 1.0293 |

**학습 표본 수를 20으로 맞춰도 1.118 vs 1.046 이다.** 표본 부족이 아니라
**체제 전이 실패**다. 그리고 1.118 은 같은 형상에서의 벤더(1.098)보다 나쁘다.

함의:

- "GBDT 가 벤더가 남긴 8.8% 중 78% 를 회수한다" 는 **긴 형상에서만** 보인
  것이다. 짧은 형상에서는 학습 모델이 벤더를 이긴다는 증거가 아직 없다.
- 여지의 87% 가 짧은 형상에 있으므로(1.164 vs 1.021), 상한을 재려면
  **크기 홀드아웃**으로 재야 한다. `M>2048` 은 그 질문에 답하지 못한다.
- `splits.py` 에 `split_by_size` 를 넣고 모든 베이스라인 리포트에 병기한다.
  경계는 **`best_ms`(정답)가 아니라 roofline 하한**으로 잡는다 — 그런데도
  실측 짧은 형상 45개를 전부 포함한다 (테스트로 고정).

## F-4. 벤더 베이스라인 재계산 — 매핑 성공률이 78.5% -> 92.9%

kernelTab 의 `scripts/baseline_*.py` **세 개 전부** `status == "ok"` 를 쓴다
(`gbdt.py:62`, `rule.py:47`, `vendor.py:143`). 정본으로 다시 계산했다.

| | 원 값 (`ok` 만) | 정본 재계산 |
|---|---:|---:|
| 벤더 (nearest) | 1.088 | **1.080** |
| 벤더 (strict) | 1.081 | 1.102 |
| 엄격 매핑 성공률 | 79% | **92.9%** |
| GBDT (블록 M>2048) | 1.011 | **1.010** |
| 손규칙 | 1.192 | **1.172** (우리 구현) |

`ok` 만 남기면 벤더가 고른 config 가 표에서 사라져 최근접 대체가 늘어난다.
`pending_fixes.md` 의 C-2 에서 예측한 그대로다 (79% -> 92.9%).

**매핑 방식이 결론을 바꾼다.** kernelTab 은 strict/nearest 가 1.081/1.088 로
일치한다고 봤으나, 정본에서는 1.102/1.080 으로 0.022 벌어진다. 둘 다 병기한다.

`vendor.json` 을 `datasets/baselines/` 에 저장했다. 이후 재채점은 표만으로

## D-7. 손규칙 — 두 번의 물리 오류를 고쳤다

**상수를 튜닝한 것이 아니라 모델이 틀린 것을 고쳤다.**

| regret@1 | 무엇이 틀렸나 |
|---:|---|
| 1.758 | `traffic_amplification` 을 **선형**으로 씀 -> 트래픽이 최소인 256x256 을 고르는데 그건 **스필한다** (실측 rel 중앙 17.9). 로그로 바꿔 포화시켰다 |
| — | `if p.is_memory_bound: s = s * w[2]` -> **순위가 하나도 안 바뀐다** (아래) |
| **1.172** | 로그 트래픽 + 워밍업 항 + 메모리바운드에서 트래픽 재가중 |

### ★ 형상 수준 분기는 config 수준 항을 **재가중해야** 의미가 있다

점수 전체에 형상 수준 스칼라를 곱하거나 더하는 것은 그 형상 안의 순위를
바꾸지 못한다 (단조 변환이고, 규칙은 형상마다 독립적으로 정렬된다).

    if p.is_memory_bound:
        s = s * w[2]                             # ⛔ no-op
        s = s + f.traffic_amplification * w[6]   # ✅ 트래픽 항의 가중치가 바뀐다

**정적 검사로는 못 잡는다** (문법적으로 합법이다). 채점기는 볼 수 있으므로
§12 진단 리포트에 "형상 수준 분기가 순위를 바꾸는가" 항목을 넣는다.

블록 분할(M>2048)에서 train 1.185 / val 1.178, **격차 -0.007** — 과적합 없음.
크기 분할에서는 train(긴) 1.114 -> holdout(짧은) 1.229 로 **+0.115** 벌어진다.
GBDT 와 같은 방향의 전이 실패다.

## D-8. 피처 라이브러리 — 25개, 자동 검증 통과

config 수준 19 + 형상 수준 6. `features/validate.py` 가 7가지를 본다.

**단독 AUC 가 방향 오류를 잡았다.** `tail_waste` 의 단독 AUC 가 **0.176** 이다 —
선언한 방향("클수록 나쁨")과 **반대**로 예측한다. 타일이 작을수록 타일 수가
많아 wave 가 커지고 `tail_waste` 가 0 에 가까워지므로, 그것만 최소화하면
작은 타일을 고른다. kernelTab 손규칙이 그 이유로 1.776(정적 top-1 보다 나쁨)
에서 시작했다 — **독립적으로 재현됐다.** 기각하지 않고 경고만 낸다: 교락
변수(트래픽 항)와 함께 있어야 의미가 산다.

### 중복 판정에 스피어만만 쓰면 안 된다

`sm_idle_cost = 1/(1-tail_waste) - 1` 은 `tail_waste` 의 **단조 변환**이라
스피어만이 0.999 다. 그런데 규칙은 **선형 가중합**이라 둘의 효과가 전혀
다르다 — 512³ 에서 선형 항으로는 못 내는 5.3배 벌점을 비선형 항이 낸다.
**스피어만과 피어슨이 둘 다 높을 때만** 폐기 후보로 본다.

### `ext` 를 안 쓰고 파이프라인 깊이를 얻는다

`pipeline_warmup_frac` 이 `cfg.ext["stages"]` 대신 **smem 에서 역산**한다
(`smem / (tile_k*(tile_m+tile_n)*elem)`). 실측에서 `ext_stages` 와
**98.3% 정확 일치, r=0.994** 다. 아키텍처 공통 필드만 쓰므로 전이가 된다.

## D-9. 정적 검사 — 18개 adversarial 케이스 전부 차단

`w[0]` 의 `0` 을 리터럴로 세지 않는다 (가중치는 `n_weights` 로 이미 예산에
들어간다). 안 빼면 항 하나마다 두 번 세어 예산이 반토막 난다.

## D-10. 샌드박스에서 밟은 두 버그

## F-5. ★ 집계 방식을 짝맞추지 않으면 결론이 뒤집힌다

GBDT 상한을 "최악 1.085" 로 적으려 했다. 그러면 이렇게 된다.

```
GBDT 최악  1.085   <- 8개 분할 중 최악
벤더 관문  1.080   <- 분할 없는 전체값
```

"GBDT 가 벤더보다 나쁘다 = 여지가 없다" 로 읽힌다. **짝을 맞추면 정반대다.**

```
기하평균   GBDT 1.044  vs  벤더 1.101     격차 0.057
최악      GBDT 1.085  vs  벤더 1.118     격차 0.033
```

이 프로젝트에서 **세 번째** 형태다 — §30.5b(다른 절차), §30.8b(다른 분모),
그리고 이것(다른 집계 방식). `baselines/` 리포트가 **분할 x 방법 표를 기본
출력**으로 내게 했다. 스칼라 하나로 요약하지 않는다.

# 3단계 (K, L, M) — 결정과 발견

## D-13. ★ 리포트가 자기 데이터와 모순되면 안 된다 — 코드로 강제

§30.5 가 "크기 층화가 난이도 층화보다 5배 더 갈린다" 를 확립했고, 그것을
진단 리포트 블록 3 템플릿에 **문장으로 박아 뒀다.** 그런데 학습 분할
(M<=2048)에는 긴 형상이 9개뿐이라 **그 분할의 실제 숫자는 반대였다.**

```
크기 격차   0.0007      <- 템플릿이 "크게 갈린다" 고 주장한 축
난이도 격차 0.1651      <- 실제로 갈린 축
```

**전역에서 참인 관측이 부분집합에서 거짓이 될 수 있다.** 리포트가 자기
데이터와 모순되면 그것을 읽는 쪽(LLM 이든 사람이든)은 데이터가 아니라
문장을 믿는다.

§30.8 의 **네 번째 뿌리**로 넣었다.

```
두 숫자를 나란히 쓰거나 비교를 서술하기 전에 넷을 확인한다.
  (1) 같은 절차인가  (2) 같은 분모인가  (3) 같은 집계 방식인가
  (4) ★ 그 서술이 **이 데이터에서 계산된 것**인가
```

`tests/test_diagnostic.py` 가 두 겹으로 강제한다.

1. **정적** — 렌더되는 문자열 리터럴에 비교어가 있으면 그 문자열은
   **계산된 값(f-string 의 `FormattedValue`)을 포함해야 한다.**
   원래 버그를 되살려 테스트가 실제로 잡는지 확인했다.
2. **행동** — 반대 데이터로 두 리포트를 만들어 **격차 부호가 뒤집히는지**
   본다. 정적 검사만으로는 계산된 f-string 안에 결론을 박는 것을 못 잡는다.

예외는 하드웨어 사실 블록뿐이다 — 물리 상수이지 이 분할의 관측이 아니다.

## D-14. 진단 리포트의 두 열

**(1) "규칙에서 사용 중"** — AST 로 `f.<이름>` 을 뽑아 표시한다.
"항이 없다"(추가)와 "항은 있는데 가중치가 틀렸다"(조정)는 다른 수정이다.
이 열이 손규칙의 두 결함(`is_two_stage`, `log_workspace_bytes` 미사용)을
한눈에 드러냈다.

**(2) 격차를 노이즈 바닥 단위로** — `(t_선택 - t_최적) / (t_최적 x floor)`.
한 숫자가 눈금 동점과 일반적인 해상도를 다 해결한다. 주변 config 목록에도
같은 단위를 쓰면 "전부 (최적)" 으로 표시되어 순위가 없다는 것이 보인다.
**사례 선정에는 쓰지 않는다** — 짧은 형상은 σ 가 작게 나오기 쉬운데 여지가
몰려 있는 곳이 거기다.

**(3) `regret` 과 `hit@1` 을 나란히** — 손규칙이 regret 1.19 / hit 0.000
이었다. 정답 집합이 노이즈 기반이라 짧은 형상에서는 수백 개가 들어가는데도
한 번도 못 들어간다. **가중치 조정이 아니라 항이 필요하다는 신호다.**

## D-15. ★ `mutate` 목은 가중치가 아니라 **구조**를 섭동한다

§24.2 는 "부모 규칙의 가중치를 무작위 섭동" 이라고 했다. **그러면 아무것도
시험하지 못한다** — 가중치는 `fit_weights` 가 맞추므로(§29.3) 초기값
섭동은 채점 결과에 거의 영향이 없다. 수렴 곡선이 평평하게 나오고, 그것이
루프가 잘 도는 것인지 목이 아무것도 안 하는 것인지 구분할 수 없다.

항을 넣고/빼고/바꾸고, 형상 수준 분기를 붙였다 뗀다. 그래야 "파이프라인이
빠진 항을 찾아내는가" 를 시험할 수 있다.

## D-16. 샌드박스가 `__main__` 가드를 요구한다

`forkserver` 도 `spawn` 도 **자식이 `__main__` 을 다시 import 한다.**
호출 스크립트에 `if __name__ == "__main__":` 가 없으면 무한 재귀이고,
파이썬은 그것을 `BrokenPipeError` 로 보여준다 — 원인이 전혀 안 보인다.
`fork` 는 그 문제가 없지만 부모 상태를 물려받아 격리가 아니다.

`run_isolated` 가 첫 호출에 preflight 를 돌려 **무엇을 고쳐야 하는지 말하는
에러**로 바꾼다. 샌드박스를 끄는 것은 답이 아니다.

## D-17. 아카이브 갱신에 노이즈 허용치

"조금 좋아졌다" 로 갱신하면 아카이브가 노이즈를 축적한다. 셀 축은
`code_len`(AST 노드) x `mem_regret` x `comp_regret` = 64 셀이다.

## F-8. ★ MockLLM 20라운드 — 루프는 도는데 **검증에서 무너진다**

손규칙을 씨앗으로 넣고 20라운드 (a888 61형상, 학습 M<=2048 50형상 /
검증 M>2048 11형상):

```
초기(손규칙)  train 1.2007  val 1.0824
20라운드 후   train 1.1176  val 3.7463   ← ★ 검증 격차 +2.63
160초 (8.0s/라운드), 셀 14/64, 제안 240개 중 137개 채점, 34개 채택
호출: diagnose 20 / optimize 240  (optimizer 92%)
```

**아카이브 엘리트 14개 중 9개가 검증 격차 > 0.5 다.** 그리고 이것은
과적합이 **아니다** — 항이 3개뿐인 규칙도 격차 +4.99 를 낸다. 50형상에
3개 파라미터로는 과적합이 불가능하다.

**체제 전이 실패다.** 학습(M<=2048)에서 좋은 규칙이 검증(M>2048)에서
무너진다. F-3 의 GBDT 긴->짧 실패와 **같은 현상의 반대 방향**이고,
§30.6c 의 질문 3 이 루프 안에서 재현된 것이다.

### 이것을 어떻게 다룰지가 열린 결정이다

`§13.4` 는 아카이브를 **전체 점수**(= 학습)로 갱신하라고 했고, `§10.2` 는
검증을 조기 종료와 사람 눈에만 쓰라고 했다. 둘 다 지키면 **검증에서
무너지는 규칙이 "최고" 가 된다.** 실제로 그렇게 됐다.

검증으로 선택하면 홀드아웃이 오염된다. 그래서 선택 규칙은 그대로 두고
**경보를 냈다** — `RoundResult.val_gap` / `n_val_blowups` 가 매 라운드
찍힌다. 하지만 이것은 진단이지 해결이 아니다.

가능한 방향(미결):
```
(a) 학습 분할을 체제별로 층화해 두 체제를 다 담게 한다
(b) 셀 축에 "체제 전이 격차" 를 넣어 전이되는 규칙을 별도 셀에 보존한다
(c) 그대로 두고 "규칙은 체제마다 따로" 를 결론으로 받아들인다
```
(c) 는 §30.6c 질문 3 의 답이 그렇다면 정직한 선택이다.

### ①②③ 을 찾았는가 — 1/3, 그런데 해석이 다르다

```
① is_two_stage         찾음. 최종 규칙에 있다
② log_workspace_bytes  ★ **네 번 시도했고 네 번 다 데이터가 거부했다**
③ split_k_cost         씨앗에 있었으나 채택된 변이가 떨어뜨렸다
```

②가 중요하다. `failures.jsonl` 을 보면 r4(2회), r9, r10, r16 에서
`log_workspace_bytes` 를 넣었고 **전부 학습 regret 이 나빠졌다.**

```
r4   1.1289 -> 1.4942   log_grid_tiles -> log_workspace_bytes 교체
r4   1.1289 -> 1.1305   if p.can_use_cp_async -> log_workspace_bytes 재가중
r9   1.1203 -> 1.1235   if p.is_memory_bound -> log_workspace_bytes 재가중
r10  1.1203 -> 1.3674   (같은 형태)
r16  1.1176 -> 1.2199   log_workspace_bytes 항 추가
```

**파이프라인이 못 찾은 것이 아니라 탐색하고 기각했다.** 내가 리포트에서
읽은 ②는 **손규칙의 실패 모드**였고, 규칙이 바뀌자 그 실패 모드가
사라져서 그 항이 더는 설명력을 갖지 않았다.

이것이 §14.4 의 "한 문제를 고쳐야 다음 문제가 보인다" 의 반대 형태다 —
**한 문제를 고치면 이전 진단이 무효가 된다.** 사람이 리포트 하나를 보고
읽은 수정 목록을 루프의 정답으로 삼으면 안 된다는 뜻이기도 하다.

### 정적 검사가 20라운드 동안 0건 거부했다

`mutate` 목이 구조적으로 유효한 규칙만 내기 때문이다. 방어는
`adversarial` 모드 테스트가 담당한다 — 12케이스 제안, **채점 0건**.
그 사실을 `test_loop.py::test_adversarial_mode_scores_nothing` 이 고정한다.

### 씨앗 없이 돌리면 다른 실험이 된다

처음 20라운드를 씨앗 없이 돌려서 루프가 `f.traffic_amplification` 하나에서
출발했다. **내가 읽은 것과 다른 리포트를 보고 있었다.** `RoundLoop.seed()`
를 추가하고 다시 돌렸다. 실험 설계 오류였다.

## F-9. ★ F-8 의 검증 폭발은 **학습 분할의 체제 불균형** 때문이다

(a)/(b)/(c) 중 어디로 갈지 정하기 전에, "(a) 가 듣는가" 만 측정했다.
같은 루프/시드/예산(12라운드)으로 **분할만** 바꿨다.

| | train | val | 씨앗 격차 | 12R 후 격차 | 아카이브 폭발 |
|---|---|---|---:|---:|---:|
| **A** 체제 분리 (M>2048) | 41짧+9긴 | 0짧+11긴 | −0.118 | **+2.629** | 9/13 |
| **B** 체제 교차 ((N,K)=11008x4096) | 35짧+16긴 | 6짧+4긴 | +0.028 | **+0.009** | 1/9 |

격차가 **+2.63 -> +0.009 로 무너진다.**

### 그런데 B 는 검증이 학습과 닮아 쉬워진 것일 수도 있다 — 교차 채점

두 규칙을 **같은 시험대**(A 의 검증 = 긴 형상 11개)에서 다시 쟀다.

| 규칙 | 긴 11 | 짧은 41 | **전체 61** |
|---|---:|---:|---:|
| 손규칙 (전체 적합) | 1.0824 | 1.2001 | **1.1772** |
| A 에서 진화 | **3.7463** | 1.1109 | **1.3900** |
| B 에서 진화 | **1.0958** | 1.1471 | **1.1430** |

**B 는 문제를 가린 것이 아니다.** A 의 규칙이 3.75 를 내는 바로 그 11형상에서
B 의 규칙은 1.096 이다.

그리고 **A 의 진화는 전체 61형상 기준으로 손규칙보다 나쁜 규칙을 만들었다**
(1.3900 vs 1.1772). 학습 점수만 보면 개선처럼 보였다 (1.2007 -> 1.1176).

### 기전 — 검증이 학습을 닮아서가 아니라 **학습이 균형 잡혀서**다

```
A 학습:  짧은 41 / 긴 9  (82% 짧음)  -> 긴 9개를 희생해 짧은 41개에서 벌면 이득
B 학습:  짧은 35 / 긴 16 (69% 짧음)  -> 같은 거래가 수지가 안 맞는다
```

**진화는 학습 분할의 체제 구성이 허용하는 거래를 한다.** 소수 체제를
희생하는 것이 학습 점수에 유리하면 그렇게 한다. 홀드아웃이 그 소수 체제와
정확히 겹치면 격차가 폭발하고, 겹치지 않으면 **폭발이 안 보일 뿐 규칙은
여전히 그 체제에서 나쁘다.**

### 결론과 남은 결정

**(a) 가 듣는다.** 다만 "층화" 의 의미가 "검증을 학습과 닮게" 가 아니라
**"학습이 두 체제를 충분히 담게"** 다. 후자가 원인이다.

여전히 열려 있는 것:
```
어느 비율이 충분한가         B 의 69/31 은 되고 A 의 82/18 은 안 됐다.
                            경계가 어디인지는 모른다
(b) 셀 축에 전이 격차 추가   균형을 맞춰도 일부 규칙은 여전히 폭발한다 (1/9)
전이 실험(§29.5)과의 관계    아키텍처 전이도 같은 구조일 가능성이 높다 —
                            학습에 없는 체제로 옮기는 것이다
```

**측정 결과일 뿐 설계 변경은 하지 않았다.** 방향은 사람이 정한다.

## F-10. ★ 경계 탐색 — 균형은 **꼬리를 줄이지 중앙을 못 올린다**

학습 총 개수를 **24로 고정**하고 긴 형상 비율만 바꿨다. 시드 3개.
고정 시험대(긴 12 / 짧은 12)는 학습에 안 쓰인다.

| 긴 비율 | 시드별 (긴 12) | 중앙 | **최악** | 짧은 12 |
|---:|---|---:|---:|---:|
| 8% | 6.57 / 16.33 / 1.19 | 6.57 | **16.33** | 1.107 |
| 17% | 1.17 / 1.08 / 10.41 | 1.17 | **10.41** | 1.095 |
| 25% | 1.09 / 1.20 / 2.19 | 1.20 | **2.19** | 1.158 |
| 33% | 1.08 / 1.22 / 1.79 | 1.22 | **1.79** | 1.147 |
| 손규칙 (참고) | — | 1.084 | — | 1.221 |

**1. 최악이 단조 감소한다** (16.33 -> 10.41 -> 2.19 -> 1.79). 중앙값은
17% 이후 평평하다.

**2. 한 궤적으로는 측정할 수 없다.** 17% 조건의 세 시드가
1.08 / 1.17 / **10.41** 이다. 같은 조건에서 어떤 궤적은 멀쩡하고 어떤
궤적은 무너진다. F-9 에서 "82% 는 3.75, 69% 는 1.10" 이라고 쓴 것은
**궤적 하나씩만 본 것이었다** — 방향은 맞았지만 근거가 약했다.

**3. 소수 체제를 희생해도 다수 체제에서 별로 못 번다.** 짧은 형상 점수가
전 조건에서 1.095~1.158 로 평평하다. 진화가 하는 거래는 절대적으로 나쁘고,
다만 짧은 형상이 지배하는 학습 점수에서 좋아 보일 뿐이다.

**25% 는 하한이지 안전선이 아니다.** 분할을 바꾸는 실험은 시드 3개 이상으로
돌리고 최악값을 함께 보고한다.

## F-11. 체제 전이 대리 실험 (a)/(b)/(c) — **차이가 작다**

```
학습        짧은 형상 35개 (긴 형상 0개)
재적합 표본  긴 형상 8개 (블록, 시험대와 겹치지 않음)
시험대      긴 형상 12개 — 학습에도 재적합에도 안 쓰임
```

| | 긴 시험대 | 비용 |
|---|---:|---:|
| 손규칙 (짧은 형상 적합) | 1.0844 | — |
| (a) 구조+가중치 그대로 | 1.0959 | 0s |
| **(b) 구조 고정 + w 재적합** | **1.0838** | **0.2s** |
| (c) 표본으로 처음부터 학습 | 1.0866 | 20.7s |

```
(b) - (c) = -0.0028      (b) 가 근소하게 낫고 131배 싸다
(a) - (b) = +0.0120      가중치 재적합에 이득이 있다
```

### ⚠️ 과대해석 금지

**네 값이 전부 1.5% 안에 있다.** 긴 형상의 노이즈 바닥이 0.05~0.2% 이므로
(b)-(c) = 0.28% 는 유의성 경계다. 그리고 **조건마다 궤적이 하나뿐이다** —
F-10 이 보여주듯 같은 조건에서 시드에 따라 1.08 과 10.41 이 다 나온다.

```
지금 말할 수 있는 것:  (b) 가 (c) 보다 나쁘지 않고 131배 싸다
아직 말할 수 없는 것:  (b) 가 유의하게 낫다
필요한 것:            시드 여러 개 + 실제 LLM (이건 MockLLM 이다)
```

**그리고 이 대리 실험의 어느 조건도 손규칙(1.0844)을 의미 있게 못 이겼다.**
MockLLM 의 진화가 긴 형상에서 손규칙보다 나은 규칙을 못 만든다는 뜻이고,
이 숫자들은 "루프가 얼마나 잘하는가" 가 아니라 **"불균형이 얼마나 해로운가"**
를 잰 것으로 읽어야 한다.

## D-19. 셀 축 교체 — 크기 체제로 (§27 재측정)

`mem_regret`/`comp_regret` -> `short_regret`/`long_regret`.
크기 층화가 난이도 층화보다 5배 더 갈린다는 §30.5 결과와 일관된다.
`Elite.regime_gap` 을 노출해 전이 신호를 볼 수 있게 했다.

**균형 분할로 20라운드 재측정: 셀 11/64** (구 축은 14/64). §27 의 10~50
안이지만 낮은 쪽이다. 축별 점유:

```
code_len   [1, 2]      <- 4구간 중 2개만. 0 과 3 은 비어 있다
short      [1, 2, 3]   <- 구간 0 (regret < 1.05) 은 도달 못 함
long       [1, 2, 3]
```

즉 **실효 공간이 2 x 3 x 3 = 18 이고 그중 11 을 채웠다.** 점유율로는 나쁘지 않다.

⚠️ **경계를 지금 조정하지 않는다.** `code_len` 이 좁은 것은 **MockLLM 이
고정 템플릿으로 규칙을 만들기 때문**이다 (항 개수가 노드 수를 거의 결정한다).
실제 LLM 은 훨씬 넓게 퍼질 것이므로, 목의 인공물에 맞춰 경계를 튜닝하면
안 된다. **실제 LLM 20라운드 후 다시 잰다.**

그리고 균형 분할에서 **20라운드 내내 검증 폭발 0건**이었다 (불균형 분할은
9/13). 셀 축 교체와 무관하게 §10.1 의 효과다.

## D-20. §14.4 — 한 문제를 고치면 **이전 진단이 무효가 된다**

진단은 그 시점 규칙의 실패 모드이지 데이터의 절대적 성질이 아니다.
②(`log_workspace_bytes`)를 루프가 네 번 시도하고 네 번 다 기각한 것이 그
사례다. **사람이 리포트 하나를 보고 읽은 수정 목록을 루프의 정답으로 삼지
마라.** 루프가 안 하면 `failures.jsonl` 에서 "왜 안 했는가" 를 확인한다 —
기각한 것과 탐색조차 안 한 것은 다르다.

# 5단계 — 실제 LLM 연결 (Pydantic AI + OpenAI)

## D-21. 클라이언트는 `LLMClient` Protocol 뒤에 둔다

`pydantic_ai.Agent` 를 호출부에 노출하지 않는다. 루프는 `complete(role,
prompt, **kw)` 만 안다. **`MockLLM` 과 교체 가능해야 ablation 과 `replay`
가 성립한다** — 그것이 §16.1 의 전제다.

```
agents/schemas.py       Pydantic 출력 스키마 (DiagnosisOutput, RuleOutput)
agents/openai_client.py OpenAILLM — Protocol 구현
agents/prompts/         _common.md / diagnose.md / optimize.md / hw/sm_86.md
```

프롬프트는 **두 층**이다 (§11.2). `_common.md`(역할 무관 제약) + `hw/*.md`
(주입되는 도메인 사실) + `<role>.md`(역할 정의). 새 하드웨어 추가가 파일
하나가 된다.

### 스키마 위반은 재시도 후 폐기

Pydantic AI 가 validator 실패를 모델에 되먹여 재시도한다(`retries=2`).
상한을 넘으면 **그 후보를 버린다.** 부분 수용하지 않는다 (§26.4).

`RuleOutput` validator 가 마크다운 펜스를 벗기고, 금지 참조·리터럴 예산을
LLM 경계에서 1차로 거른다. AST 검사(`rules/checks.py`)가 2차다 —
**문자열 검사는 우회 가능하므로 구조적 방어와 병행한다** (§11.7).

### 안전장치 (§4-1)

```
OPENAI_API_KEY 없음  -> MissingAPIKey. ★ MockLLM 으로 조용히 폴백하지 않는다
예산 상한            -> 호출/입력/출력 토큰 각각. 넘으면 BudgetExceeded
확인 요구            -> estimate_and_confirm(). --yes 로만 우회
프롬프트 캐싱        -> 해시 키. 초반에 같은 프롬프트가 반복된다
llm_calls/          -> 프롬프트·응답 원본. 키와 인증 헤더는 저장하지 않는다
rate limit          -> 한 번 물러서되 조용히 줄이지 않고 카운터에 남긴다
```

`tests/test_openai_client.py` 14개가 **API 호출 없이** 이것들을 고정한다.

### 밟은 것

`pydantic-ai 2.x` 에서 `RunResult.usage` 는 **속성**이다 (1.x 는 메서드).
`res.usage()` 가 `TypeError` 를 냈다. 둘 다 시도하되 **토큰을 못 읽으면
에러**로 만들었다 — 0 으로 떨어지면 예산 감시가 무력해진다 (§26.4).

## D-22. 첫 실행 구성 (§4-2)

```
에이전트   Diagnostician + Optimizer 만 (Instrumenter / Auditor 는 끔)
분할      균형 분할 nk11008 (긴 31% / 짧은 69%)
씨앗      손규칙
모델      gpt-5.4-mini-2026-03-17, 온도 0.7, seed 20260821
```

Instrumenter 를 끄는 이유: 첫 실행에서 피처가 늘면 regret 개선이 "진단
덕분" 인지 "피처 덕분" 인지 섞인다. §16.1 ablation 의 두 번째 줄이 핵심
주장이므로 그것부터 깨끗하게 잰다.

**1라운드 실측** (스모크): 13 호출 / 입력 78,511 · 출력 5,793 토큰 / 30.3초.
train 1.1846 -> 1.1316. 20라운드 예상 입력 약 157만 토큰.

LLM 이 첫 시도에서 가설을 정확히 따랐다 — `log_workspace_bytes` 항 추가,
정적 검사 통과. 그리고 `f.reg_pressure * f.occupancy_deficit` 같은 **피처
곱**을 스스로 만들었다. MockLLM 의 템플릿에는 없던 구조다.

## F-12. ★ 첫 실제 LLM 실행 — 관문 미달, 그리고 예산 우회

```
모델      gpt-5.4-mini-2026-03-17, 온도 0.7, seed 20260821
구성      Diagnostician + Optimizer (Instrumenter/Auditor 끔)
분할      nk11008 (긴 31% / 짧은 69%)   씨앗  손규칙
20라운드  557초  호출 128  입력 100만 · 출력 10만 토큰  rate-limit 0
```

학습 분할 regret 1.1846 -> **1.0632**. 검증 폭발 0건, 셀 8/64.

### 관문과 같은 기준(a888 61형상)에서 재채점

| | 전체 61 | 짧은 41 | 긴 20 | 홀드아웃 10 |
|---|---:|---:|---:|---:|
| **벤더 (nearest) ★관문** | **1.0797** | 1.0977 | 1.0439 | 1.0700 |
| 손규칙 (같은 분할 적합) | 1.1891 | 1.2180 | 1.1318 | 1.2121 |
| **LLM 최고** | **1.0850** | **1.0695** | 1.1174 | 1.2035 |

**관문 미달** (1.0850 vs 1.0797). 그러나 **짧은 형상에서는 벤더를 이겼다**
(1.0695 vs 1.0977) — 여지의 87% 가 있는 구간이고 GBDT 상한 1.044 에 가깝다.
대신 긴 형상에서 잃는다 (1.1174 vs 1.0439).

**학습 분할이 짧은 형상 69% 라 §10.1 이 예측한 그대로다.**
`MIN_REGIME_FRAC = 0.25` 를 통과한 31% 로도 부족했다 — F-10 의 "25% 는
하한이지 안전선이 아니다" 에 실증이 하나 더 붙었다.

### ★ 이 실행은 관문 판정에 쓸 수 없다 — 예산을 우회했다

최종 규칙이 **가중치 8개로 항 19개**다 (§15.1b). 정적 검사가 통과시켰다.
따라서 "8개 가중치로 얻은 1.085" 가 아니다.

세 가지를 고쳤다.

| | 무엇 | 왜 |
|---|---|---|
| 정적 검사 | 각 `w[i]` 는 **한 번만** | 항 수를 무제한으로 늘려 예산을 우회했다 |
| 클라이언트 | `asyncio.Semaphore` 를 **루프마다** | `__init__` 생성이면 2라운드부터 죽고, 그 예외가 폐기로 처리돼 **조용히 호출을 잃는다** |
| 프롬프트 | **실제 거부된 코드**를 함께 제시 | 규칙만 적으면 지켜지지 않는다 (132/240 재시도 소진) |

"같은 식이 두 번 나오면 거부" 는 **넣지 않았다** — 형상 수준 분기의
정당한 재가중을 오탐한다. 실제 병리(같은 식 + 같은 가중치)는 재사용
검사가 이미 잡는다.

새 검사로 손규칙은 통과(항 7 / 가중치 7), 문제의 LLM 규칙은 거부된다
(항 19 / 가중치 8). 회귀로 고정했다.

### 확인된 것

LLM 이 MockLLM 템플릿에 없던 구조를 만들었다 — 피처 곱, 항의 합에 하나의
가중치, 형상 분기 안에서 여러 항 재가중. 그리고 §30.6b 의 힌트를 따라
`log_workspace_bytes` / `log_inst_total` / `log_mainloop_iters` 를 전부
넣었다. **손규칙이 안 쓴 축들이다.**

# 6단계 — 저장소 정리 (재실행 전)

## D-23. ★ 감시가 있는데 보증하지 못하는 두 가지

`§26.3` 의 스킵 감시가 두 군데서 새고 있었다. **둘 다 같은 뿌리다** —
감시는 돌지만 그 결과가 "검증됐다" 를 보증하지 못한다.

### (1) 우회 경고가 캡처에 삼켜진다

`print` -> `terminalreporter.write_line` 로 이미 한 번 고쳤는데도
부족했다. `runtest` 안에서는 pytest 버전에 따라 전역 캡처가 살아 있어
리포터 출력도 삼켜진다.

**이 환경(pytest 9.1.1)에서는 통과했고 다른 환경에서는 실패했다.**
즉 감시의 보장이 pytest 버전에 의존하고 있었다 — 그것 자체가 §30.8 이
말한 "강제되지 않은 규율" 이다.

`capturemanager.global_and_fixture_disabled()` 로 캡처를 명시적으로 끈다.
`user_properties` 에도 남겨 한 겹 더 둔다.

### (2) 부분 스킵을 못 잡는다

kernelTab R-1 은 **모듈 전체** 스킵을 잡았다. 한 층 아래가 남아 있었다.

```
R-1    모듈 전체 스킵 (ran == 0)   -> 감시가 잡는다
이번   모듈 일부 스킵              -> 감시가 못 잡는다
```

`datasets/` 가 gitignore 되어 있으므로 **새로 클론한 사람은 이 상태가
기본**인데 아무 신호도 없었다. 실측:

```
test_leakage.py  11/15 (73%) 스킵      <- 누출 방지 검증의 1/4 만 돈다
test_loop.py     14/22 (64%)
test_synth.py    13/14 (93%)
190 passed, 63 skipped  — 초록불
```

`MAX_SKIP_FRAC = 0.5` 초과면 경고하고 "이 실행 결과로 누출 방지를
보증하지 마라" 를 띄운다. **거부하지 않는다** — 번들 없이 개발하는 것은
정상 경로다. 다만 그 사실이 보여야 한다.

## D-24. ruff — ISC004 가 실질적이었다

298건 -> 0건. 대부분 형식이지만 하나는 실제 위험이었다.

**ISC004 49건이 전부 규칙 코드 템플릿과 테스트 케이스 표였다.**
컬렉션 리터럴 안에서 괄호 없이 문자열이 이어지면 **쉼표 하나를 빠뜨렸을
때 조용히 합쳐진다.** mock 이 의도와 다른 규칙을 내도 문법은 맞으니
발견이 어렵다.

`mock.py` 의 두 표는 삼중따옴표로 다시 썼다 — 위험 자체가 사라진다.

무시한 규칙과 이유는 `ruff.toml` 에 적었다. 특히 `PLC0415`(함수 안
import)는 이 코드베이스에서 **의도**다 — 뜨거운 경로에서 pandas 를 빼고,
순환 의존을 끊고, 선택 의존성을 격리한다.

### 밟은 것 — 도구가 이미 하는 일을 직접 짰다

ISC004 를 자동으로 고치려고 스크립트를 짰는데 같은 줄의 컬럼 오프셋이
밀려 파일 6개를 깨뜨렸다. 두 번째 판에 `ast.parse` 검증을 넣었더니
그것이 깨짐을 막았다. 결국 `ruff --fix --unsafe-fixes` 가 정확히 해결했다.

**자동 수정 스크립트를 직접 짜기 전에 도구가 이미 하는지 확인할 것.**
