## ★ 수정 1 — §14.1 채점 비용 정정

원 문서는 "채점 수 밀리초"라고 했다. **틀렸다.**

```
형상당 후보 ≈ 980,915 / 66 ≈ 15,000
라운드당 score() 호출 = 12규칙 × 66형상 × 15,000 ≈ 1,190만 회
순수 파이썬, 호출당 10µs  ->  라운드당 약 2분
50라운드면 채점에만 100분
```

이러면 **"채점이 공짜라서 규칙 12개를 병렬로 만든다"는 설계 전제가
무너진다.** §21의 피처 행렬 사전 계산으로 해결한다.

### 라운드 루프에 단계 하나 추가

원 문서 §14.1 의 5번 단계를 다음으로 대체한다.

```
5. 정적 검사 -> 샌드박스 실행 -> ★ 가중치 최적화 -> 채점
```

**모든 후보를 가중치 최적화 후에 채점한다.** 안 하면 진화가 구조가
아니라 **가중치 운**을 선택한다. 근거는 §29.3.

비용: 규칙당 Nelder-Mead 200회 평가 × 형상 66개 × numpy 연산 ≈ 1~2초.
12개면 라운드당 20초 내외이며 병렬화 가능하다. 채점 자체(0.4초)보다
크지만 LLM 호출(20~40초)보다는 작다.

## ★ 대체 1 — §8.1 규칙 인터페이스 (벡터화)

### 왜 바꾸는가

피처는 `(Problem, Hardware, Config)` 의 **순수 함수**이고 규칙과 무관하다.
같은 `(형상, config)` 쌍에 대해 어떤 규칙이 오든 값이 같다. 그러니
**한 번만 계산해 행렬로 올려두고, 규칙은 그 행렬 위의 연산이 되게 한다.**

```
라운드당 12규칙 × 66형상 × numpy 연산 ~10회 (15k 배열)
  = 약 8,000 numpy 연산  ->  0.4초        (300배 개선)
```

### 새 인터페이스

**LLM 이 쓰는 것 — 형상 하나에 대한 점수 벡터. 가중치는 별도 인자.**

```python
W0 = [2.0, 0.5, 1.5, 0.3]      # 초기값만 LLM 이 제시한다

def score(f: Feats, p: ShapeInfo, hw: Hardware, w) -> np.ndarray:
    """이 형상의 모든 후보에 대한 점수. 낮을수록 좋다.

    f.<name>  : shape (n_candidates,) float 배열. config 별 피처값
    p.<name>  : 스칼라. 형상 수준 값 (M, N, K, arith_intensity,
                is_memory_bound, ridge_ratio ...)
    hw.<name> : 스칼라. 하드웨어 상수
    w         : 길이 고정 float 배열. ★ 수치 최적화기가 맞춘다
    """
    s  = f.tail_waste * w[0]
    s += f.smem_pressure * w[1]
    if p.is_memory_bound:                        # 형상 수준 -> if 가능
        s += f.tile_bytes_ratio * w[2]
    s += np.where(f.spill_bytes > 0, w[3], 0.0)  # config 수준 -> 산술로
    return s
```

**가중치를 `w` 로 분리하는 이유는 §29에서 다룬다.** 요약하면: 규칙은
구조(이산, 조합적)와 가중치(연속)로 나뉘고, LLM 은 구조에만 강점이
있다. 가중치를 코드에 박으면 좋은 구조가 나쁜 초기값 때문에 버려진다.

### 이 설계의 부수 이득

**config 수준 `if` 분기가 문법적으로 어려워진다.** `f.tail_waste` 는
배열이라 `if f.tail_waste < 0.1:` 이 `ValueError` 를 낸다. §2.3 에서
"나쁜 수정" 이라고 한 조건부 특수화를 자연스럽게 막는다.

반대로 **형상 수준 조건은 스칼라라 `if` 가 그대로 된다.** 이것이 바로
우리가 허용하고 싶은 종류다 — "메모리 바운드면 다르게 판단한다" 는
일반화되지만 "M이 4096이면 17번 config" 는 암기다.

### 배포 형태

최종 산출물은 스칼라 함수여야 하므로 얇은 shim 을 제공한다.

```python
W_FITTED = [2.31, 0.44, 1.87, 0.29]   # 최적화기가 맞춘 값. 규칙과 함께 저장

def rank(problem, hw, candidates) -> list[Config]:
    """배포용. 내부적으로 피처를 계산해 score() 에 넘긴다.
    후보가 수천 개뿐이므로 속도는 문제되지 않는다."""
    f, p = build_feats(problem, hw, candidates)
    return [candidates[i] for i in np.argsort(score(f, p, hw, W_FITTED))]
```

**같은 `score()` 코드가 학습과 배포 양쪽에서 쓰인다.** 변환이 없으므로
"학습 때와 배포 때가 다르다" 는 오류가 원천 차단된다.

**배포 산출물 = `score()` 코드 + `W_FITTED`.** 아키텍처를 옮길 때는
코드를 그대로 두고 `W_FITTED` 만 재적합한다 (§29.5).

### 정적 검사 갱신 (§8.3)

```
추가 금지:
  - f.<피처> 에 대한 if / while / 비교 후 분기
    (AST 로 f.* 가 if 조건에 등장하면 거부)
  - 등록되지 않은 f.<이름> 접근  (오타를 조용히 통과시키지 않기 위해)
  - np 외 import
허용:
  - p.* / hw.* 에 대한 if
  - np.where, np.clip, np.minimum/maximum, np.log, np.sqrt, 사칙연산

가중치 관련:
  - w 는 반드시 인덱스로만 접근 (w[0], w[1] ...). 슬라이싱/연산 금지
  - W0 의 길이 == score 안에서 참조하는 최대 인덱스 + 1 (검증)
  - ★ len(W0) 를 리터럴 예산에 포함시킨다 (§29.4)
```

리터럴 예산 8개(= 숫자 리터럴 + 가중치 개수 합산), AST 노드 상한은
그대로.

## §21. 피처 행렬 사전 계산

### 21.1 구조

```python
class FeatureMatrix:
    """(형상, config) -> 모든 피처값. 표 로드 시 한 번 계산한다."""

    def __init__(self, table: PerfTable, features: FeatureRegistry): ...

    def for_shape(self, p: Problem) -> tuple[Feats, ShapeInfo]:
        """이 형상의 후보 전체에 대한 피처 배열 묶음."""

    def invalidate(self, feature_name: str) -> None:
        """피처가 추가/수정되면 그 열만 다시 계산한다."""
```

- 형상별로 `dict[str, np.ndarray]` 를 들고 있는다.
- 전체 크기: 66형상 × 15k후보 × 25피처 × 8바이트 ≈ **200MB**. 문제없다.
- 초기 계산 비용: 100만 × 25 = 2,500만 회 파이썬 호출 ≈ 4분.
  **디스크에 캐싱한다** (`.npz`, 피처 라이브러리 해시를 키로).

### 21.2 피처 추가 시

Instrumenter 가 새 피처를 만들면 **그 열만** 계산한다 (100만 회, 10초).
전체 재계산은 필요 없다.

피처 버전이 바뀌면(`tail_waste_v2`) 새 열로 추가하고 구 열은 남긴다.
§8.4 의 라이프사이클과 일치한다.

### 21.3 `Feats` 객체

```python
@dataclass
class Feats:
    _cols: dict[str, np.ndarray]
    def __getattr__(self, name):
        try:
            return self._cols[name]
        except KeyError:
            raise AttributeError(
                f"등록되지 않은 피처: {name}. 사용 가능: {sorted(self._cols)}"
            ) from None
```

**오타가 조용히 통과하지 않게 한다.** LLM 이 `f.tail_wast` 를 쓰면
`AttributeError` 로 즉시 실패하고, 그 규칙은 폐기된다.

## §22. 합성 표 생성기 — 데이터 없이 개발하기 위한 핵심 장치

### 22.1 왜 "적당히 랜덤" 이면 안 되는가

무작위 시간을 채운 표로 파이프라인을 돌리면:
- 어떤 피처도 성능을 설명하지 못하므로 규칙이 배울 게 없다
- LLM 이 "아무 피처나 조합" 하는 방향으로 수렴한다
- 채점기 버그(부호 반전, 정답 누출)를 **잡을 수 없다** —
  랜덤 표에서는 정답 누출이 있어도 regret 이 좋아 보이지 않는다

**물리를 흉내 낸 생성기가 필요하다.** 알려진 구조를 심어두고, 파이프라인이
그 구조를 찾아내는지로 검증한다.

### 22.2 생성 모델

> **갱신 (kernelRule 1단계).** 아래 스켈레톤의 구조 하나가 틀렸다.
> `t_sol = max(compute, memory)` 를 먼저 만들고 벌점을 곱하면 **형상 x
> config 상호작용이 사라진다.** 실측했더니 고정 config 하나가 모든 형상에서
> 최적에 가까워져 정적 top-1 이 **1.03** 까지 내려갔다. 그런 표에서는 규칙이
> 배울 것이 없다. **벌점은 연산 쪽에만 곱한다.**

```python
def synth_time(p, hw, cfg, rng) -> float:
    # 1. roofline 두 항을 ★ 따로 둔다
    t_compute = flops(p) / hw.peak_tflops_f16 / 1e12
    t_memory  = bytes_moved(p) / hw.bandwidth_gbps / 1e9

    # 2. wave quantization                     ceil(w)/w
    # 3. ★ 부분 타일 낭비 (구조 #11)            형상 x config 상호작용의 주 동인
    #    M=1 에 128행 타일이면 일의 99.2% 가 버려진다
    # 4. occupancy (smem 압력)                 1 + c * smem/smem_per_block
    # 5. ★ 스필                                 1 + c * (spill > 0)
    #    실측: 전체 행의 7.4% 가 스필. rel 중앙 13.6, 최대 37.2
    #    **긴 꼬리가 전부 여기서 나온다** (비스필은 중앙 1.54 / 최대 8.6)
    # 6. split-K 리덕션                         1 + c * (split_k - 1)
    # 7. mainloop 워밍업                        stages / iters
    # 8. ★ 타일/warp 연산 강도 — **포화가 있다**
    #    안 두면 256x256 이 공짜 이득을 받아 스필 벌점을 상쇄한다.
    #    실측에서 256x256 의 rel 중앙값은 17.9 로 가장 나쁘다
    # 9. 명령어 수 / 레지스터 압력 — 연속 축. 없으면 눈금 충돌이 과해진다
    penalty = wave * edge * smem * spill * sk * warm * tile * warp * inst * reg
    penalty = penalty ** PRESET.struct          # struct=0 -> null 프리셋

    # ★ 연산 쪽에만 곱한다. 대역폭은 타일 모양을 모른다.
    #   이러면 "메모리 바운드에서 config 영향이 약하다"(구조 #4)가
    #   **부과되는 대신 자연히 나온다.**
    t = max(t_compute * penalty,
            t_memory * (1 + mem_damp * (penalty - 1))) + LAUNCH_MS

    # 측정 노이즈 — ★ 커널 시간에 의존한다 (§30.2)
    sigma = NOISE_A / t + NOISE_B
    t = t * (1.0 + rng.normal(0, sigma))

    # ★ 타이머 양자화 — 빼면 실제로는 없는 순위가 생긴다
    return round(t / TICK_MS) * TICK_MS
```

**보정 결과** (`normal` 프리셋, 실측 대비):

| 지표 | 실측 | 합성 |
|---|---:|---:|
| 난이도 중앙 | 1.670 | 1.597 |
| p90/best 중앙 | 2.811 | 2.355 |
| max/best 중앙 | 24.68 | 23.18 |
| 정적 top-1 (정본) | 1.115 | 1.208 |
| 정적 top-3 / 5 / 8 | 1.040 / 1.033 / 1.028 | 1.037 / 1.030 / 1.028 |
| `distinct_time_frac` 중앙 | 0.200 | **0.102** |

마지막 줄이 남은 불일치다 — 합성 커널이 실제보다 서로 덜 다르다. 눈금 충돌이
실제보다 심하다는 뜻이라 **보수적인 방향**이지만, **분해능 관련 결론을 합성
표로만 내리면 안 된다.**

### 22.3 생성기가 만족해야 할 것

```
- 실제 형상 그리드를 그대로 쓴다 (kernelTab core/shapes.py 재사용)
- 실제 config 열거를 그대로 쓴다 (kernelTab backends/sm80.py 재사용)
- 실제 alignment 구조를 반영한다 (a888 형상과 a448 형상의 후보가 다르다)
- 난이도 분포가 실측과 비슷하게 나온다 (실측 중앙 1.67, 범위 1.12~2.95)
- ★ 정적 top-1 이 1.10~1.25, top-8 이 1.00~1.02
  (실측 정본: 1.115 / 1.006 — §30.5)
- p90/best 중앙 2.8, max/best 중앙 24.7 (실측)
- ★ **긴 꼬리는 전적으로 스필이다.** 전체 행의 7.4% 가 스필이고 그들의
  slowdown 중앙 13.6(최대 37.2), 비스필은 중앙 1.54 / p90 2.58 / 최대 8.6.
  스필을 따로 보정하지 않으면 꼬리가 재현되지 않는다.
- ★ 노이즈가 커널 시간에 의존한다 (§30.2). 고정 노이즈면 작은 형상의
  어려움이 사라져 합성 표가 실제와 근본적으로 달라진다
- ★ **타이머 양자화를 적용한다.** 빼면 합성 표에 실제로는 존재하지 않는
  순위가 생기고, 채점기의 눈금 처리를 검증할 수 없다.
  검증: 짧은 형상에서 `n_distinct_times / n_candidates` 가 실측과
  비슷한가 (예: `512x512x512` 는 최빈값 하나에 9% 가 몰린다)
- table.parquet 과 **동일한 스키마**로 저장된다
```

마지막이 중요하다. **합성 표도 진짜 표와 같은 파일 형식**이어야
로더/어댑터가 검증된다.

### 22.4 파이프라인 검증 — 심은 구조를 되찾는가

합성 표의 진짜 가치는 여기 있다. **정답을 알고 있으므로 파이프라인이
맞게 도는지 판정할 수 있다.**

| 검증 | 기대 |
|---|---|
| 손으로 쓴 규칙의 regret@1 | 1.10 이내 |
| 정적 top-1 / top-8 | 1.10~1.25 / 1.00~1.02 |
| GBDT regret@1 | 1.02 이내 |
| `distinct_time_frac` 중앙 | 0.15~0.25 (실측 0.20) |
| LLM 루프 20라운드 후 | 손으로 쓴 규칙 근처 도달 |
| 난이도가 `is_memory_bound` 와 음의 상관 | r < -0.5 |
| 규칙이 `tail_waste` 를 반드시 쓰게 되는가 | 상위 규칙 대부분 사용 |

**LLM 루프가 심어둔 구조를 못 찾으면 진단 리포트나 프롬프트에 문제가
있는 것이다.** 실제 데이터에서 실패하면 원인이 "데이터가 어려워서"인지
"파이프라인이 나빠서"인지 구분할 수 없지만, 합성 데이터에서는 구분된다.

### 22.5 여러 난이도 프리셋

```
easy    구조가 강하고 노이즈가 작다     -> 파이프라인이 반드시 성공해야 함
normal  실측 통계를 흉내낸다             -> 주 개발 대상
hard    구조가 약하고 노이즈가 크다      -> 실패를 실패로 보고하는지 확인
null    시간이 config 와 완전히 무관     -> ★ regret 이 1.0 근처여야 함
```

**`null` 프리셋이 정답 누출 탐지기다.** config 가 성능에 아무 영향을
안 주는 표에서 규칙이 regret 1.0(= 무작위와 동등)이 아니라 개선을
보이면, **어딘가에서 정답이 새고 있다.**

`null` 프리셋에도 **양자화는 적용한다.** 그래야 "동점이 대량으로
발생할 때 tie-break 가 정답을 보는가" 를 시험할 수 있다 (§30.7).

### 22.6 합성 모드 오염 방지

```python
@dataclass(frozen=True)
class RunConfig:
    data_source: Literal["real", "synthetic"]
    synthetic_preset: str | None
```

- 합성 모드의 모든 산출물(`runs/`, 리포트, 그림)에 **`SYNTHETIC` 워터마크**를
  파일명과 문서 제목에 박는다.
- 합성 run 의 규칙을 실제 데이터에 그대로 쓰지 않는다.
  실제 표가 오면 **처음부터 다시 돌린다** (피처 라이브러리만 재사용).
- 논문/보고에 합성 결과를 인용하지 않는다. 파이프라인 검증용이다.

## §24. Mock LLM 모드

### 24.1 목적

- API 비용 없이 루프 전체를 개발/디버깅한다
- CI 에서 루프가 도는지 확인한다
- **정적 검사와 샌드박스를 시험한다** — 일부러 나쁜 코드를 내게 한다

### 24.2 인터페이스

```python
class LLMClient(Protocol):
    async def complete(self, prompt: str, schema: type[BaseModel]) -> BaseModel: ...

class MockLLM(LLMClient):
    """모드별로 정해진 응답을 낸다."""
```

### 24.3 Mock 모드

| 모드 | 동작 | 검증 대상 |
|---|---|---|
| `canned` | 미리 준비한 규칙 5~10개를 순환 | 루프 배관, 아카이브, 채점 |
| `mutate` | ★ 부모 규칙의 **구조**를 섭동 (아래) | 진화 동역학, 수렴 곡선 |
| `adversarial` | 암기/누출/무한루프/오타 코드를 낸다 | **정적 검사와 샌드박스** |
| `replay` | 이전 run 의 `llm_calls/` 를 재생 | 결정론적 재현 |

#### ★ 정정 — `mutate` 는 가중치가 아니라 **구조**를 섭동한다

이 문서의 이전 판은 "부모 규칙의 가중치를 무작위 섭동" 이라고 했다.
**그러면 아무것도 시험하지 못한다** — 가중치는 어차피 `fit_weights` 가
맞추므로(§29.3) **무작위** 초기값 섭동은 채점 결과에 거의 영향이 없다
(⚠️ 2026-08-22: 무작위 섭동이 그렇다는 뜻이다. **체계적으로 더 나은
초기값은 결과를 크게 바꾼다** — §29.3 의 정정 참조). 수렴 곡선이
평평하게 나오고, 그것이 루프가 잘 도는 것인지 목이 아무것도 안 하는
것인지 구분할 수 없다.

**항을 넣고 빼고 바꾸는 것**이 진화의 단위다.

```
항 추가 (가설이 지목한 것 우선) / 항 제거 / 항 교체 /
형상 수준 분기 추가·제거
```

그래야 "파이프라인이 빠진 항을 찾아내는가" 를 실제로 시험할 수 있다.
그리고 그것이 §16.1 ablation 의 "진단이 기여하는가" 와 직접 연결된다 —
목이 가설을 따를 때와 무작위일 때의 차이가 곧 그 답이다.

**`adversarial` 모드가 특히 중요하다.** 다음을 반드시 포함한다:

```python
ADVERSARIAL_CASES = [
    "if problem.M == 4096: return [candidates[17]]",   # 암기
    "return sorted(candidates, key=lambda c: TABLE[...])",  # 정답 누출
    "while True: pass",                                 # 무한 루프
    "import os; os.system('rm -rf /')",                 # 샌드박스 탈출
    "s = f.tail_wast * 2.0",                            # 오타
    "if f.waves < 1: s += 5.0",                         # 배열에 if
    "s = f.a*1.1 + f.b*2.2 + ... (리터럴 20개)",         # 리터럴 초과
    "s = np.random.rand(len(candidates))",              # 비결정론
]
```

각각이 **의도한 검사에 걸리는지** 테스트로 고정한다. 하나라도
통과하면 방어에 구멍이 있는 것이다.

### 24.3b 샌드박스는 호출 스크립트에 `__main__` 가드를 요구한다

`multiprocessing` 의 `forkserver` 도 `spawn` 도 **자식이 `__main__` 을 다시
import 한다** (`spawn.get_preparation_data`). 루프를 돌리는 스크립트가
`if __name__ == "__main__":` 로 감싸여 있지 않으면 무한 재귀가 되고,
파이썬은 그것을 `BrokenPipeError` 로 보여준다 — **원인이 전혀 안 보인다.**

`fork` 는 그 문제가 없지만 부모 상태를 통째로 물려받아 격리가 아니다.

그래서 `run_isolated` 가 첫 호출에 **preflight** 를 돌려, 실패하면 무엇을
고쳐야 하는지 말하는 에러로 바꾼다. **샌드박스를 끄는 것은 답이 아니다** —
LLM 은 무한 루프를 실제로 만들어낸다.

### 24.4 `replay` 모드와 재현성

`runs/{run_id}/llm_calls/` 에 프롬프트와 응답 원본을 저장하므로,
같은 run 을 LLM 없이 재실행할 수 있다. 채점기나 아카이브를 고쳤을 때
**같은 LLM 응답으로 결과가 어떻게 달라지는지** 볼 수 있다.

## §25. 실행 추적 (`runs/`)

```
runs/{run_id}/
  config.json        RunConfig — 모델, 온도, 시드, 데이터 소스, 프리셋
  bundle.json        쓴 번들의 bundle_id 와 env_hash
  features.lock      피처 라이브러리 스냅샷 (이름 + 코드 해시)
  rounds.jsonl       라운드별 요약 (regret, 아카이브 상태, 소요)
  rules/             생성된 모든 규칙 (버린 것 포함)
    rule_0001.py
    rule_0001.json   부모, 가설, changes, 채점 결과, 정적검사 결과
  hypotheses.jsonl   가설 이력
  archive.jsonl      아카이브 갱신 이력
  failures.jsonl     실패 이력 (프롬프트에 들어가는 것)
  llm_calls/         프롬프트 + 응답 원본
  report.md          최종 리포트
```

`run_id` = `{timestamp}-{data_source}-{모델}-{설정해시}` 형태.
**`data_source` 가 `synthetic` 이면 이름에 드러나야 한다.**

`features.lock` 이 중요하다. 피처가 진화하므로, 어느 시점의 피처
집합으로 얻은 결과인지 알아야 재현이 된다.

### 26.4b ★ 판정할 수 없으면 판정하지 마라 (2026-08-22, D-37)

§26.4 는 "조용히 **아무것도 안 하는**" 경우를 모았다. 그 쌍둥이가 있다 —
**조용히 한쪽으로 판정하는** 경우다.

```python
try:
    src = inspect.getsource(f.fn)
except (OSError, TypeError):
    return True          # "hw 를 쓴다" 로 판정한 것이다
```

`True` 는 기본값처럼 보이지만 **주장**이다. 그리고 그 주장이 틀리면
하드웨어를 안 쓰는 정상 피처가 스케일 검사에서 전부 기각된다. 실제로
그랬다 — `exec` 로 만든 함수는 `inspect.getsource` 가 **항상** 실패하므로
생성된 피처가 하나도 통과하지 못했다.

```
예외 처리의 기본값이 한쪽 판정이면 그것은 판정이지 기본값이 아니다.
판정할 수 없으면 판정하지 마라 — 예외를 내라.

★ 특히 그 기본값이 "더 안전한 쪽" 으로 보일 때 위험하다.
  "의심스러우면 기각" 이 합리적으로 보였지만, 판정 근거 자체가 없었다.
```

**점검 방법.** `except` 블록이 값을 **반환**하면 물어라 — 그 값이 관측인가
추측인가. 추측이면 예외로 바꿔라. 로그에 남기는 것으로는 부족하다.
그 값을 쓰는 쪽은 로그를 안 본다.

이 부류를 하나 더 잡았다: 섭동 검사에서 축 하나를 안 흔든 것(D-38).
`min(a, b, c)` 에서 `a` 를 고정하면 `a` 에 물린 대상이 통째로 "변하지
않는다" 로 판정된다 — 그것도 관측이 아니라 **검사 설계의 산물**이다.

### 26.4 "조용히 아무것도 안 하는" 경계 목록

구현 중 다음을 만들 때마다 **"조건이 안 맞으면 무엇을 하는가"** 를
명시적으로 결정하고 주석에 남긴다.

```
- 정적 검사가 파싱에 실패하면?          -> 거부 (통과 아님)
- 피처 검증이 예외를 만나면?             -> 기각 (승인 아님)
- 홀드아웃 분할이 빈 집합을 내면?        -> 에러 (진행 아님)
- 번들에 필수 컬럼이 없으면?             -> 에러 (기본값 아님)
- 노이즈 바닥을 계산할 수 없으면?        -> 보수적 큰 값 (0 아님)
- LLM 응답이 스키마를 위반하면?          -> 재시도 후 폐기 (부분 수용 아님)
```

**전부 "실패 쪽으로 기운다."** 조용히 통과하는 기본값을 두지 않는다.

## §29. 가중치 최적화 — 구조와 파라미터의 분리

### 29.1 왜 나누는가

규칙은 두 가지가 섞여 있다.

```python
s  = f.tail_waste * 2.0          # 구조: tail_waste 를 쓴다   가중치: 2.0
s += f.smem_pressure * 0.5       # 구조                        가중치
if p.is_memory_bound:            # 구조 (이산 분기)
    s += f.tile_bytes_ratio * 1.5
```

| | 성격 | 적합한 도구 |
|---|---|---|
| **구조** | 이산, 조합적. "어떤 피처를 어떻게 엮을까" | **LLM** |
| **가중치** | 연속. "2.0 이 맞나 2.7 이 맞나" | **수치 최적화기** |

**LLM 에게 가중치를 튜닝시키는 것은 낭비다.** 호출 한 번에 하나씩만
시도하게 되고, LLM 이 잘하는 종류의 판단도 아니다. 반대로 수치
최적화기는 구조를 제안할 수 없다.

### 29.2 최적화기 선택

**gradient descent 는 쓸 수 없다.** 목적함수 regret 은 `argmin` 을 거쳐
나오므로 가중치에 대해 **계단 함수**다. 가중치를 조금 바꿔도 순위가
안 바뀌면 regret 이 그대로고, 어느 순간 순위가 뒤집히며 점프한다.
기울기가 0이거나 정의되지 않는다.

| 방법 | 언제 | 비고 |
|---|---|---|
| **Nelder-Mead** | **기본 선택** | `scipy.optimize`. 파라미터 8개 이하, 200회 평가에 수 초 |
| Powell | Nelder-Mead 가 불안정할 때 | 좌표 방향 직선탐색 |
| CMA-ES | 파라미터 10개 초과, 지형이 험할 때 | `cma` 패키지. 재시작으로 국소최적 탈출 |
| 좌표 하강 | 해석이 필요할 때 | 어느 가중치가 민감한지 부수적으로 나온다 |
| 미분가능 완화 | `[열림]` | listwise ranking loss 로 대체하면 GD 가능. 대리 손실이라 regret 과 불일치. **처음엔 하지 않는다** |

채점이 numpy 벡터화되어 있으므로(§21) 200회 평가가 1~2초다.
**가중치 최적화는 사실상 공짜다.**

### 29.3 ★ 언제 돌리는가 — 이것이 핵심

**모든 후보 규칙을 가중치 최적화 후에 채점한다.**

```
잘못:  LLM 규칙 생성 -> 채점 -> 아카이브
맞음:  LLM 규칙 생성 -> 가중치 최적화 -> 채점 -> 아카이브
```

안 하면 이런 일이 벌어진다:
- 좋은 구조 A 가 나쁜 초기값을 받아 regret 이 나쁘게 나와 **버려진다**
- 평범한 구조 B 가 우연히 좋은 초기값을 받아 **살아남는다**
- 진화가 구조가 아니라 **가중치 운**을 선택하게 된다

공정한 비교는 각 구조가 자기 최선의 가중치를 가졌을 때만 성립한다.

**부수 이득: 프롬프트가 단순해진다.** LLM 에게 이렇게 말할 수 있다.

```
가중치는 자동으로 맞춰집니다. 당신은 **어떤 피처를 어떻게 엮을지**에
집중하세요.
```

#### ★ 정정 (2026-08-22) — `w0` 는 "대략적이면 충분" 하지 않다

위 문장에 원래 *"초기값은 대략적인 것으로 충분하며"* 가 있었다. **틀렸다.**

`regret` 은 `argmin` 을 거치므로 **계단 함수**이고, Nelder-Mead 는 전역
탐색이 아니라 **국소 하강**이다. 나쁜 초기값이 나쁜 국소 최적에 가두면
재시작으로도 못 빠져나온다. 계단의 평평한 면 위에서는 방향 정보가 아예
없다.

**실증 둘:**

```
Architect 규칙을 전부 w=1 에서 출발      2.10 대신 10.26
has_spill 가중치 중앙 2.22 vs 15.07      홀드아웃 1.1384 vs 1.0735
```

두 번째가 특히 분명하다. 같은 조건에서 **바뀐 것은 피처 설명뿐**이고,
LLM 이 `has_spill` 에 준 초기 가중치가 7배 커졌다. 사용률은 양쪽 다
100% 였다 — **구조는 같았고 출발점만 달랐다**
(`docs/artifacts/feature-descriptions.md`).

**따라서:**

```
피처 설명은 "무엇을 재는가" 뿐 아니라 **"얼마나 중요한가"** 를 담아야
한다. 그것이 w0 의 출발점을 정하고, 출발점이 도착점을 정한다.
```

`features/physical.py::_PHYSICS` 가 그 자리다. 크기는 **식에서 유도되는
것만** 쓴다 (`1/(1-x)` 이면 0.5 에서 2배) — 측정에서 나온 배수를 쓰면
§12.3b 위반이다.

**§29.1 의 분리 자체는 유효하다.** 가중치 적합을 채점 전에 두는 것은
여전히 옳다 — 다만 그것이 **초기값을 무의미하게 만들지는 않는다.**

### 29.4 과적합 방지

파라미터 8개를 형상 66개에 맞추는 것이라 여유는 있으나 방심하면 안 된다.

```
- ★ len(W0) 를 리터럴 예산(8개)에 포함시킨다
  가중치가 많으면 어떤 구조든 비슷한 regret 에 도달해
  구조 비교 자체가 무의미해진다
- 학습 분할에서만 적합하고 검증 분할로 확인한다
- 학습 regret 과 검증 regret 의 격차를 라운드마다 기록한다
  격차가 벌어지면 파라미터 수를 줄여야 한다
- 가중치가 0 근처로 수렴한 항은 제거 후보로 표시한다
  (§8.4 의 피처 정리와 진단 리포트에 활용)
```

### 29.5b ★ 체제 전이는 아키텍처를 안 바꿔도 재현된다

**같은 GPU, 같은 표 안에서 짧은 형상 ↔ 긴 형상으로도 일어난다.**

이것이 중요한 이유가 둘이다.

1. **(a)/(b)/(c) 실험을 4090 을 기다리지 않고 지금 할 수 있다.** 결과가
   나쁘면 GPU 를 빌리기 전에 알게 되고, 좋으면 그 실험의 가설이 명확해진다.
2. **아키텍처 전이는 원리적으로 "학습에 없는 체제" 다.** 학습 분할을 아무리
   균형 잡아도 H100 의 체제는 담을 수 없다 (§10.1). 그래서 (b) 가 필요한
   이유가 데이터로 정당화된다 — 순수 전이 (a) 는 실패할 것으로 예상된다.

#### 대리 실험 (dev-cu124, MockLLM 12라운드, 고정 시험대 = 긴 형상 12개)

```

재적합 표본  긴 형상 8개 (블록 선택, 시험대와 겹치지 않음)

```

| | 긴 시험대 regret | 비용 |
|---|---:|---:|
| 손규칙 (짧은 형상 적합) | 1.0844 | — |
| **(a) 구조+가중치 그대로** | 1.0959 | 0s |
| **(b) 구조 고정 + w 재적합** | **1.0838** | **0.2s** |
| **(c) 표본으로 처음부터 학습** | 1.0866 | 20.7s |

```
(b) - (c) = -0.0028   (b) 가 근소하게 낫고, 비용은 131배 싸다
(a) - (b) = +0.0120   가중치 재적합에 이득이 있다
```

#### ⚠️ 이 결과를 과대해석하지 마라

**네 값이 전부 1.5% 안에 있다** (1.0838~1.0959). 긴 형상의 노이즈 바닥이
0.05~0.2% 이므로 (b)-(c) = 0.28% 는 유의성 경계에 있다. 그리고 **조건마다
궤적이 하나뿐이다.**

같은 방향의 다른 실험에서 궤적에 따라 **3.75 와 1.10 이 둘 다 나왔다**
(§10.1). 즉 "체제 불균형이 폭발을 부른다" 는 경향은 반복 관측됐지만,
**한 번의 궤적으로 (b) vs (c) 를 판정할 수는 없다.**

```
결론: (b) 가 (c) 보다 나쁘지 않고 131배 싸다는 것까지가 지금 말할 수 있는 것.
     "(b) 가 유의하게 낫다" 는 아직 아니다. 시드를 늘려야 한다.
     그리고 이 대리 실험은 **실제 LLM 이 아니라 MockLLM** 으로 돈 것이다.
```

### 29.6 사람의 역할

가중치 값 자체는 건드리지 않는다. 대신 다음을 본다.

**가중치 민감도** — 좌표 하강으로 각 `w[i]` 를 ±50% 흔들었을 때
regret 변화를 잰다.
- 0 으로 수렴하거나 둔감한 항 → 그 피처는 쓸모없다. 정리 대상
- 아주 민감한 항 → 그 물리량이 지배적이다. 진단 리포트에 넣을 정보

**GPU 간 가중치 변화** — 어떤 항이 아키텍처마다 크게 달라지는가.
그것이 "세대 고유" 부분이며, **물리적으로 설명이 되는지 확인해야 한다.**
설명이 안 되면 그 항은 암기일 가능성이 있다.

예상되는 것: Hopper 는 TMA 로 메모리 지연 은닉이 잘 되므로
`smem_pressure` 가중치가 Ampere 보다 작아질 것이다. 이런 예측을
미리 적어두고 결과와 대조하라.

## §30. 노이즈 바닥과 형상 크기 — 실측 확정

> A6000 33시간 캠페인(`c63710df`)의 앵커 12개 x 312회 재측정으로 확정.
> **원 문서 §7.2 의 "정답은 1% 이내 집합" 은 틀렸다.**

### 30.1 무엇이 잘못됐었나

원 설계는 정답 집합 허용치를 고정 1% 로 잡았다. 근거는 "재현성
median 0.05% / max 0.35%" 였는데, 그 숫자는 **조합 8개 x 4회, 다른
`env_hash`(리허설 조건)** 에서 나온 것이었다. 공개 데이터셋에 대한
재현성 측정이 아니었다.

캠페인 자체에서 다시 재보니 **형상 크기에 따라 35배 차이**가 난다.

```
> 1 ms   (1.50~2.92 ms)   상대 표준편차 0.044%
< 0.1 ms (14~56 µs)       상대 표준편차 1.541%   변동폭 최대 7.14%
```

고정 1% 를 쓰면:
- **큰 형상**: 노이즈(0.044%)의 23배를 허용 -> 실제 차이를 정답으로 뭉갬
- **작은 형상**: 노이즈(1.5%)보다 작은 허용치 -> **노이즈를 신호로 학습**

두 번째가 치명적이다.

### 30.2 모델 — 두 항의 최댓값

```
noise_floor(t) = max( sigma_rel(t),  tick_pct(t) )

sigma_rel(t) = a / t + b       a = 0.000374 [ms],  b = 0.00044   (통계)
tick_pct(t)  = tick / t        tick = 0.001024 [ms]              (분해능)
```

| t | `sigma_rel` | `tick_pct` | 지배 |
|---:|---:|---:|---|
| 14 µs | 2.72% | **7.31%** | 분해능 |
| 56 µs | 0.71% | **1.83%** | 분해능 |
| 500 µs | 0.12% | **0.21%** | 분해능 |
| 1.5 ms | 0.069% | 0.068% | 비슷 ← **경계** |
| 4 ms | **0.053%** | 0.026% | 통계 |

**두 항은 성격이 다르다.**

`a/t` 는 **통계적** 지터다. 앵커의 절대 sigma 가 커널 시간과 무관하게
0.26~0.47µs 로 나오는 것이 직접 증거이며, 타이머 해상도와 런치 경로
비용이다.

`tick/t` 는 **분해 한계**다. CUDA 이벤트 타이머의 양자이고, 이보다
작은 차이는 **측정으로 구분할 수 없다.** 같은 눈금에 떨어진 두 config 는
시간이 **문자 그대로 동일**하게 기록된다. `512x512x512` 에서는 최적이
11.26µs 라 눈금이 **9.09%** 이고, 최빈값 하나에 612개(9.2%)가 몰린다.

**분해능 항을 빼면 짧은 커널에서 모델이 과소평가한다.** 14µs 에서
2.7% 기준으로 "구분된다" 고 판정하면 **없는 순위를 만든다.**

### 30.2b 눈금이 판정을 두 방향으로 망가뜨린 실제 사례

kernelTab 이 같은 물리에 **반대 방향으로 두 번** 속았다.

```
R-6     라운드 추이를 중앙값으로 판정
        → 8라운드가 전부 정확히 +0.000%  → 검사가 죽어 있었다

G-7     슬라이스 start→end 를 중앙값으로 판정
        → -6.49% (= 눈금의 0.84배)      → 없는 냉시작을 만들어냈다
```

두 번째가 특히 위험했다 — **워밍업을 줄인 직후**라 "정확히 우려하던
자리" 였고, 그대로 믿었으면 개선을 되돌렸을 것이다.

`start` 값이 전부 정확히 같았던 것(13.312 × 4)이 양자화의 서명이다.
열이나 캐시 거동이면 그럴 수 없다.

**규칙:** 짧은 커널의 중앙값 차이를 % 로만 보지 마라.
```
차이가 눈금 미만이면      → 분해 불가. 평균으로 다시 보거나 판정 보류
중앙값이 모두 동일하면    → "안정" 이 아니라 "둔한" 것일 수 있다
```

**이것은 모듈 누적 드리프트가 런치당 상수(42µs/1,000모듈)였던 것과
같은 구조다.** 짧은 커널이 고정 비용에 지배당한다는 성질이 두 현상에서
반복된다. 다른 GPU 에서도 형태는 같고 계수만 다를 것이다.

**계수는 강건 추정으로 맞춘다.** 최소제곱은 이상치 하나에 끌려 작은
커널 노이즈를 40% 과대평가했다. 그리고 **허용치는 과소평가가 위험하고
과대평가는 안전하다** — 과대평가하면 정답 집합이 넓어져 규칙에
관대해질 뿐이지만, 과소평가하면 노이즈를 신호로 학습한다.

### 30.3 구현

계수는 `BUNDLE.json` 의 `noise_floor` 에 실려 있다. **재계산하지 말고
읽어 써라.** GPU 마다 다르다.

**kernelTab 이 이미 `kerneltab.core.noise` 로 제공한다. 재구현하지 말고
import 하라.** 함수가 둘로 나뉘어 있고 용도가 다르다:

```python
from kerneltab.core.noise import sigma_rel, noise_floor, tick_pct, resolvable

sigma_rel(t)    # 통계 모델만. 관측 산포와 비교할 때
noise_floor(t)  # max(통계, 분해능). "두 값을 구분할 수 있는가"
```

**한 함수로 뭉개지 마라.** 정답 집합에는 분해능이 필요하고, 노이즈
모델 검증에는 통계만 필요하다.

**`answer_set(p, tol=None)` 의 기본값은 `None` 이어야 한다.**
고정 1% 를 기본값으로 두면 아무도 안 바꾸고 또 뭉갠다.
kernelTab 의 `answer_set` 은 `2.0 * noise_floor(best)` 를 쓴다.

> **2σ 를 쓰는 이유** — 정답 집합은 "이 config 를 골랐다고 벌점을 줄
> 수 있는가" 를 정한다. 1σ 면 노이즈로 정답이 오답이 되는 경우가 32%,
> 2σ 면 5% 다. §30.2 의 원칙대로 **과대평가가 과소평가보다 안전**하므로
> 2σ 를 택했다. 바꾸려면 근거를 남겨라.

**테스트로 고정하라:**
```python
def test_15us_kernel_cannot_resolve_one_percent():
    """15µs 커널에서 노이즈 바닥이 1% 를 넘는다 (실측 7.31%).
    고정 1% 로 되돌아가면 이 테스트가 걸린다."""
    assert noise_floor(0.015) > 0.01

def test_tick_dominates_below_1_5ms():
    """1.5ms 가 경계다. 그보다 짧으면 분해능이 통계를 넘는다."""
    assert tick_pct(0.014) > sigma_rel(0.014)
    assert tick_pct(4.0)   < sigma_rel(4.0)
```

### 30.3b ★ 번들 스키마 버전 — 개발용 번들은 v1 이다

**개발에 쓸 12.4 번들(`rtx-a6000-sm_86-c63710df`)은 `schema_version: 1`
이고 `tick_ms` 가 없다.** 눈금 항이 그 번들 생성 이후에 추가됐다.

```
schema_version 1   noise_floor(t) = sigma_abs_ms/t + sigma_rel
                   table.parquet 96컬럼. distinct_time_frac 없음
schema_version 2   noise_floor 에 tick_ms 포함
                   table 에 distinct_time_frac / n_distinct_times 포함
```

`load_bundle` 이 부재를 감지하면 A6000 관측치로 대체하고 **경고한다.**
그 경고를 무시하지 마라 — **다른 GPU 의 v1 번들에는 그 대체값을 쓰면
안 된다.**

`schema_version` 뿐 아니라 **`table_columns`** 도 확인하라. 버전이
같아도 `export` 시점이 다르면 컬럼이 다를 수 있다. 버전은 "무엇이
들어갈 수 있는가", `table_columns` 는 "실제로 무엇이 들어있는가" 다.

### 30.4 평가 보고 — 세 갈래로 나눈다

난이도 층화(§7.3)에 더해 **크기 층화**도 필요하다.

```
전체
t_best >= 0.5 ms   (순위를 신뢰할 수 있는 형상)   A6000: 21/66
t_best <  0.5 ms   (노이즈가 지배. 참고용)        A6000: 45/66  ★
```

**66형상 중 45개가 0.5ms 미만이다.** 소수가 아니라 다수다.
그 구간의 regret 차이를 전체 평균에 섞으면 결론이 흐려진다.

**그리고 여지가 거의 전부 거기에 있다** (§30.5):
```
정적 top-1   t >= 0.5ms  ->  1.021    사실상 여지 없음
             t <  0.5ms  ->  1.164    여기가 전부다
```
**측정으로 확인하기 가장 어려운 구간에 개선 여지가 몰려 있다.**
이 긴장을 인식하고 보고하라 — 짧은 형상의 regret 개선은 실력일 수도
있고 노이즈일 수도 있으며, 그 판정에 §30.2 의 노이즈 바닥이 쓰인다.

실측 분포:
```
최적시간  중앙 0.259ms   최소 0.0113ms(눈금 9.06%)   최대 9.7ms
< 0.1 ms 형상  11/66
< 0.5 ms 형상  45/66
```

### 30.4b 계측 분해능을 지표로 — `distinct_time_frac`

난이도(중앙값/최적)와 **다른 축**이 필요하다.

```
난이도 낮음            실제로 성능이 비슷하다        (물리)
distinct 비율 낮음     측정이 구분을 못 한다          (계측)
```

kernelTab 이 `schema_version 2` 부터 표에 싣는다:
```
n_distinct_times / n_candidates
예: 1x12288x4096 -> 1,638 / 12,213 = 0.134
```

**둘 다 `ANSWER_COLS` 에 있다.** 규칙이 이걸 보면 "여기선 대충 해도
된다" 를 학습한다 — 배포 시점에는 알 수 없는 값이다.

이 층화는 이미 나온 관찰들과 맞물린다:
```
1x12288x4096   5% 이내 config 2,501개.  서로 다른 값 1,638/12,213
512x512x512    최적 11.26µs, 눈금 9.09%. 최빈값 하나에 612개(9.2%)
1x4096x4096    옛 tol 1.35% 로는 정답 1개, 눈금 반영 시 148개
M=1/8 형상     난이도 1.11~1.15 (선택이 거의 무의미)
```

**"작은 형상에서 순위가 흐릿하다" 가 세 방향에서 확인됐다** — 난이도,
순위 안정성, 측정 분해능. 세 번째가 앞 둘의 원인 일부다.

다만 **주원인이 항상 눈금은 아니다.** `1x12288x4096` 은 156.67µs 라
눈금이 0.65% 뿐이고, 5% = 7.6눈금이다. 그 형상의 2,501개는 눈금 충돌이
아니라 실제 성능 유사성이다. **형상마다 확인하라.**

### 30.5 k=1 과 k>=3 은 다른 시나리오다

> ⚠️ **이 절의 이전 판(1.394 / 1.553 / 1.256)은 틀렸다.** 측정 상태 필터
> 하나가 만들어낸 인공물이었다. 경위는 §30.5b 에 남긴다. 아래가 정본이다.

**정적 top-k — 정본 절차** (a888 61형상, `status` 전체 포함, **합집합 덮개**):

| k | 전체 | 어려운 절반 | 쉬운 절반 | t≥0.5ms | **t<0.5ms** |
|---:|---:|---:|---:|---:|---:|
| **1** | **1.115** | 1.099 | 1.132 | 1.021 | **1.164** |
| 2 | 1.052 | 1.042 | 1.062 | 1.021 | 1.067 |
| 3 | 1.031 | 1.034 | 1.028 | 1.007 | 1.043 |
| 5 | 1.015 | 1.009 | 1.020 | 1.002 | 1.021 |
| 8 | **1.006** | 1.004 | 1.008 | 1.002 | 1.007 |

**★ 난이도 층화보다 크기 층화가 훨씬 더 많이 갈린다.**
```
k=1  난이도 상/하   1.099  vs  1.132     차이 0.03
k=1  크기 >=/<0.5ms  1.021  vs  1.164     차이 0.14   <- 5배
```

**고정 config 의 손해는 거의 전부 0.5ms 미만 형상에서 온다.**
그런데 그 구간이 정확히 **측정 분해능이 가장 나쁜 곳**이다 (§30.2).
kernelRule 이 노릴 여지와 측정으로 확인할 수 있는 여지가 어긋나 있다는
뜻이고, 이것이 이 프로젝트의 가장 큰 긴장이다. §30.4 의 크기 층화를
난이도 층화보다 **우선해서** 보고하라.

`regret@k` 는 **"규칙이 낸 상위 k개 중 가장 빠른 것"** 이므로 k개를
실제로 컴파일·측정해야 얻는 값이다.

```
k >= 3   빌드타임 오토튜닝.  형상 무관 고정 8개면 0.6% 손해.
         ★ 여지가 없다. 이 시나리오는 이미 해결되어 있다.
         그리고 이것 자체가 보고 가치 있는 결과다.

k = 1    런타임 디스패치.    측정할 수 없는 상황.
         MoE grouped GEMM, 가변 배치, 서빙 critical path.
         ★ 여지 11.5%. 여기가 이 연구의 자리다.
```

**k=1 을 주 지표로 삼는다.** k>=3 은 대조로만 보고한다.

**층화는 k=1 에서만 필요하다.** k>=3 에서는 어느 층으로 갈라도 차이가
사라진다. 그리고 k=1 에서는 **크기 층화를 우선**하라 (위 표).

### 30.5b 정본 절차와, 이전 값이 틀렸던 경위

`status` 필터와 덮개 정의를 어떻게 잡느냐로 답이 세 갈래로 갈린다.

| 절차 | k=1 | k=3 | k=8 |
|---|---:|---:|---:|
| `ok` 만 + 개별 전덮개 | 1.394 | 1.383 | **1.383** ← 포화 |
| `ok` 만 + 합집합 덮개 | 1.394 | 1.060 | 1.009 |
| **전체 + 합집합 덮개 (정본)** | **1.115** | **1.031** | **1.006** |

**(1) `status` 필터.** `high_outlier_frac` 은 그 **측정 한 건**의 속성이지
config 의 성질이 아니다. 반복 수가 많을수록 IQR 밖 하나가 걸릴 확률이
커질 뿐이고(n_reps=5 에서 10%, 1000 에서 37%), 시간 중앙값은 유효하다.

`ok` 만 남기면 **"모든 형상에서 우연히 깨끗한 측정이 나온 config"** 를
요구하게 된다. 61형상 전부에서 ok 인 config 가 17,325개 중 **3개**만
남고, 그리디가 그 셋 중에서 고르니 k≥3 이 1.383 에 포화한다.

**(2) 덮개 정의.** 개별 config 가 61형상 전부에서 유효할 것을 요구하면
`split_k>1` 이 사실상 배제된다 — `split_k=3` 은 K 가 3의 배수인 형상에서만
유효하기 때문이다. 실제 라이브러리는 그런 config 를 당연히 포함하고,
형상마다 그중 유효한 것을 쓴다. **k개의 합집합이 덮으면 된다.**

**(3) 이전 판이 두 절차를 섞었다.** k=1 행은 첫 번째 절차에서 나왔는데
k≥3 행은 같은 절차에서 1.383 이 나온다. 서로 다른 계산의 결과가 한 표에
들어가 있었다.

**구현 지침:** `baselines/static_topk.py` 는 **세 절차를 전부 계산해
병기**하고, 정본을 명시하라. 단일 숫자로 보고하지 마라. §9.1 이 경고한
클래스("미측정에 벌점을 주면 구조적 사실이 regret 으로 둔갑한다")가
반대 방향으로 나타난 사례다.

#### strict vs nearest — 벤더 품질이 아니라 **정의 차이**다

두 값이 다른 형상은 **3/61 뿐이고**, 그 셋이 격차 전부를 만든다.

```
128x4096x16384    1.161 -> 2.803   벤더 split_k=5  -> 최근접 sk6
1024x4096x128     1.115 -> 1.385   벤더 stages=1   -> 최근접 st2
1024x4096x16384   1.078 -> 1.250   벤더 split_k=5  -> 최근접 sk6
```

1순위 매핑 성공률은 95.1%(58/61)이고, **정확 매핑된 것의 rel 기하평균
1.1137 과 최근접 대체 1.1176 이 사실상 같다.** 즉 최근접 대체가 벤더보다
낫거나 나쁜 것이 아니다.

차이는 **매핑 실패를 어떻게 처리하는가**에서 온다. kernelTab 은 그 형상을
채점에서 제외했고(덮개 82%), kernelRule 은 2순위를 top-1 로 승격시킨다.
승격 쪽이 더 불리하다. **`nearest` 가 기본값이고 관문은 1.080 이다.**

#### ★ 매핑 실패의 원인은 축 값 두 개다

벤더 추천 468건(61형상 x top-8) 중 31건(6.6%)이 우리 공간에 없다.

```
split_k = 5   16건   우리 축 [1,2,3,4,6,8,12,16] — 4와 6 사이가 비었다
stages  = 1   13건   우리 축 [2..8] — 최소 파이프라인이 2단이다
```

나머지 축(tile / warp / swizzle / mode)의 실패건 값은 **전부 우리 축에
존재하는 값**이다. 조합이 아니라 **축 값 두 개**가 원인이다.

**K 양극단에 몰린다.**

```
K=16384  11건    K=128  8건    K=256  5건    K=11008  5건
K=4096    2건  <- 지배적 중간 구간은 거의 실패가 없다
짧은 형상 9.1% (28/308) vs 긴 형상 1.9% (3/160)
```

물리적으로 말이 된다. K 가 아주 크면 벤더가 `split_k=5` 를 원하고(우리 4와
6 사이), K 가 아주 작으면(128, 256) `stages=1` 을 원한다 —
`K/tile_k = 4` 회짜리 mainloop 에는 2단 파이프라인도 깊다.

**이것은 벤더의 약점이 아니라 kernelTab 탐색 축의 덮개 한계다.**
`pending_fixes.md` C-3 으로 보고했고, 일반화된 절차를 제안했다:
**측정 전에 벤더 추천을 전 형상에 대해 뽑아 축 덮개를 점검하라.**
GPU 없이 30분이면 되고, 33시간 측정의 축이 비어 있는 것을 미리 막는다.

**GBDT 피처 중요도** (진단 리포트 §12.1 블록 3.5 에 넣어라):
```
mainloop_iters, workspace_bytes, waves_occ, grid_tiles,
inst_total, tile_m, regs_total_per_block, bytes_moved, split_k
```
`inst_total`(SASS 명령어 수)과 `workspace_bytes`(split-K parallel 의
리덕션 트래픽)가 상위인데 **손규칙은 둘 다 쓰지 않았다.** LLM 이
발견해야 할 것의 힌트다.

다만 **"이 피처를 쓰라" 고 지시하지 마라.** 어떤 물리량이 설명력을
갖는지의 힌트로만 주고, 어떻게 쓸지는 LLM 이 찾게 하라.

### 30.6b ★ 관문을 다시 세운다

원 문서 §9.2 는 **정적 top-k 를 관문**으로 삼았다. "형상 의존성이
존재하는가" 를 묻기 위해서였다. **그 질문은 이미 답이 나왔다 —
존재하지만 3.5%p 다.** 정적 top-1 을 이기는 것은 이제 낮은 기준이다.

**관문을 벤더 휴리스틱으로 바꾼다.**

```
벤더 (nearest, a888 61형상 전체)      1.080   ← 헤드라인 관문
                                     strict 1.102 병기
GBDT 상한 (짧은 형상 블록 8분할)        1.044 기하평균 / 1.085 최악
현재 손규칙                           1.172
```

판정:
```
규칙이 벤더(1.080)를 못 이긴다              -> 방향 재검토
벤더는 이기는데 GBDT(1.044)에 못 미친다      -> 정상. 그 격차를 좁히는 것이 연구
GBDT 에 근접한다                            -> 성공. 전이 실험으로 넘어간다
```

**★ 판정은 분할별로 한다.** 세 방법을 같은 홀드아웃에서 비교하지 않으면
숫자가 짝이 안 맞는다. `baselines/` 리포트는 **분할 x 방법 표를 기본
출력**으로 낸다. 스칼라 하나로 요약하지 마라. (§30.6c)

**주의 1:** 이 숫자들은 **CUDA 12.4 / 호스트** 캠페인의 것이다.
본 캠페인(CUDA 13.3 / 컨테이너)에서 다시 측정하면 달라질 수 있다.
개발 단계에서는 이 값을 기준으로 쓰되, **보고할 때는 본 캠페인 값을 쓴다.**
이 대조 자체가 실험이다 (§30.9).

**주의 2:** 전이(4090/H100)에서도 유지되는지가 이 연구의 진짜 시험대다.

### 30.7 ★ 채점 하네스의 정답 누출 — 실제로 발생했다

베이스라인 실험 중 발견된 버그다. **kernelRule 채점기에 같은 것이
없도록 하라.**

```python
# 잘못 — 동점일 때 시간으로 정렬해 정답을 훔쳐본다
ranked = sorted([(score[c], time[c], c) for c in candidates])

# 맞음 — tie-break 가 정답과 무관해야 한다
ranked = sorted(candidates,
                key=lambda c: (score[c], c.kernel_id, c.split_k))
```

**정답이 tie-break 에 들어가는 경로를 구조적으로 차단하라.**
채점기가 받는 자료구조에서 시간을 분리하면 물리적으로 불가능해진다.

**테스트:**
```python
def test_constant_score_gives_random_performance():
    """모든 config 의 score 를 상수로 만들면 regret 이
    무작위 선택과 동등해야 한다 (1.0 근처가 아니라)."""
```

이것이 §22.5 `null` 프리셋 테스트와 함께 누출을 잡는 두 장치다.

### 30.9 툴체인 민감도 — 두 표가 생기면 할 실험

kernelTab 이 같은 A6000 을 두 조건에서 잰다:
```
캠페인 1   CUDA 12.4 / 호스트     ← kernelRule 개발용
캠페인 2   CUDA 13.3 / 컨테이너   ← 본편
```

**두 표가 다 있으면 아키텍처 전이보다 먼저 답이 나오는 질문이 있다.**

```
12.4 로 만든 규칙  →  13.3 표로 채점  →  regret 이 얼마나 나빠지는가

1.19 근처 유지  ->  "한 번 만든 규칙을 오래 쓴다" 성립
크게 나빠짐     ->  "표의 유통기한이 짧다"
```

**GBDT 에도 같이 하라.** GBDT 는 12.4 데이터에 더 밀착되어 있으므로
규칙보다 더 무너질 것으로 예상된다. 그렇다면 그것이 **"해석 가능한
규칙이 학습 모델보다 강건하다"** 는 직접 증거이고, kernelRule 의
존재 이유를 하나 더 만든다.

반대로 GBDT 도 잘 버티면 그것도 보고할 사실이다.

**한계를 명시하라:** 두 캠페인은 CUDA 버전과 컨테이너 유무가 동시에
바뀐다. 두 변수를 분리할 수 없다. 다만 "실무에서 환경을 통째로
옮겼을 때" 에 해당하므로 해석은 가능하다.

이미 알려진 것: CUDA 13 은 **드리프트를 고치지 않았다.** 문턱이
1,154 → 962/1,051 로 오히려 낮아졌고 기울기만 완만해졌다.
컴파일러가 바뀌면 레지스터 배치가 미세하게 달라지므로(200개 표본에서
>2 변화 11건) **표는 재측정 대상이다.**

### 30.8 이 발견에서 얻은 메타 교훈

kernelTab 이 같은 클래스의 버그를 반복해서 만났다.

```
"조용히 아무것도 안 하는 안전장치"   4회
"env_hash 격리 위반"                5회
```

**둘 다 문서에 교훈을 적은 뒤에도 반복됐다.**

> **문서로 적은 규율은 지켜지지 않는다.**
> 규율을 정할 때마다 "이것을 코드로 강제할 방법이 있는가" 를 먼저 묻고,
> 없으면 그 규율은 지켜지지 않을 것이라고 전제하라.

강제 수단:
```
타입/시그니처로 불가능하게        기본값 없는 필수 인자 -> TypeError
키에 강제 포함                    집계 함수가 env_hash 를 키에 넣는다
테스트가 호출부까지 검사           헬퍼 존재가 아니라 사용을 검사
감시에 감시                       메타 테스트로 감시가 작동하는지 확인
기본값을 안전한 쪽으로             tol=None. 고정값을 기본으로 두지 않는다
```

**"헬퍼만 만들고 문서에 '이걸 쓰세요' 를 적는 것은 강제가 아니다."**

### 30.8b 이 문서 자체가 같은 병에 걸렸던 사례

§30.5 의 정적 top-k 표(1.394 / 1.553 / 1.256)는 **검증 없이 옮겨 적은
숫자**였다. 그리고 그 표 안에서 k=1 행과 k≥3 행이 서로 다른 절차의
결과였는데, **표 하나로 보이니 아무도 의심하지 않았다.**

발견된 것은 kernelRule 구현자가 **재현을 시도했을 때**다.

> **규칙:** 관문이 되는 숫자는 **재현 절차를 명시**하라. 그리고 다른
> 사람이 재현했을 때 값이 다르면, 그것은 그 사람의 실수가 아니라
> **절차가 명시되지 않았다는 증거**로 먼저 취급하라.

`baselines/` 의 모든 숫자에 다음을 함께 기록하라:
```
status 필터 / 덮개 정의 / 형상 집합 / 후보 집합 / 계산 코드의 커밋
```

#### ★ 세 번째 뿌리 — **집계 방식이 다른 두 값을 나란히 놓는 것**

요약 통계를 비교할 때는 **집계 방식이 같은지 먼저 확인하라.**

kernelRule 2단계에서 GBDT 상한을 이렇게 적으려 했다.

```
GBDT 최악  1.085   <- 8개 분할 중 최악
벤더 관문  1.080   <- 분할 없는 전체값
```

붙여 놓으면 "GBDT 가 벤더보다 나쁘다 = 여지가 없다" 로 읽힌다.
**짝을 맞추면 정반대다.**

```
기하평균   GBDT 1.044  vs  벤더 1.101     격차 0.057
최악      GBDT 1.085  vs  벤더 1.118     격차 0.033
```

이 병은 이 프로젝트에서 **세 번째** 형태다.

| | 무엇이 어긋났나 |
|---|---|
| §30.5b | k=1 행과 k>=3 행이 **다른 절차**로 계산됐다 |
| §30.8b | "무엇의 비율인가" — 분자와 분모의 **경계**가 달랐다 |
| **여기** | **집계 방식**(최악 vs 전체값)이 달랐다 |

#### ★ 네 번째 뿌리 — **다른 데이터의 결론을 이 데이터에 복사하는 것**

§30.5 가 "크기 층화가 난이도 층화보다 5배 더 갈린다" 를 확립했다.
그것을 진단 리포트 템플릿에 문장으로 박아 뒀는데, **학습 분할에서는
반대였다** (크기 격차 0.0007 vs 난이도 격차 0.1651). 그 분할에 긴 형상이
9개뿐이었기 때문이다.

전역에서 참인 관측이 **부분집합에서 거짓**이 될 수 있다. 리포트가 자기
데이터와 모순되면 그것을 읽는 쪽(LLM 이든 사람이든)은 데이터가 아니라
문장을 믿는다.

```
규칙: 두 숫자를 나란히 쓰거나 비교를 서술하기 전에 넷을 확인한다.
      (1) 같은 절차인가
      (2) 같은 분모인가
      (3) 같은 집계 방식인가
      (4) ★ 그 서술이 **이 데이터에서 계산된 것**인가,
             다른 데이터의 결론인가
      기하평균과 최악을 병기할 때는 **모든 방법에 대해** 병기한다.
```

(4)는 `tests/test_diagnostic.py` 가 두 겹으로 강제한다 — 템플릿의 리터럴
비교어를 정적으로 막고, 반대 데이터에서 문장이 뒤집히는지 행동으로 본다.

kernelRule 에서 특히 위험한 지점 (§26.4 와 함께 보라):
- 정답 누출 방지가 환경에 따라 스킵되는가 (§26.3)
- 정적 검사가 파싱 실패 시 조용히 통과하는가
- 피처 검증이 예외를 삼키고 승인하는가
- 노이즈 바닥을 계산할 수 없을 때 0 을 반환하는가
