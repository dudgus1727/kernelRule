# kernelRule — 시스템 설계

> 이 문서는 구현자(사람 또는 Claude Code)가 읽고 **일관되게 구현할 수 있도록**
> 쓰였다. 결정된 것과 열려 있는 것을 구분해 표시했다. `[열림]` 표시가 없는
> 항목은 결정된 것이며, 바꾸려면 이유를 문서에 남겨야 한다.
>
> 짝이 되는 저장소: **`kernelTab`** (측정 하네스, 표를 만드는 쪽).
> 이 문서는 그 표를 **소비하는** 쪽을 다룬다.

---

## 0. 한 문단 요약

성능 표에서 **GEMM config 선택 규칙을 자동으로 만들어내는 파이프라인**이다.
LLM이 규칙 코드를 쓰고, 미리 측정된 표가 채점하고, 진화 루프가 반복한다.
LLM은 규칙을 **만드는 도구**이지 최종 시스템의 일부가 아니다. 배포되는
산출물은 마이크로초 단위로 도는 순수 파이썬 함수와, 그 함수가 왜 그렇게
생겼는지의 기록이다.

```
입력   kernelTab 번들 (table.parquet + env.json + kernels.jsonl + BUNDLE.json)
출력   rank(problem, hw, candidates) -> 순서 매겨진 config 목록
       + features.py (검증된 물리 피처 라이브러리)
       + 가설 이력 (규칙이 그렇게 생긴 이유)
```

## 1. 목적과 비목적

### 1.1 목적

1. **표에서 규칙을 뽑아내는 기계를 만든다.** 특정 규칙이나 특정 표가
   아니라 파이프라인 자체가 산출물이다.
2. **그 규칙이 일반화되는지 검증한다.** 안 본 형상, 안 본 dtype,
   **안 본 아키텍처**에서 동작하는가. 이것이 선행연구와의 주된 차별점이다.
3. **휴리스틱 제작 비용을 낮춘다.** "NVIDIA보다 정확하다"가 아니라
   "사람 몇 주가 걸리던 것을 하룻밤에"가 주장이다.

### 1.2 비목적 — 하지 않는 것

- **커널 코드 생성.** LLM에게 CUDA/CUTLASS를 짜게 하지 않는다.
  그건 KernelBench/Astra/CuTeGen 계열의 붐빈 영역이고 다른 문제다.
- **런타임 LLM 호출.** 배포된 규칙은 LLM을 부르지 않는다.
  서빙 critical path에서 밀리초도 쓸 수 없다.
- **절대 성능 예측.** 규칙은 **순위**만 매긴다. 시간을 예측하지 않는다.
- **CUTLASS/cuBLAS를 이기는 것 자체.** 그것이 부수적으로 일어날 수는
  있으나 주장의 근거로 삼지 않는다.

### 1.3 성공 조건

```
필수: 정적 top-k 베이스라인을 유의미하게 이긴다        (아래 §9 관문)
필수: 손으로 쓴 30줄 분석 휴리스틱을 이긴다
핵심: A6000+4090으로 학습한 규칙이 H100에서 동작한다   (아키텍처 홀드아웃)
```

## 2. 핵심 개념 — 세 가지를 혼동하지 말 것

이 프로젝트에서 가장 흔한 혼동이다. 명확히 구분한다.

| | 형태 | 실행 가능 | 개수 | 만드는 주체 | 저장 위치 |
|---|---|---|---|---|---|
| **가설** | 자연어 문장 | 아니오 | 기록용 누적 | LLM (Diagnostician) | `hypotheses.jsonl` |
| **피처 함수** | 코드 → float | 예. **판단 안 함** | 20~30개, 천천히 | 주로 사람, 가끔 LLM | `features/` |
| **규칙 함수** | 코드 → 순서 | 예. **판단함** | 수백~수천, 대부분 폐기 | LLM (Optimizer) | `rules/` |

### 2.1 예시로 관통하기

**가설** (자연어, 실행 불가):
> "M=1024, N=1024 형상에서 타일이 64개인데 SM이 84개라 SM의 4분의 1이
> 논다. 규칙이 split-K를 항상 1로 두기 때문에 이 낭비를 못 없앤다."

**피처** (개념을 숫자로 — 좋고 나쁨을 판단하지 않는다):
```python
def tail_waste(p: Problem, hw: Hardware, cfg: Config) -> float:
    """마지막 wave에서 노는 SM 슬롯의 비율. 0~1, 클수록 나쁨."""
    tiles = ceil(p.M / cfg.tile_m) * ceil(p.N / cfg.tile_n) * cfg.split_k
    waves = tiles / hw.sm_count
    full = ceil(waves)
    return (full * hw.sm_count - tiles) / (full * hw.sm_count)
```
→ M=N=1024, 128×128 타일, sk=1 이면 **0.238**

**규칙** (피처를 재료로 판단):
```python
def rank(p: Problem, hw: Hardware, candidates: list[Config]) -> list[Config]:
    def score(cfg: Config) -> float:
        s  = F.tail_waste(p, hw, cfg) * 2.0
        s += F.smem_pressure(p, hw, cfg) * 0.5
        if F.is_memory_bound(p, hw):
            s += F.tile_bytes_ratio(p, hw, cfg) * 1.5
        return s
    return sorted(candidates, key=score)
```

### 2.2 왜 피처와 규칙을 분리하는가

한 줄로 다 쓸 수도 있다. 동작은 같다. 그런데:

1. **틀렸을 때 분해가 안 된다.** regret 1.14일 때 wave 계산식이 틀린
   건지 가중치 2.0이 잘못된 건지 구분할 수 없다.
2. **LLM이 매번 같은 계산을 다시 짠다.** 그리고 매번 조금씩 다르게
   짠다. 어떤 버전은 `split_k`를 빼먹고 어떤 버전은 `ceil`을 안 쓴다.
   **진화 과정에서 버그가 섞여 들어가는 주된 경로다.**
3. **재사용이 안 된다.** `tail_waste`는 한 번 만들면 모든 규칙이 쓰고,
   아키텍처가 바뀌어도 `hw.sm_count`만 달라진다. 인라인이면 전이
   실험 때 규칙마다 다 고쳐야 한다.

### 2.3 규칙은 가설들의 누적이다

```
r3   가설 H1  "waves<1에서 split-K를 안 본다"    -> tail_waste 항 추가
r8   가설 H4  "메모리 바운드에서 타일이 크다"      -> 조건부 분기 추가
r15  가설 H9  "smem을 꽉 채워 occupancy 하락"     -> smem_pressure 항 추가
```

r15의 규칙에는 H1, H4, H9가 모두 들어있다. **가설이 국소적인 것은
의도다** — 한 번에 하나만 바꿔야 인과를 알 수 있다. 국소 수정의 부작용은
전역 채점이 잡는다.

**좋은 수정과 나쁜 수정:**
```python
# 나쁨 — 조건부 특수화. 반복되면 룩업 테이블이 된다.
if F.waves(p, hw, cfg) < 1:
    s += F.tail_waste(...) * 5.0

# 좋음 — 연속적 통합. tail_waste가 waves 큰 형상에서 자연히 0에 가깝다.
s += F.tail_waste(...) * 2.0
```
§8.3의 정적 제약(리터럴 개수, AST 검사)이 이를 강제한다.

## 3. 절대 규칙 — 정답 격리

### 3.1 규칙 함수는 표를 볼 수 없다

```
피처:  (형상, config)       -> float          표 접근 불가
규칙:  (형상, config 목록)   -> 정렬된 목록     표 접근 불가
채점기: 규칙 + 표            -> regret         표 접근 가능
```

규칙이 표를 볼 수 있으면 정답을 베끼면 되므로 아무것도 배우지 않는다.
그리고 배포 시점에는 표에 없는 형상이 들어온다.

### 3.2 kernelTab이 제공하는 강제 장치

`kernelTab/core/table.py`가 이미 이를 구조적으로 막는다. **반드시 이 두
로더만 쓴다.**

```python
from core.table import load_for_ranking, load_for_scoring, assert_no_answers

X = load_for_ranking(path, env_hash="...")   # 정답 제거됨. 규칙 입력용
y = load_for_scoring(path, env_hash="...")   # 조인 키 + 정답. 채점기만
```

`load_for_scoring`이 피처를 함께 주지 않는 것은 의도다 — 반환값을 그대로
규칙에 넘기는 사고를 막는다.

**제거되는 컬럼** (`ANSWER_COLS`):
```
time_ms  time_std_ms  time_min_ms  time_max_ms  n_reps  outlier_frac
cublas_ms  tflops  frac_of_peak  vs_cublas  difficulty
```

`difficulty`가 여기 있는 이유: "이 형상은 어려우니 신중하게"를 규칙이
알면 정답을 훔쳐본 것이다. 평가 층화(§7.3)에만 쓴다.

**함께 제거되는 것** (`OUTCOME_COLS` — 측정해야 아는 값):
```
status  error  max_rel_error  actual_split_k
sm_clock_mhz  mem_clock_mhz  gpu_temp_c  power_w
soak_elapsed_s  drift_ratio  timestamp
```

**써도 되는 것**: 형상, config, **빌드 시점에 알 수 있는 커널 속성**
(`regs_per_thread`, `threads`, `smem_dynamic`, `spill_*`, `hmma_count`,
`max_blocks_per_sm`, `pipeline_kind`, `theoretical_occupancy`, `launchable`),
그리고 파생 물리 피처.

정적 분석 값을 허용하는 이유는 **커널을 빌드하기만 하면 알 수 있고
실행할 필요가 없기 때문**이다. 실무에서도 커널 캐시를 갖고 있으면 같은
정보를 얻는다.

### 3.3 데이터 구조 수준의 방어

`Problem` / `Config` / `Hardware` **어디에도 측정 시간을 넣지 않는다.**
표는 별도 딕셔너리에만 있고 `Config`에는 없으므로, 규칙 함수가 손댈
방법이 물리적으로 없다.

### 3.4 `env_hash`는 조인 키가 아니라 격리 경계다

kernelTab이 이 함정을 **세 번** 밟았다 (`difficulty` 22배 부풀림,
번들 통계 오염, 드리프트 경고 55%). 전부 "여러 조건이 섞인 데이터를
필터 없이 집계"였다. 그리고 **에러 없이 조용히 틀렸다.**

kernelRule에서도 같은 규율을 적용한다:
- 표를 읽을 때 `env_hash`는 **필수 인자**. 기본값 없음.
- 여러 조건을 의도적으로 합칠 때는 명시적 옵션으로만.
- 형상/조건 단위 집계는 조건별로 계산한다.

## 4. 저장소 분리와 데이터 계약

### 4.1 왜 저장소를 나누는가

| | kernelTab | kernelRule |
|---|---|---|
| 필요한 것 | CUDA, CUTLASS, GPU | CPU, Python, LLM API |
| 컨테이너 | 수 GB | 수백 MB |
| 실행 빈도 | 캠페인당 1회 | 계속 |
| 수명 | 표를 만들면 동결 | 계속 수정 |

한 저장소면 규칙 실험마다 CUDA 이미지를 끌고 다녀야 한다.

### 4.2 연결 지점 — 번들

```
datasets/{gpu_slug}-{arch}-{env_hash앞8}/
  table.parquet      측정 결과 (파생, 재생성 가능)
  env.json           ★ 없으면 해석 불가 (유효 peak/bandwidth/ridge)
  kernels.jsonl      커널 정적 속성
  manifest.json      코드/CUTLASS/CUDA 버전
  BUNDLE.json        체크섬 + 요약 메타 + 층별 형상 목록
  validate_report.md 무결성 검사 통과 기록
```

`kernelTab/core/bundle.py`의 `load_bundle()` / `load_bundles()`를 쓴다.
sha256을 대조하고, 여러 번들을 합칠 때 `common_shapes_only=True`를
지원한다.

### 4.3 다중 번들 결합 시 주의

**층 C의 형상은 GPU마다 다르다.** `hw.sm_count`에서 M을 역산하기
때문이다 (A6000 84 SM vs 4090 128 SM). 층 A/B/D/E는 공통이다.

```
공통 (직접 비교 가능):  층 A(워크로드), B(K변화), D(정렬), E(정방형)
GPU별 (비교 불가):      층 C(waves 역산)
```

전이 실험에서 이 구분이 없으면 **"규칙이 나빠서인지 형상이 달라서인지"
구분할 수 없다.**

**컬럼도 다르다.** SM90 번들에는 `ext_cluster_m` 같은 컬럼이 생기고
SM80 행에서는 null이다. **아키텍처 전이를 노리는 규칙은 `ext_*`를
쓰지 않는다.** 공통 필드(`tile_m/n/k`)와 파생 물리 피처만으로
`waves`, `tail_waste`, `mainloop_iters`가 계산되도록 설계되어 있다.

### 4.4 설치

```bash
pip install -e ../kernelTab   # core.table, core.bundle, core.features 사용
```

주의: kernelTab의 flat layout(`build` 이름 충돌)이 `kerneltab.*`
네임스페이스로 이전되기 전에는 `pip install`이 위험하다. 이전 전에는
`sys.path` 조작으로 import하고, 이전 후 정식 의존성으로 바꾼다.

## 6. 데이터 모델

### 6.1 핵심 타입

**뜨거운 경로이므로 frozen dataclass를 쓴다. Pydantic은 LLM 경계에서만.**

이유: 채점 루프에서 수백만 번 생성·해시된다. Pydantic v2는 생성마다
검증을 돌아 한 자릿수 느리다. 채점이 밀리초여야 이 시스템이 성립한다.

```python
from dataclasses import dataclass

@dataclass(frozen=True, slots=True)
class Problem:
    M: int; N: int; K: int
    dtype: str = "f16"
    acc_dtype: str = "f32"
    layout_a: str = "row"
    layout_b: str = "col"
    layout_c: str = "row"

@dataclass(frozen=True, slots=True)
class Hardware:
    name: str
    arch: str                 # "sm_86"
    sm_count: int
    smem_per_block: int
    max_threads_per_sm: int
    regs_per_sm: int
    peak_tflops_f16: float    # ★ 실효값 (클럭 고정 보정 후)
    bandwidth_gbps: float     # ★ 실효값 (P2 상태 관측 클럭 기준)
    l2_bytes: int

@dataclass(frozen=True, slots=True)
class Config:
    """규칙이 순위를 매기는 대상. 아키텍처 공통 필드 + ext."""
    # 공통 — 물리 피처가 이것만으로 계산되어야 전이가 성립
    tile_m: int; tile_n: int; tile_k: int
    align_a: int; align_b: int; align_c: int
    split_k: int
    split_k_mode: str         # "serial" | "parallel"
    arch: str
    # 빌드 시점에 알 수 있는 커널 속성 (써도 되는 것)
    regs_per_thread: int
    threads: int
    smem_bytes: int
    spill_bytes: int
    max_blocks_per_sm: int
    pipeline_kind: str        # "pipelined" | "multistage"
    kernel_id: str
    # 아키텍처 전용
    ext: dict                 # SM80: warp_m/n/k, stages, swizzle_type/n
```

**`Config`에 측정 시간이 없다는 것이 이 설계의 핵심이다.**

`ext`를 dict로 두는 이유: 아키텍처마다 필드가 다르고, 피처 함수는
어차피 `ext`를 보면 안 된다. dataclass로 만들면 오히려 접근을 부추긴다.

### 6.2 실효 하드웨어 값 (중요)

`peak_tflops_f16`와 `bandwidth_gbps`는 **스펙 값이 아니라 실효값**이다.

```
A6000 스펙:  154.8 TFLOP/s @1800MHz,  768 GB/s @8001MHz  -> ridge 201.5
A6000 실효:  116.1 TFLOP/s @1350MHz,  729.7 GB/s @7601MHz -> ridge 159.1
```

측정 시 SM 클럭을 1350으로 고정했고, 메모리는 컴퓨트 워크로드가 P2
상태로 돌아 7601이 상한이다. **이 보정을 안 하면 `is_memory_bound`
판정이 25% 어긋나 경계 근처 형상의 분류가 뒤집힌다.**

`kernelTab.core.hardware.hardware_from_env(env)`를 **유일한 진입점**으로
쓴다. `Hardware(**env["hardware"])`를 직접 쓰면 스펙 값이 들어온다.

## 7. 채점 코어

### 7.1 `PerfTable`

```python
class PerfTable:
    """(형상, config) -> 시간 조회.
    측정 시간은 여기에만 존재하며 규칙 함수에 절대 노출되지 않는다."""

    def __init__(self, bundle_path: str, env_hash: str): ...

    def shapes(self) -> list[Problem]: ...
    def candidates(self, p: Problem) -> list[Config]:
        """이 형상에 대해 status=='ok'로 측정된 config 목록."""
    def time_of(self, p: Problem, c: Config) -> float | None: ...
    def best_time(self, p: Problem) -> float: ...
    def answer_set(self, p: Problem, tol: float | None = None) -> set[Config]:
        """최적 대비 tol 이내를 전부 정답으로 인정 (노이즈 방어).
        ★ tol=None 이면 noise_floor(p) 를 쓴다. 고정 1% 를 기본값으로
        두면 작은 형상에서 노이즈를 신호로 학습한다. §30 참조."""
    def difficulty(self, p: Problem) -> float:
        """중앙값 시간 / 최적 시간. 무작위 config가 몇 배 느린가."""
    def noise_floor(self, p: Problem) -> float:
        """이 형상에서 구분 가능한 최소 상대 차이. 커널 시간의 함수다.
        ★ 통계 노이즈와 **타이머 분해능** 중 큰 쪽이다.
        BUNDLE.json 의 noise_floor 계수에서 계산한다. §30 참조."""
```

**구현 노트:**
- 로드 시 `(shape_key, config_key) -> time_ms` 딕셔너리로 메모리에 올린다.
  98만 행이면 수백 MB. 조회가 마이크로초여야 한다.
- 채점 속도가 문제되면 축소 표(`shape_id, kernel_id, split_k, mode,
  time_ms`)를 별도 parquet으로 만든다. **처음부터 하지 말고 병목이
  확인되면 한다.**
- `status != "ok"`는 후보에서 제외한다. 실패는 결측이 아니라 명시 기록이다.

### 7.2 regret

```python
def regret_at_k(rank_fn, table: PerfTable, shapes: list[Problem],
                k: int) -> float:
    """geomean over shapes of (min time among top-k) / best_time"""
```

- k = 1, 3, 5, 10 전부 보고한다. **k=1 과 k>=3 은 다른 배포 시나리오다**
  (§30.5). k=1 이 이 연구의 주 대상이다.
- **기하평균**을 쓴다 (비율 척도이므로).
- 정답은 **형상별 노이즈 바닥 이내 집합**으로 정의한다.
  고정 1% 가 아니다 — 15µs 커널에서 1% 는 노이즈 안이다. §30 참조.

### 7.3 ★ 난이도 층화 — 필수

A6000 데이터에서 확인된 사실:

```
난이도 중앙 1.57, 범위 1.11 ~ 2.66
난이도 < 1.2 (선택이 거의 무의미)  10개 형상
난이도 > 2.0 (선택이 결정적)        6개 형상

상관:  log M +0.626   log K -0.677   log AI +0.521
층별:  b_kvary 1.77(12개) > e_square 1.68 > a_workload 1.50(40개)
```

**쉬운 형상은 M이 작아서가 아니라 메모리 바운드라서 쉽다.** K가 크면
A/B 읽기가 대역폭을 포화시켜 config가 바꿀 여지가 없다. M=1 형상은
0.14ms로 런치 오버헤드(13µs)의 10배라 오버헤드 설명은 성립하지 않는다.

**함의:** 균등 geomean은 쉬운 형상이 분모를 부풀린다. 어려운 형상에서
20% 손해를 봐도 쉬운 형상 10개가 1.00이면 전체가 좋아 보인다.

**모든 regret 보고는 세 값으로 한다:**
```
전체  /  난이도 상위 절반  /  난이도 하위 절반
```

### 7.4 노이즈 바닥과 유의성

```python
def is_significant(delta: float, p: Problem, table: PerfTable) -> bool:
    """이 regret 차이가 이 형상의 측정 노이즈보다 큰가.
    ★ 고정 임계값을 쓰지 마라. 형상마다 다르다. §30 참조."""
```

**노이즈 바닥 이하의 개선은 보고하지 않는다.** regret 1.021 vs 1.018
같은 숫자는 대부분 의미가 없다. 아카이브 갱신, 조기 종료 판정에도
이 함수를 쓴다.

**노이즈 바닥은 형상 크기에 따라 35배 차이 난다.** 1ms 이상 커널은
0.044%, 15µs 커널은 1.5% 다. 단일 임계값을 쓰면 큰 형상에서는 실제
개선을 놓치고 작은 형상에서는 노이즈를 개선으로 착각한다. 전체 규격은
§30 에 있다.

## 8. 규칙과 피처

### 8.1 규칙 인터페이스 — 고정

```python
def rank(problem: Problem, hw: Hardware,
         candidates: list[Config]) -> list[Config]:
    """순수 함수. I/O 없음, 학습된 가중치 없음, 결정론적.
    candidates를 좋은 순서로 정렬해 반환한다."""
```

**후보 집합을 인자로 받는 이유:** 함수가 config를 직접 생성하게 하면
유효성 제약(smem 한도, warp 나눔, alignment)을 함수가 떠안게 되고,
LLM이 제약 코드를 재발명하느라 예산을 낭비한다. 열거와 제약 검사는
kernelTab이 이미 했다. 함수는 **순서만** 매긴다.

**점수를 무차원으로:** 내부 점수는 `t̂ / t_SOL` 같은 무차원 효율로
생각하도록 유도한다. 절대 시간을 예측하면 GPU가 바뀔 때 전부 다시
배워야 하지만 무차원 량은 전이된다.

### 8.2 피처 라이브러리

**시작 전에 손으로 10~15개를 채워둔다.** LLM 생성에 의존하면 초반에
아무것도 못 한다. 그리고 이것이 "LLM이 추가한 피처가 기여했는가"를
재는 기준선이 된다.

```python
# features/physical.py — 사람이 작성, 검증 완료
waves(p, hw, cfg)                 # 그리드가 GPU를 몇 번 채우는가
tail_waste(p, hw, cfg)            # 마지막 wave의 낭비 비율
grid_tiles(p, cfg)
tiles_per_sm(p, hw, cfg)
mainloop_iters(p, cfg)            # K / (tile_k * split_k)
smem_pressure(p, hw, cfg)         # smem_bytes / smem_per_block
est_occupancy(p, hw, cfg)         # max_blocks_per_sm 기반
arith_intensity(p)                # 형상만의 함수
ridge_point(hw)
roofline_ratio(p, hw)             # AI / ridge. 1 미만이면 메모리 바운드
is_memory_bound(p, hw)
tile_bytes_ratio(p, hw, cfg)      # 타일이 읽는 바이트 / L2
tail_m_frac(p, cfg); tail_n_frac(p, cfg)
tile_aspect_ratio(cfg)
k_per_split(p, cfg)
accum_regs_per_thread(cfg)
reg_pressure(hw, cfg)             # regs_per_thread * threads / regs_per_sm
has_spill(cfg)
can_use_cp_async(p)               # ★ alignment 1이면 multistage 불가
min_access_bytes(p)
pipeline_warmup_frac(p, hw, cfg)  # ★ 깊이를 smem 에서 역산 (아래)
```

#### ★ `ext` 없이 파이프라인 깊이를 얻는 법 — Instrumenter 가 찾아야 할 종류

`stages` 는 SM80 전용 축이라 `cfg.ext` 에 있고, 전이 규칙은 그것을 볼 수
없다 (§4.3). 그런데 **같은 정보를 아키텍처 공통 필드에서 얻을 수 있다.**

CUTLASS 의 mainloop smem 이 `stages * tile_k * (tile_m + tile_n) * elem`
이므로 나누면 깊이가 나온다.

```python
stages_est = smem_bytes / (tile_k * (tile_m + tile_n) * elem_bytes)
```

A6000 전수(980,915행)에서 `ext_stages` 와 **정확 일치 98.3%, |오차|<=1
99.6%, r = 0.994** 다.

**이것이 §11.4 Instrumenter 가 발견해야 할 종류의 대표 사례다.**
"아키텍처 전용 노브를 공통 자원량에서 역산한다" — 물리적으로 설명되고,
전이되고, 검증 가능하다. 프롬프트 예시로 쓸 것.

SM90 처럼 `stages` 개념이 다른 곳에서도 "smem 을 얼마나 깊이 쌓았는가" 로
여전히 의미가 있다는 것이 이 형태의 장점이다.

**작성 규칙 (LLM에게도 동일하게 강제):**
```
- 순수 함수. 부작용 없음.
- (Problem, Hardware, Config) 만으로 계산. 실측값/프로파일러 지표 금지.
- float 하나 반환. 0~1 정규화 권장. **클수록 나쁜 방향으로 통일.**
- 하드웨어 상수는 hw.*에서 읽기. 84, 101376 하드코딩 금지.
- cfg.ext 참조 금지 (아키텍처 전이 전제).
- 물리적 의미가 있을 것. 임의 조합 금지.
- 10줄 이내.
```

**부호 통일이 중요하다.** "클수록 나쁨"으로 맞추면 규칙이 항상
"가중합 후 오름차순 정렬"이 되고, LLM이 부호를 헷갈릴 여지가 사라진다.
실제로 부호 실수가 자주 나는데 이 규칙 하나로 대부분 없어진다.

### 8.3 정적 검사 — LLM 생성 코드에 적용

**규칙 코드** (`rules/checks.py`, AST 기반):
```
- 숫자 리터럴 개수 <= 8
- 등록된 피처 함수 외 호출 금지
- problem.M / N / K 를 직접 비교하는 분기 금지 (피처를 거쳐야 함)
- ANSWER_COLS / OUTCOME_COLS 이름 참조 금지
- import 금지, 파일 접근 금지
- AST 노드 수 상한
```

`if problem.M == 4096` 같은 암기는 AST 검사로 잡힌다. LLM 심사관이
필요 없다.

**피처 코드** (`features/validate.py`):
```
1. 실행되는가       샘플 1000개에서 유한한 float
2. 범위가 선언대로인가
3. 중복인가         스피어만 **과** 피어슨이 **둘 다** > 0.95 -> 폐기 후보
                   ★ 단조 변환은 중복이 아니다 (아래)
4. 상수인가         std < 1e-6 -> 기각
5. 차원이 맞는가    단위 선언 기반 (무차원/바이트/개수)
6. 스케일 불변성    hw.sm_count를 2배로 바꿨을 때 물리적으로 타당하게 반응
7. 유용한가         단독 랭킹 AUC — 기각은 안 하고 표시만
```

**6번이 중요하다.** `hw`를 바꿨는데 결과가 안 바뀌면 하드웨어를 안 쓰는
것이다. 실제로 이 검사를 시험하다가 **검사 자체가 무력했던 것**을 발견했다 —
대체 하드웨어의 `regs_per_sm` 을 A6000 과 같게 뒀더니 `reg_pressure` 가
"hw 를 안 쓴다" 로 잘못 걸렸다. **대체 하드웨어는 모든 수치 필드가 달라야
한다.** 하나라도 같으면 그 필드를 쓰는 피처는 검사를 그냥 통과한다.

#### ★ 3번 정정 — 스피어만만으로 중복을 판정하면 안 된다

원래 "스피어만 0.95 초과면 기각" 이라고 적었다. **틀렸다.**

`sm_idle_cost = 1/(1 - tail_waste) - 1` 은 `tail_waste` 의 **단조 변환**이라
스피어만이 0.999 다. 그런데 규칙은 **선형 가중합**이므로 둘의 효과가 전혀
다르다 — 512³ 에 128x128 을 쓰면 타일 16개로 84 SM 중 16개만 돌아 5.3배
손해인데, 선형 항(`tail_waste = 0.81`)으로는 그 크기가 안 나온다. 실측에서
손규칙이 1.221 -> 1.192 로 내려간 이유가 정확히 이 비선형 항이다.

```
수정: 스피어만과 피어슨이 **둘 다** 높을 때만 폐기 후보.
     단조 변환은 중복이 아니다 — 규칙이 선형 결합이기 때문이다.
```

측정된 쌍 (A6000, dev-cu124):

| 쌍 | 스피어만 | 피어슨 | 판정 |
|---|---:|---:|---|
| `has_spill` ↔ `spill_magnitude` | 0.999 | 0.971 | 폐기 후보 (진짜 중복) |
| `tail_waste` ↔ `sm_idle_cost` | 0.999 | 낮음 | **단조 변환. 유지** |

#### ★ 7번 정정 — 단독 AUC 가 낮다고 기각하지 마라

`tail_waste` 의 단독 랭킹 AUC 가 **0.176** 이다. 선언한 방향("클수록 나쁨")과
**반대로** 예측한다. 타일이 작을수록 타일 수가 많아 wave 가 커지고
`tail_waste` 가 0 에 가까워지므로, 그것만 최소화하면 작은 타일을 고른다 —
kernelTab 손규칙이 그 이유로 1.776(정적 top-1 보다 나쁨)에서 시작했다.

**그래도 기각하지 않는다.** 교락 변수(트래픽 항)와 함께 있어야 의미가 사는
피처를 단독 AUC 로 자르면, 조합으로만 설명되는 물리를 전부 버리게 된다.
**경고만 내고 사람이 본다.**

형상 수준 피처는 형상 안에서 상수라 AUC 가 0.5 인 것이 **정상**이다
(랭킹이 아니라 `if p.is_memory_bound:` 같은 분기용이다). 자동 검사가
그것을 "무정보" 로 기각하지 않도록 분리해서 판정한다.

### 8.4 피처 라이프사이클 — append-only 금지

라이브러리를 append-only로 두면 반드시 썩는다. 세 연산을 정의한다.

**폐기(deprecate)** — 지우지 않고 표시만
```python
@feature(deprecated_at_round=47, reason="waves와 스피어만 0.97, 중복")
def sm_utilization(...): ...
```
기존 규칙은 계속 돈다. 새 규칙 생성 시 프롬프트의 피처 목록에서만
빠진다. 되돌리기가 쉽다.

**수정(revise)** — 버그 발견 시 새 버전 추가
```python
tail_waste_v1(...)   # split_k를 안 곱하는 버그
tail_waste_v2(...)   # 수정본
```
**in-place 수정 절대 금지.** 과거 실험이 무효가 되고 재현이 안 된다.
`v1`을 쓰던 상위 규칙만 골라 `v2`로 재채점하면 버그의 영향을
정량화할 수 있다.

**제거(remove)** — 프로젝트 정리 시점에만.

**주기적 정리 (20라운드마다 자동):**
```
- 최근 50개 상위 규칙에서 한 번도 안 쓰인 피처 -> 폐기 후보
- 스피어만 **과** 피어슨이 둘 다 0.95 넘는 쌍 -> 나중 것 폐기 후보
- 유효성 검사 실패 -> 즉시 폐기 + 알람
```

**피처마다 유효성 검사를 붙이고 GPU/번들 추가 시마다 자동 재실행한다.**
잘못된 피처가 가장 잘 드러나는 시점이 새 아키텍처를 추가할 때다.

## 9. 베이스라인 사다리

**모두 표만 있으면 계산된다. GPU 불필요.**

| # | 방법 | 의미 | 비용 |
|---|---|---|---|
| 1 | 랜덤 k개 | 하한 | 0 |
| 2 | **정적 top-k** | **관문** | 분 |
| 3 | cuBLASLt heuristic | 프로덕션 기준 | 표에서 추출 |
| 4 | CUTLASS heuristic | 같은 커널 계열 벤더 | 표에서 추출 |
| 5 | 손으로 쓴 30~50줄 | 사람 반나절 | 반나절 |
| 6 | GBDT 랭커 | 학습 모델 상한 | 시간 |
| 7 | LLM-as-searcher | Helion 방식 | 재구현 |
| 8 | **kernelRule** | | |

### 9.1 정적 top-k — 관문

형상과 **무관하게** 고정된 config k개만 쓸 때의 regret.

```python
def greedy_facility_location(table, shapes, k) -> list[Config]:
    """min_{|C|=k} geomean_s [ min_{c in C} T(s,c) / best(s) ]
    submodular이므로 greedy가 (1-1/e) 보장."""
```

**주의 — 덮개 문제.** alignment가 형상을 구조적으로 나누므로
**어떤 config도 모든 형상에서 측정되지 않는다.** a888 커널은
alignment 4 형상에 애초에 쓰이지 않는다. 미측정에 벌점을 주면 그
구조적 사실이 regret으로 둔갑한다 (실제로 7.6까지 치솟았다).

**덮은 형상에서만 재고 덮개율을 함께 보고한다.**

주 지표는 **a888 형상 61개**로 계산한다 (층 D 5개는 alignment 검증용이지
실무 워크로드가 아니다). 전체 66개는 참고로 병기한다.

k = 1, 3, 5, 8, 10, 20에 대해 계산하고, **전체 / 크기 층화(t≥0.5ms vs
t<0.5ms) / 난이도 층화**를 나눠 보고한다. ★ **크기 층화를 먼저 보라.**

**전수 확정값 (정본 절차, 부록 §30.5):**
```
k=1:  전체 1.115   t>=0.5ms 1.021   t<0.5ms 1.164
k=8:  전체 1.006   t>=0.5ms 1.002   t<0.5ms 1.007
```
**크기 층화가 난이도 층화보다 5배 더 갈린다** (0.14 vs 0.03).
k=1 의 여지가 거의 전부 0.5 ms 미만 형상에 있다.

### 9.2 판정 — ★ 관문은 정적 top-k 가 아니라 **벤더 휴리스틱**이다

전수 결과가 나온 뒤 관문이 바뀌었다. 부록 §30.6b / §30.6c 를 따르라.

```
정적 top-1  1.115    형상을 전혀 안 보는 고정 config
벤더        1.080    형상을 보는 NVIDIA 휴리스틱   ← 차이 3.5%p 뿐
GBDT        1.044    학습이 도달 가능한 상한
```

"형상 의존성이 존재하는가" 라는 원래 질문의 답은 나왔다 — **존재하지만
3.5%p 다.** 정적 top-k 를 이기는 것은 이제 낮은 기준이라 관문이 못 된다.

#### 확정된 관문 (dev-cu124, 정본 절차 — §30.5b)

```
벤더 (nearest, a888 61형상 전체)      1.080   ← 헤드라인 관문
                                     strict 1.102 병기
GBDT 상한 (짧은 형상 블록 8분할)        1.044 기하평균 / 1.085 최악
현재 손규칙                           1.172

★ 판정은 분할별로 한다.
  세 방법을 같은 홀드아웃에서 비교하지 않으면 숫자가 짝이 안 맞는다.
  분할 x 방법 표를 항상 병기하라. (§30.6c)
```

```
규칙이 벤더(1.080)를 못 이긴다              -> 방향 재검토
벤더는 이기는데 GBDT(1.044)에 못 미친다      -> 정상. 격차를 좁히는 것이 연구
GBDT 에 근접한다                            -> 전이 실험으로
```

#### ★ 9.2b — 여지가 없는 체제에서는 규칙 기반이 고정 config 를 못 이긴다

체제별로 나눠 보면 관문의 의미가 달라진다 (dev-cu124, 같은 집합·같은 집계).

| | 짧은 41 (여지 16.3%) | 긴 20 (여지 **1.5%**) |
|---|---:|---:|
| 정적 top-1 (형상 무관 고정) | 1.1627 | **1.0145** |
| 벤더 (nearest) | 1.0977 | 1.0439 |
| 손규칙 (체제 전용 재적합) | 1.1889 | 1.1137 |
| LLM 첫 실행 | **1.0695** | 1.1174 |
| GBDT | — | **1.0056** |

**긴 형상에서 정적 top-1 을 이기는 것은 GBDT 뿐이다.** 벤더도 손규칙도
LLM 도 형상을 전혀 안 보는 고정 config 하나보다 나쁘다.

즉 그 체제에서는 **"형상을 보는 것" 자체가 이득이 없다.** 여지 1.5% 안에서
순위를 가르려면 형상당 15,000개 후보의 미세한 차이를 읽어야 하고, 그것은
회귀가 하는 일이지 8항짜리 물리 규칙이 하는 일이 아니다.

`fit_weights` 를 긴 형상 전용으로 돌려도 1.1151 -> 1.1137 (0.0014 개선)이다.
**가중치 문제도 학습 표본 문제도 아니다.**

```
함의 1  관문은 체제별로 판정해야 한다. 전체 geomean 하나로는 이 구조가 안 보인다.
함의 2  긴 형상은 형상을 보지 말고 고정 config 를 쓰는 것이 낫다 —
        그것 자체가 보고할 결과다.
함의 3  이 연구의 자리는 **여지가 큰 체제**다. 그 경계가 어디인지가
        실제 결과가 될 수 있다.
```

⚠️ 긴 형상 **전용** 진화는 아직 안 돌렸다. 위 LLM 값은 짧은 형상이
지배하는 학습 분할에서 나온 것이다. 여지가 작아서인지 탐색이 부족해서인지는
전용 실행으로만 갈린다.

#### ★ 집계 방식을 짝맞추지 않으면 결론이 뒤집힌다

한때 "GBDT 상한 = 최악 1.085" 로 적으려 했다. 그러면 이렇게 된다.

```
GBDT 최악  1.085   <- 8개 분할 중 최악
벤더 관문  1.080   <- 분할 없는 전체값
```

붙여 놓으면 **"GBDT 가 벤더보다 나쁘다 = 여지가 없다"** 로 읽힌다.
같은 방식으로 맞추면 정반대다.

```
기하평균   GBDT 1.044  vs  벤더 1.101     격차 0.057
최악      GBDT 1.085  vs  벤더 1.118     격차 0.033
```

**어느 쪽으로 재도 GBDT 가 이긴다. 다만 짝을 맞춰야 보인다.**
기하평균과 최악을 나란히 쓸 때는 **반드시 세 방법 모두에 대해** 쓴다.
이 병은 §30.5b(다른 절차)와 §30.8b(다른 분모)와 같은 뿌리다 — §30.8 참조.

**전체 geomean 만 보고 판단하지 마라.** 여지가 거의 전부 0.5 ms 미만
형상에 있고, 그 구간이 측정 분해능이 가장 나쁜 곳이다 (부록 §30.4).

### 9.3 벤더 휴리스틱 — 두 가지 지표를 구분하라

```
regret@1  =  벤더가 1등으로 고른 config 의 시간 / 전수 최적    ← ★ 관문
C/A       =  cuBLAS 시간 / 전수 최적                          ← 참고용
```

**둘을 혼동하지 마라.** `regret@1` 은 **같은 CUTLASS config 공간 안에서
휴리스틱의 순위 품질**을 잰다. `C/A` 는 cuBLAS 의 **다른 커널 구현**과
비교하는 것이라 구현 차이가 섞인다.

전수 확정값:
```
벤더 regret@1   1.088     ← 이것이 kernelRule 이 이겨야 할 값
C/A 중앙        1.084     (66형상 중 60개에서 전수 탐색이 cuBLAS 를 이김)
```

### 9.4 손으로 쓴 휴리스틱 (5) — LLM이 넘어야 할 실질 기준선

**LLM 루프보다 먼저 만든다.** 30~50줄, `features/physical.py`만 사용,
규칙과 동일한 제약(리터럴 8개, M/N/K 직접 분기 금지)을 적용한다.
같은 조건이어야 비교가 공정하다.

이것이 regret@1 = 1.03을 찍으면 LLM이 다툴 여지가 3%뿐이고, 그건
측정 노이즈와 비슷한 크기다. **가장 싼 반증 실험이다.**

### 9.5 LLM-as-searcher (7) — 진짜 대조군

Helion 방식을 **같은 프레임워크 안에 재구현**한다. 외부 도구를 돌리면
"다른 커널 생성기와의 비교"가 되어 주장과 무관해진다.

```
LLM-as-searcher:        형상이 주어지면 LLM이 config를 직접 제안
                        -> 측정 -> 반복. 산출물 재사용 불가.
LLM-as-heuristic-writer: LLM이 규칙 코드를 쓴다.
                        -> 런타임 오버헤드 0으로 무한 재사용.
```

같은 표, 같은 모델, 같은 예산으로 비교하면 이 접근의 존재 이유가
정량화된다. 구현은 어렵지 않다 — 진단/피처 없이 config만 제안하게
하면 된다.

**보고 형식:**

| 방법 | regret@1 | regret@5 | 런타임 오버헤드 | 제작 비용 |
|---|---|---|---|---|
| 전수 최적 | 1.000 | — | — | 33시간 |
| cuBLASLt | ? | — | ~µs | (벤더) |
| 정적 top-k | ? | ? | 0 | 분 |
| 손으로 쓴 규칙 | ? | ? | ~µs | 반나절 |
| GBDT | ? | ? | ~ms | 시간 |
| LLM-as-searcher | ? | ? | **초** | **형상마다** |
| **kernelRule** | ? | ? | **~µs** | **하룻밤** |

마지막 두 열이 주장의 핵심이다. **regret이 비슷해도 오버헤드와 제작
비용에서 이기면 된다.**

## 10. 홀드아웃

### 10.1 무작위 분할 금지 — 그리고 **학습은 다른 제약을 받는다**

#### ★ 학습 분할과 홀드아웃 분할은 요구가 다르다

```
홀드아웃   블록이어야 한다.                 보간을 막기 위해서
학습      모든 체제를 충분히 담아야 한다.    소수 체제 희생을 막기 위해서

두 요구가 충돌하면 **학습 쪽이 우선**이다.
학습이 못 본 체제는 애초에 평가할 자격이 없다.

체제 = 최소한 {t_sol >= 0.5ms, < 0.5ms} 두 개.
       필요하면 {memory-bound, compute-bound} 도.
```

원래 이 절은 "블록 분할을 쓰라, 무작위는 보간이다" 만 말했다. **블록 분할이
체제를 통째로 한쪽에 몰아넣을 수 있다는 것**을 놓쳤다. `M > 2048` 이 정확히
그 형태다 — 긴 형상 11개가 전부 홀드아웃으로 가고 학습은 82%가 짧은 형상이
된다.

**실측** (같은 루프/시드/예산 12라운드, 분할만 바꿈. 교차 채점):

| 학습 구성 | 검증 격차 | 긴 형상 11개 | 전체 61형상 |
|---|---:|---:|---:|
| 손규칙 (기준선) | — | 1.082 | **1.177** |
| 짧은 82% / 긴 18% | **+2.629** | **3.746** | **1.390** ← 손규칙보다 나쁘다 |
| 짧은 69% / 긴 31% | +0.009 | 1.096 | **1.143** |

**82% 구성에서 학습 점수는 좋아졌는데(1.201 -> 1.118) 실제로는 퇴보했다.**
진화는 학습 분할의 체제 구성이 허용하는 거래를 한다 — 소수 체제를 희생하는
것이 학습 점수에 유리하면 그렇게 한다.

그리고 **홀드아웃이 그 소수 체제와 겹치지 않으면 폭발이 안 보일 뿐, 규칙은
여전히 그 체제에서 나쁘다.** `M > 2048` 분할은 문제를 만든 것이 아니라
**드러낸** 것이다.

#### ★ 경계 탐색 — 균형은 **중앙값이 아니라 꼬리**를 줄인다

학습 총 개수를 24로 **고정**하고 긴 형상 비율만 바꿨다. 시드 3개.
고정 시험대(긴 12 / 짧은 12)는 학습에 안 쓰인다.

| 긴 비율 | 시드별 (긴 12) | 중앙 | **최악** | 짧은 12 |
|---:|---|---:|---:|---:|
| 8% | 6.57 / 16.33 / 1.19 | 6.57 | **16.33** | 1.107 |
| 17% | 1.17 / 1.08 / 10.41 | 1.17 | **10.41** | 1.095 |
| 25% | 1.09 / 1.20 / 2.19 | 1.20 | **2.19** | 1.158 |
| 33% | 1.08 / 1.22 / 1.79 | 1.22 | **1.79** | 1.147 |
| 손규칙 (참고) | — | 1.084 | — | 1.221 |

세 가지가 읽힌다.

1. **최악이 단조 감소한다** (16.33 -> 10.41 -> 2.19 -> 1.79). 중앙값은
   17% 이후 평평하다 (1.08~1.22). **균형은 꼬리를 줄이지 중앙을 못 올린다.**
2. **한 궤적으로는 측정할 수 없다.** 17% 조건의 세 시드가 1.08 / 1.17 /
   10.41 이다. 같은 조건에서 어떤 궤적은 멀쩡하고 어떤 궤적은 무너진다.
   **분할 실험은 시드를 여러 개 돌려 꼬리를 봐야 한다.**
3. **소수 체제를 희생해도 다수 체제에서 별로 못 번다.** 짧은 형상 점수가
   전 조건에서 1.095~1.158 로 평평하다. 진화가 하는 거래는 절대적으로
   나쁘고, 다만 (짧은 형상이 지배하는) 학습 점수에서 좋아 보일 뿐이다.

#### ★ 비율 기준은 **충분조건이 아니다**

첫 실제 LLM 실행에서 학습 분할이 69/31 로 `check_balance` 를 통과했는데도
체제 희생이 일어났다. 아카이브 엘리트를 라운드순으로 보면:

```
r    train    짧은     긴     항
0   1.1506  1.1782  1.0926   8     <- 긴 형상이 가장 좋았던 지점
1   1.1083  1.0858  1.1593   9
9   1.0712  1.0501  1.1187  16
18  1.0632  1.0394  1.1170  19
```

**짧은 형상은 1.1782 -> 1.0394 로 개선되고 긴 형상은 1.0926 -> 1.1170 으로
악화됐다.** 25% 하한을 넘겨도 다수 체제가 진화를 끌고 간다.

그리고 §9.2b 가 보여주듯 **그 체제에서는 애초에 규칙이 통하지 않는다** —
비율을 더 올려도 해결되지 않을 가능성이 크다. 분할을 손보기 전에
**그 체제에 여지가 있는지부터 확인하라.**

#### 강제 장치

`core/splits.py` 의 `check_balance()` 가 학습 분할의 체제 구성을 검사한다.
소수 체제가 `MIN_REGIME_FRAC`(현재 25%) 미만이면 **경고**하고,
`strict=True` 면 에러다. `describe()` 가 분할의 체제 구성을 항상 출력한다 —
조용히 통과시키지 않는다 (§26.4).

⚠️ **25% 는 하한이지 안전선이 아니다.** 33% 에서도 최악이 1.79 다.
균형만으로 충분하지 않으므로 **분할을 바꾸는 실험은 시드 3개 이상으로
돌리고 최악값을 함께 보고한다.**

#### 블록 분할 목록

M=4095가 학습에 있으면 M=4096은 시험이 아니다. **블록 분할**을 쓴다.

```python
def split_by_M_range(shapes)      # M > 2048 홀드아웃 (외삽)
def split_by_layer_type(shapes)   # 특정 (N,K) 조합 전체
def split_by_K_range(shapes)      # 층 B의 K 구간
def split_by_alignment(shapes)    # 층 D 전체
def split_by_size(shapes, hw)     # ★ roofline 하한 < 0.5ms 홀드아웃
def split_by_arch(bundles)        # ★ 주 지표
```

**층 C는 `sm_count`에서 역산된 형상이므로 M 절대값 기준 분할이
GPU마다 다른 것을 자른다.** waves 값 기준으로 분할하는 경로도 제공하라.

#### ★ "층 안에서 무작위" 도 보간이 될 수 있다

블록으로 나눴다고 끝이 아니다. **그 블록 안에서 다시 무작위로 나누면
같은 병에 걸린다.**

실제로 밟았다. 짧은 형상 41개의 GBDT 상한을 재려고 그 41개를 **무작위
5-fold** 로 나눴다. M=1024 가 학습에, M=1000 이 시험에 들어간다 —
사실상 보간이다. 결과가 1.029 로 나왔다.

같은 41개를 **블록 8분할**로 다시 재니 기하평균 1.044 / 최악 1.085 였다.
**0.015~0.056 의 낙관 편향**이 무작위 분할에서 나온 것이다.

```
규칙: 홀드아웃은 어느 수준에서든 **구조**로 자른다.
     (N,K) 레이어 타입 / K 구간 / M 구간 / alignment / 크기 / 아키텍처
     "이 부분집합 안에서는 무작위여도 된다" 는 없다.
```

#### ★ 크기 분할의 경계는 정답으로 잡으면 안 된다

`t_best < 0.5ms` 로 자르고 싶지만 `best_ms` 는 `ANSWER_COLS` 다. 분할
정의에 정답이 들어가면 그 홀드아웃은 오염된다.

**roofline 하한**으로 자른다 — 형상과 하드웨어만으로 계산되므로 배포
시점에도 알 수 있다. A6000 에서 이 대리 지표는 실측 짧은 형상 45개를
**전부** 포함한다 (46 예측 / 45 실측, 재현율 100%).

### 10.2 3분할

```
학습용   진단 리포트에 쓰임. LLM이 본다.
검증용   라운드마다 채점. LLM은 못 보지만 사람은 본다.
최종용   프로젝트 끝에 딱 한 번. 봉인.
```

**가운데가 필요한 이유는 사람이 오염원이기 때문이다.** 라운드마다
홀드아웃 점수를 보며 프롬프트를 고치면 결국 홀드아웃에 맞춰 시스템을
튜닝하게 된다. LLM은 못 봤어도 사람이 봤고 사람이 시스템을 고쳤다.

**강제 장치:**
- 진단 리포트 생성기가 **학습용 데이터에만 접근**하도록 구조를 짠다.
  프롬프트에 홀드아웃 점수를 넣을 수 있는 경로 자체를 없앤다.
- 조기 종료도 **검증용**으로 판정한다. 학습 regret으로 하면 이미
  과적합이 시작된 뒤에도 계속 돈다.

### 10.3 아키텍처 홀드아웃이 주 지표인 이유

**이것이 없으면 이 연구는 "FunSearch를 GEMM에 적용"과 구분되지 않는다.**

방향도 중요하다:
```
위로 (구형 -> 신형)  A6000+4090 학습 -> H100 예측.  실용적. 어렵다.
아래로 (신형 -> 구형)  쉽지만 쓸모가 적다.
가로 (같은 세대)      A6000 -> 4090. 최소 검증.
```

세 방향 다 보고하되 **위로 향하는 결과를 주 지표**로 삼는다.

그리고 정직하게: **완전한 전이는 안 될 것이다.** SM80의 warp tile은
SM90에 대응물이 없다. 주장을 나눠라.
```
전이되는 부분   wave quantization, roofline, smem 예산 — 물리라서 세대 무관
전이 안 되는 부분  세대별 고유 노브 (warp tile, cluster shape)
```
"물리 기반 부분은 전이되고 세대 고유 노브만 재학습하면 된다,
그 재학습 비용이 얼마다" — 이것이 현실적이고 오히려 설득력 있다.

## 11. 에이전트

### 11.1 구조 — 자율 에이전트가 아니다

**서로 대화하지 않는다. 순서를 코드가 통제한다.** 각자 한 번 호출되고
끝난다. 진짜 멀티 에이전트(스스로 순서 결정)로 만들면 어느 단계에서
망가졌는지 추적이 불가능해진다.

```
[코드] 진단 리포트 생성
   |
[LLM 1] Diagnostician  -> 가설 3~5개              라운드당 1회
   |
[코드] 기존 피처로 측정 가능한가 판정
   |
[LLM 2] Instrumenter   -> 피처 함수 1개           필요할 때만 (전체 20~30회)
   |
[LLM 3] Auditor        -> 반증 시도               2가 돌 때만. 다른 모델.
   |
[코드] 자동 검사 (차원/범위/중복/스케일)
   |
[LLM 4] Optimizer x12  -> 규칙 코드 (병렬)        라운드당 10~15회
   |
[코드] 정적 검사 -> 채점 -> 아카이브 갱신
```

**호출의 약 89%가 Optimizer다.**
```
100라운드 기준:  진단 100 / 피처 20~30 / 검사 20~30 / 규칙 1,200
```

**함의: 1, 2, 3을 정교하게 만드는 데 시간 쓰지 마라.** Optimizer와
그 입력(진단 리포트)을 먼저 완성하고 나머지는 나중에 붙인다.

### 11.2 하드웨어 지식의 소재

| 에이전트 | 하드웨어 지식 | 교체 필요 |
|---|---|---|
| Diagnostician | 필요 | 예 |
| Instrumenter | 필요 (물리량 계산) | 예 |
| Auditor | 필요 (타당성 판단) | 예 |
| **Optimizer** | **거의 불필요** | **아니오** |

Optimizer가 보는 것은 "피처 f1=0.24, f2=0.48인 config A가 f1=0.09인
config B보다 느렸다 → f1 가중치를 올려라"다. **f1이 무엇인지 몰라도
된다.** 그래서 GPU든 NPU든 그대로 쓴다.

**프롬프트를 두 층으로 분리한다:**
```
[고정] 역할 정의, 출력 스키마, 작성 규칙, 제약   -> 하드웨어 무관
[주입] 하드웨어 사실, 실행 모델 설명, 피처 목록   -> 백엔드마다 교체
```
`agents/prompts/hw/sm_86.md` 같은 파일로 두면 새 하드웨어 추가가
파일 하나가 된다.

### 11.3 Diagnostician

**입력:** §12의 진단 리포트 전체.
**출력:**
```json
{"hypotheses": [
  {
    "claim": "waves<1 형상에서 split-K를 고려하지 않아 SM 다수가 유휴",
    "evidence_cases": [3, 7, 11],
    "affected_regime": "waves < 1",
    "measurable_with": ["tail_waste", "waves"],
    "needs_new_feature": null,
    "proposed_direction": "tail_waste 가중치 상향 또는 split_k 후보 우대",
    "risk": "waves>8 구간에서 불필요한 split-K를 유발할 수 있음"
  }
]}
```

**설계 의도:**
- **코드 출력 금지.** 같이 시키면 원인 분석을 대충 하고 바로 `if`를
  추가한다.
- `evidence_cases` 필수 → 근거 없는 일반론을 못 쓴다.
- `needs_new_feature`가 채워진 경우에만 Instrumenter를 부른다.
  기존 피처 목록을 보여주고 스스로 판정하게 한다.
- `risk` → 부작용을 미리 말하게 하면 다음 라운드에 그 구간을 확인할
  근거가 생기고, LLM이 스스로 신중해진다.

### 11.4 Instrumenter

**대부분의 라운드에서 건너뛴다.** 초기 10라운드에 피처가 빠르게 늘고
이후 거의 안 는다. 물리량이 그렇게 많지 않다.

**입력:** 가설 하나 + 기존 피처 전체 목록(이름/설명/시그니처) +
데이터클래스 정의 + 작성 규칙.
**출력:**
```json
{"name": "l2_working_set_ratio",
 "code": "def l2_working_set_ratio(p, hw, cfg) -> float: ...",
 "rationale": "타일 하나가 읽는 A,B 바이트를 L2 용량으로 나눈 값",
 "unit": "dimensionless",
 "expected_range": [0.01, 5.0],
 "direction": "higher_is_worse"}
```

`unit` / `expected_range` / `direction`을 요구하면 자동 검증에 쓸 수 있다.

### 11.5 Auditor

**다른 모델**을 쓰고 **적대적 프롬프트**를 쓴다. 같은 계열 모델이
만들고 심사하면 같은 방향으로 틀린다 — 상관된 오류라 필터 역할을
못 한다.

```
아래 함수가 GPU GEMM 성능 예측에 물리적으로 타당한지 반증하시오.
당신의 임무는 승인이 아니라 결함 찾기입니다. 특히:
  - 차원/단위가 성립하는가
  - 지수나 계수가 물리적 근거 없이 붙어 있는가
  - 하드웨어 상수를 무시하는가
  - 특정 값 범위에만 맞춰진 것으로 보이는가
결함을 못 찾으면 "결함 없음"과 함께, 이 함수가 재는 물리량을
한 문장으로 쓰시오.
```

**마지막 문장이 장치다.** 설명을 못 쓰면 그 자체가 거부 신호다.

**가설을 함께 주지 않는다.** 만든 맥락을 모르는 상태에서 판단하게
하면 상관이 더 낮아진다.

**심사는 예선일 뿐이다.** 진짜 방어선은 아키텍처 홀드아웃이다.
물리적으로 타당한 피처는 전이되고, 우연히 맞은 피처는 무너진다.
그러니 애매한 것은 통과시키고 데이터가 판정하게 두어도 된다.

**사람은 심사관들이 갈리거나 확신이 낮은 건만 본다** (30개 중 3~5개).

### 11.6 Optimizer

**입력:** 부모 규칙 1~2개 + 채택된 가설 1개 + 사용 가능한 피처 목록 +
제약 조건 + **현재 규칙에 반영된 가설 이력**.

**출력:**
```json
{"code": "def rank(problem, hw, candidates): ...",
 "changes": "tail_waste 가중치를 2.0에서 3.0으로 올리고 split_k>1 우대항 추가",
 "hypothesis_id": "H12"}
```

- **diff가 아니라 전체 코드**를 받는다. diff는 적용 실패가 잦고 재시도
  비용이 크다.
- `changes` 필드가 계보 추적에 유용하다. diff를 뜨는 것보다 읽기 쉽다.

**프롬프트에 반드시 포함:**
```
현재 규칙에는 다음 가설들이 반영되어 있습니다:
  H1 (r3):  tail_waste 항 — waves<1 대응
  H4 (r8):  memory-bound 분기
  H9 (r15): smem_pressure 항

이번 가설: H12 "K가 작을 때 stages를 깊게 잡아 워밍업 손해가 크다"

기존 가설들의 효과를 훼손하지 않으면서 H12를 반영하세요.
특수 케이스 분기보다 기존 항의 수정이나 연속적 항 추가를 우선하세요.
```

**"기존 가설 목록"이 없으면 LLM이 `tail_waste` 항을 왜 있는지 모른 채
지운다.** 실제로 생기는 일이다.

### 11.7 Pydantic 사용 경계

```
agents/schemas.py   Pydantic       LLM 입출력만
core/types.py       frozen dataclass  채점 뜨거운 경로
```

경계에서만 변환한다. Pydantic AI를 쓴다면 validator로 금지 참조를
자동 재시도시킬 수 있다:

```python
@field_validator("code")
def no_forbidden(cls, v: str) -> str:
    banned = ["time_ms", "cublas_ms", "difficulty", "import ", "open(", "TABLE"]
    for b in banned:
        if b in v:
            raise ValueError(f"금지된 참조: {b}")
    return v
```

**문자열 검사는 우회 가능하니 §6.1의 구조적 방어와 병행한다.**

## 12. 진단 리포트 — 이 시스템의 엔진

**LLM이 기존 최적화 알고리즘을 이길 수 있는 유일한 지점이다.**
스칼라 점수만 주면 성능 나쁜 수치 최적화기가 된다.

### 12.1 다섯 블록

**블록 1 — 하드웨어 사실 (매번 고정 주입)**
```
GPU: RTX A6000 (GA102, sm_86)
  SM 84개 / 블록당 smem 99KB(101376B) / SM당 최대 1536 스레드
  SM당 레지스터 65536 / L2 6MB
  실효 116.1 TFLOP/s @1350MHz / 729.7 GB/s @7601MHz
  ridge point 159.1 FLOP/byte

실행 모델:
  CTA가 SM에 배분되며 마지막 wave에서 SM 일부가 유휴.
  split-K는 K를 나눠 타일 수를 늘리되 리덕션 비용이 추가된다.
  serial split-K는 파티션마다 fp16으로 D를 왕복한다 (정밀도 손실).
  parallel split-K는 부분합을 fp32로 한 번에 합산한다.
  alignment 1 형상은 cp.async를 못 써서 2단 파이프라인만 가능하다.
```

**기억에서 꺼내게 하면 틀린다.** 이 프로젝트에서 실제로 네 번
틀렸다 (ScaleType 의미, split-K 제약, swizzle 호환성, serial 부분합 타입).

**블록 2 — 현재 규칙 코드 전문**

**블록 3 — 체제별 regret 분해**
```
전체 regret@1: 1.14   (@3: 1.06)

체제별:

  waves 1~4        형상 8개   regret 1.09
```

**블록 4 — 사례 10~15개 (핵심)**
```
사례 #7  M=1024 N=1024 K=4096 fp16

  규칙 선택: tb128x128x64 w64x64x64 st4 swid8 sk1serial  -> 0.412ms (regret 1.31)
  실제 최적: tb128x128x64 w64x64x64 st4 swid8 sk6serial  -> 0.315ms

  피처              선택    최적
  waves            0.76    4.57
  tail_waste       0.24    0.09
  smem_pressure    0.48    0.48
  arith_intensity   683     683
  regs_per_thread   168     168
  mainloop_iters     64      11

  같은 형상 상위 5개 실측:
    sk=6 0.315 | sk=4 0.332 | sk=8 0.341 | sk=3 0.358 | sk=2 0.389

  난이도 1.42 — 1등과 10등이 38% 차이 (뾰족함)
  노이즈 바닥 0.12%
```

**선택 vs 최적을 나란히 보여주는 것이 핵심이다.** 값 하나만 있으면
인과를 읽을 수 없다. 주변 config를 넣는 이유는 **최적이 뾰족한지 넓은지**
알려주기 때문이다 — sk=4,6,8이 다 비슷하면 "6을 정확히 맞춰라"가 아니라
"3의 배수를 고려하라" 같은 견고한 규칙이 나온다.

**사례 선정 — 다양성을 강제한다:**
```python
for regime in ["waves<1", "waves1-4", "waves>8", "mem-bound", "K작음"]:
    cases += worst_n(regime, 3)
cases += best_n(all, 2)          # ★ 잘 맞춘 사례 (퇴행 방지)
```
"regret 상위 15개"는 나쁜 선택이다. 같은 실패 모드가 15번 반복되면
정보가 하나뿐이다.

**잘 맞춘 사례를 넣는 것이 의외로 중요하다.** 실패만 보여주면 규칙을
뜯어고쳐 잘 되던 것까지 망가뜨린다.

**매 라운드 사례를 교체한다.** 같은 15개를 계속 보여주면 과적합한다.

**블록 5 — 실패 이력**
```json
{"idea": "swizzle을 K로 분기", "round": 12,
 "regret_before": 1.14, "regret_after": 1.145, "verdict": "no_effect"}
```
프롬프트에는 **최근 20개 + verdict가 "made_worse"인 것 전부**를 넣는다.
악화시킨 것은 오래돼도 계속 경고해야 한다.

**없으면 같은 아이디어를 3라운드마다 반복한다. 가장 큰 시간 낭비다.**

### 12.2 토큰 예산

| 블록 | 토큰 |
|---|---|
| 하드웨어 사실 | 250 |
| 현재 규칙 코드 | 800 |
| 체제별 분해 | 300 |
| 표 구조 관찰 | 400 |
| 사례 15개 | 3,000 |
| 실패 이력 | 500 |
| 제약 | 200 |
| **합계** | **~5,500** |

라운드당 규칙 생성 12회면 66K 토큰. 100라운드 660만 토큰. **비용은
문제가 안 된다. 표 전체를 넣으려는 유혹만 참으면 된다.**

### 12.2b ★ 리포트는 결론을 미리 쓰지 않는다 — 전부 계산한다

```
금지: "X 가 Y 보다 크게 갈린다", "A 가 지배적이다" 같은 서술을
      템플릿에 박아 두는 것
허용: 계산 결과를 서술로 렌더링하는 것
      (어느 쪽이 큰지 재서 문장을 만든다)

★ 이 규칙은 하드웨어 사실 블록(블록 1)에는 적용되지 않는다.
  그것은 물리 상수이지 이 분할의 관측이 아니다.
```

**실제로 밟았다.** 이 문서의 §30.5 가 "크기 층화가 난이도 층화보다 5배 더
갈린다" 를 확립했고, 그것을 블록 3 템플릿에 그대로 적어 뒀다. 그런데
학습 분할(M<=2048)에는 긴 형상이 9개뿐이라 **그 분할의 실제 숫자는
반대였다** — 크기 격차 0.0007 vs 난이도 격차 0.1651.

**리포트가 자기 데이터와 모순되면 LLM 은 데이터가 아니라 문장을 믿는다.**
전역 관측을 지역 리포트에 복사하면 그 순간 거짓이 될 수 있다.

**코드로 강제한다.** `tests/test_diagnostic.py` 가 두 겹으로 막는다.

1. **정적** — 렌더되는 문자열 리터럴에 비교어("보다", "더 크", "지배적",
   "훨씬", "대부분" ...)가 있으면 그 문자열은 **계산된 값을 포함해야
   한다.** 순수 리터럴 비교 서술은 실패다.
2. **행동** — 데이터가 반대인 두 표로 리포트를 만들어 **문장이 뒤집히는지**
   확인한다. 정적 검사만으로는 계산된 f-string 안에 결론을 박는 것을
   못 잡는다.

### 12.2c 블록 3의 지표 — `regret` 과 `hit@1` 을 나란히

```
regret 은 낮은데 hit@1 이 0 이면
  -> 아깝게 빗나가는 것이 아니라 **구조적으로 다른 곳을 짚는 것**이다
  -> 가중치 조정이 아니라 **항이 필요하다**
```

정답 집합은 노이즈 바닥 2σ 이내이므로 짧은 형상에서는 수백 개가 들어간다.
그런데도 hit 이 0 이면 신호가 강하다. 손규칙이 regret 1.19 / hit 0.000
이었고, 원인은 **`stages=2` 를 항상 고르고 `parallel` 을 계속 고르는데
둘 다 66/66 에서 최적이 아니라는 것**이었다 — 규칙에 그 두 항이 아예
없었다.

### 12.2d 사례에 필요한 두 열

**(1) 규칙에서 사용 중인가** — AST 로 `f.<이름>` 참조를 뽑아 표시한다.

```
피처                선택    최적    규칙에서
is_two_stage        1.0    0.0    ★ 미사용   <- 항이 없다. **추가**해야 한다
split_k_cost        0.5    0.0    사용 중     <- 있는데 방향이 틀렸다. **조정**
```

"항이 없다" 와 "항은 있는데 가중치가 틀렸다" 는 다른 수정이다. 이 열이
없으면 LLM 이 규칙 코드를 읽어 유추해야 한다.

**(2) 격차를 노이즈 바닥 단위로**

```
gap_sigma = (t_선택 - t_최적) / (t_최적 x noise_floor(t_최적))

격차 = 노이즈 바닥의 18.3배   -> 실재한다. 배울 것이 있다
격차 = 노이즈 바닥의  0.8배   -> 노이즈다. 무시하라
```

**한 숫자가 두 문제를 다 해결한다** — 눈금 동점도, 일반적인 해상도도.
주변 config 목록에도 같은 단위를 적용하면 "전부 (최적)" 으로 표시되어
그 형상에 순위가 없다는 것이 한눈에 보인다.

⚠️ **사례 선정에는 쓰지 마라.** 짧은 형상은 σ 가 작게 나오기 쉬운데
여지가 몰려 있는 곳이 거기다 (§30.5). 선정은 체제·실패모드 다양성으로
하고 σ 는 **표시만** 한다.

### 12.3 절대 넣지 말 것

- **표 전체.** 토큰도 안 되고 넣는 순간 암기한다.
- **홀드아웃 점수.** 넣으면 홀드아웃에 맞춰 최적화한다.
- **모든 형상의 최적 config 목록.** 사례 15개 안에서만 보여준다.
  전부 주면 조건문으로 옮겨 쓴다.

### 12.4 검증 방법

**프롬프트를 완성하기 전에 사람이 먼저 읽는다.** 이 다섯 블록만 보고
"나라면 뭘 고칠까"가 떠오르면 리포트가 잘 만들어진 것이다. 안 떠오르면
정보가 부족한 것이다.

**프롬프트를 고치기 전에 리포트를 고쳐라.** 프롬프트만 계속 손보다
시간을 날리는 것이 흔한 실패 양상이다.

## 13. 아카이브 (MAP-Elites)

### 13.1 왜 단일 최고로는 안 되는가

```
레시피A(60) -> 소금(70) -> 불(75) -> 시간(73 버림) -> 마늘(76) -> 76에서 정체
```

항상 최고에서만 출발하면 근처만 뒤진다. 언덕 꼭대기까지는 가지만
옆의 더 높은 산은 못 본다.

### 13.2 셀 축

```
코드 길이            (짧음 / 중간 / 김)
memory-bound regret  (구간)
compute-bound regret (구간)
```

각 셀에 최고 하나씩. 전체 점수가 낮아도 **특정 영역 최고면 살려둔다.**

```
전체 최고        규칙#47   1.12
짧은 코드 최고    규칙#12   1.19 (8줄)
mem-bound 최고   규칙#31   1.08 (전체 1.24)
compute 최고     규칙#40   1.03 (전체 1.31)
```

규칙#31과 #40은 단일 최고 방식이면 진작 버려졌다. 그런데 **둘을 합치면
양쪽 다 잘하는 규칙이 나올 수 있다.** 이것이 교차(crossover)이고
도약이 나오는 지점이다.

### 13.3 부모 선택

```
6개  현재 최고에서 변형        착실한 개선
3개  아카이브 무작위에서 변형   다른 언덕 탐색
3개  아카이브 둘을 합치기      도약 시도
```

앞의 6개가 exploitation, 뒤의 6개가 exploration이다.

### 13.4 갱신 규칙

```
전체 점수가 기존 최고보다 유의하게 좋은가?  -> 전체 최고 갱신
각 셀에서 최고인가?                        -> 그 셀 갱신
어느 자리도 못 차지했나?                   -> 버림
```

"유의하게"는 §7.4의 노이즈 바닥으로 판정한다.

## 14. 라운드 루프

### 14.1 한 라운드

```
1. 아카이브 최고 규칙 채점 -> 진단 리포트 생성          [코드]
2. 가설 3~5개                                        [LLM 1회]
3. 필요시 피처 생성 + 심사 + 자동 검증                 [LLM 0~4회]
4. 규칙 12개 생성 (부모/가설 조합, 병렬)               [LLM 12회]
5. 정적 검사 -> 샌드박스 실행 -> 채점                  [코드, 밀리초]
6. 아카이브 갱신
7. 가설 이력 / 실패 목록 기록
8. 종료 조건 확인
```

**벽시계 1분 남짓.** LLM 호출 20~40초(병렬), 채점 수 밀리초.
30~50라운드면 한 시간이다.

### 14.2 왜 라운드당 12개인가

세대당 표본이 1개면 진화가 아니다. 개선 확률 30%면 셋 중 둘이 헛돈다.
12개를 만들면 3~4개가 개선되고 그중 최고를 다음 부모로 쓴다.

**같은 가설이라도 구현이 다르다.** "tail_waste 가중치를 올려라"를 받아도
어떤 건 2.0→3.0으로, 어떤 건 조건부 분기로, 어떤 건 비선형 항으로
구현한다. 어느 게 나은지는 채점해봐야 안다.

**비용 구조가 이를 허용한다:**
```
LLM 호출 12개 (병렬)   20~40초
채점 12개              수 밀리초
```
채점이 사실상 공짜라 LLM 호출만 비용이고, 병렬이라 12개나 1개나
벽시계가 비슷하다. **이것이 §7.1에서 표를 메모리에 올리는 이유다.**

각 호출은 독립적이다. LLM이 대화를 이어가는 것이 아니라 매번 새 요청이고
필요한 맥락은 프롬프트에 전부 담는다.

### 14.3 개선 곡선과 종료

```
regret
1.35 |*
1.30 | **
1.25 |   ***
1.20 |      ****
1.15 |          *******
1.12 |                 *************
     +--------------------------------
      r1        r10       r20      r30
```

초반에 빠르게 떨어지고 곧 평평해진다. (Helion 실험에서도 LLM이 전체
예산의 7% 안에서 plateau에 도달했다.)

**종료 조건:**
```
10라운드 연속 개선이 노이즈 바닥 이하
  AND
아카이브에 새 셀이 채워지지 않음
```

점수가 멈춰도 다양성이 늘고 있으면 아직 탐색 중이다. 두 조건을 모두
쓴다.

### 14.4 라운드의 숨은 역할

```
r1   최악 = waves<1 구간 (1.31)     -> 고침
r5   최악 = memory-bound (1.22)      -> 이제 보임
r12  최악 = K 작은 형상 (1.15)       -> 그 다음
```

**한 문제를 고쳐야 다음 문제가 보인다.** 짠맛을 잡아야 고기가 질긴 게
보이는 것과 같다. 이것이 한 번에 다 못 하고 여러 라운드가 필요한 이유다.

#### ★ 그리고 한 문제를 고치면 **이전 진단이 무효가 된다**

진단은 **그 시점 규칙의 실패 모드**이지 데이터의 절대적 성질이 아니다.

실제로 밟았다. 손규칙의 리포트를 사람이 읽고 세 가지 수정을 즉시 읽어냈다
(`is_two_stage` 미사용 / `log_workspace_bytes` 미사용 / `split_k_cost` 방향).
그것을 루프의 정답으로 삼고 20라운드를 돌렸더니 ②를 못 찾았다.

`failures.jsonl` 을 보니 **네 번 시도했고 네 번 다 데이터가 거부했다.**

```
r4   1.1289 -> 1.4942   log_grid_tiles -> log_workspace_bytes 교체
r4   1.1289 -> 1.1305   if p.can_use_cp_async -> log_workspace_bytes 재가중
r9   1.1203 -> 1.1235   if p.is_memory_bound -> log_workspace_bytes 재가중
r10  1.1203 -> 1.3674   (같은 형태)
r16  1.1176 -> 1.2199   log_workspace_bytes 항 추가
```

**파이프라인이 못 찾은 것이 아니라 탐색하고 기각했다.** ②는 손규칙이
parallel split-K 를 고르던 실패 모드였고, 규칙이 바뀌자 그 실패 모드가
사라져서 그 항이 더는 설명력을 갖지 않았다.

```
규칙: 사람이 리포트 하나를 보고 읽은 수정 목록을 루프의 정답으로 삼지 마라.
     루프가 그것을 안 하면 "왜 안 했는가" 를 failures.jsonl 에서 확인하라.
     기각한 것과 탐색조차 안 한 것은 다르다.
```

## 15. 안전장치

### 15.1 암기 방지

LLM은 반드시 이런 것을 쓴다:
```python
if 4090 <= M <= 4100 and N == 14336:
    return [candidates[17], ...]
```

**방어:**
1. **홀드아웃** — 특히 아키텍처 홀드아웃. 우연히 맞은 것은 여기서 무너진다.
2. **리터럴 예산** — 숫자 상수 + 가중치 개수의 합이 8 이하.
   ★ **각 `w[i]` 는 정확히 한 번만 쓸 수 있다** (아래).
3. **AST 검사** — `problem.M/N/K` 직접 비교 분기 금지.
4. **연속성 제약** — 인접 M에서 점수가 급변하는 지점 개수에 페널티.
   wave quantization 때문에 실제 불연속이 있으므로 완전 금지는 아니다.

### 15.1b ★ 예산 우회 — 실제 LLM 이 뚫었다

첫 실제 실행에서 규칙이 이렇게 나왔다.

```python
s = s + f.log_workspace_bytes * w[0]
s = s + f.log_dram_traffic    * w[0]      # w[0] 재사용
s = s + f.is_two_stage        * w[0]      # 또
...
w = [26.09, 95.11, 17.77, 108.84, 1.57, 115.26, 122.97, -3.24]
```

**가중치 8개로 항 19개를 만들었다.** 정적 검사는 통과했다 —
`len(W0) == max_index + 1` 만 봤기 때문이다.

예산(§29.4)의 목적은 "파라미터가 많으면 어떤 구조든 비슷한 regret 에
도달해 구조 비교가 무의미해진다" 를 막는 것이다. **항을 늘려 그 제한을
피하면 목적이 무너진다.** 가중치가 26~123 으로 폭주하고 `w[7]` 이 음수가
된 것(전 피처가 "클수록 나쁨" 인데)도 같은 증상이다.

```
수정: 각 w[i] 는 정확히 한 번만 쓸 수 있다.
     항 개수 <= len(W0) 가 자동으로 따라온다.
```

⚠️ **"같은 식이 두 번 나오면 거부" 는 넣지 마라.** 정당한 재가중을
오탐한다 — 형상 수준 분기에서 같은 피처에 **다른** 가중치를 주는 것이
바로 §8.1 이 권장하는 패턴이다.

```python
s = f.traffic_amplification * w[0]
if p.is_memory_bound:
    s = s + f.traffic_amplification * w[1]   # ✅ 재가중. 정당하다
```

실제 병리(같은 식 + **같은** 가중치)는 재사용 검사가 이미 잡는다.

### 15.1c 프롬프트에 규칙만 적으면 지켜지지 않는다

`_common.md` 가 예산 규칙을 명시했는데도 240 제안 중 132건이 스키마
재시도 소진으로 폐기됐다 (대부분 `w0` 길이 초과).

**실제로 거부된 코드를 프롬프트에 함께 넣었다.** 규칙만 읽고 넘어가는
것을 막는다 — §30.8 의 "문서로 적은 규율은 지켜지지 않는다" 가 LLM 에게도
그대로 적용된다.

### 15.2 교묘한 암기 — 사람의 물리적 판단이 필요한 지점

```python
def combined_pressure(p, hw, cfg):
    return (cfg.tile_m * cfg.stages) / (p.K ** 0.5) * 1.3
```

자동 검증을 다 통과한다. 실행되고, 범위도 맞고, 기존 것과 상관도 낮고,
regret도 조금 개선될 수 있다. **그런데 의미가 없다.** 표에 맞춰진
우연이고 다른 GPU에서 무너진다.

승인 기준은 하나다: **"이 함수가 재는 물리량을 한 문장으로 설명할 수
있는가."** 설명이 안 되면 기각한다.

다만 §11.5대로 **아키텍처 홀드아웃이 있으면 이 부담이 데이터로 넘어간다.**
GPU가 한 대뿐이면 승인 게이트의 중요성이 훨씬 커진다.

### 15.3 코드 실행 격리

LLM이 쓴 코드를 그대로 `exec`하면 안 된다.
```
- 타임아웃 (무한 루프를 실제로 만들어낸다)
- import 제한 (허용: math. 금지: os, sys, subprocess, importlib)
- 파일/네트워크 접근 차단
- 메모리 상한
- 별도 프로세스 (크래시 격리)
```

### 15.4 캐싱과 재현성

- 같은 코드가 나오면 재채점하지 않는다 (해시 키).
- **프롬프트 해시로 LLM 호출도 캐싱**한다. 초반에 똑같은 것을 반복
  생성하는 경우가 많다.
- `runs/{run_id}/llm_calls/`에 프롬프트와 응답 원본을 남긴다.
  재현성과 사후 분석에 필요하다.
- 모델 이름, 온도, 시드를 `config.json`에 기록한다.

### 15.5 "조용히 아무것도 안 하는 안전장치" 경계

kernelTab이 이 클래스의 버그를 **세 번** 만났다:
```
WARMUP_SECONDS      정의만 되고 안 쓰임. 로그는 "워밍업 한다"고 찍힘
MEM_CLOCK_MIN_FRAC  주석에 기준만 있고 미구현
test_table.py       pyarrow 없으면 통째로 스킵되는데 "86 passed" 초록불
```

kernelRule에서 특히 위험한 지점:
- 누출 방지 테스트가 환경에 따라 스킵되는가
- 정적 검사가 파싱 실패 시 조용히 통과하는가
- 피처 검증이 예외를 삼키고 승인하는가
- 홀드아웃 분할이 빈 집합을 반환하고도 통과하는가

**"조건이 안 맞으면 건너뛴다"를 쓰는 모든 곳에서 건너뛴 사실 자체를
실패나 경고로 만들어라.**

## 16. 실험 설계

### 16.1 Ablation — 4개 역할이 정리되면 자동으로 만들어진다

| 구성 | 검증하는 것 |
|---|---|
| Optimizer만 (점수만 피드백) | LLM = 나쁜 최적화기 베이스라인 |
| **+ Diagnostician** | **진단이 기여하는가 <- 핵심 주장** |
| + Instrumenter | 피처 발견이 기여하는가 |
| + Auditor | 심사가 기여하는가 |
| 피처/규칙 미분리 (프로그램 전체 진화) | FunSearch 대비 도메인 설계의 가치 |
| 손으로 쓴 규칙 | 사람 기준선 |
| GBDT | 학습 모델 상한 |

**두 번째 줄이 이 연구의 핵심 주장이다.** 여기서 유의미한 차이가 안
나면 나머지를 아무리 정교하게 만들어도 소용없다.

### 16.2 선행연구 대비 차별점 — 세 개

| | 산출물 | 재사용 | 일반화 검증 |
|---|---|---|---|
| Helion (PyTorch) | config | 없음 | 해당 없음 |
| FunSearch / AlphaEvolve | 프로그램(답) | 해당 없음 | 없음 |
| tritonBLAS | 휴리스틱 | 있음 | 없음 (사람이 만듦) |
| **kernelRule** | **휴리스틱** | **있음** | **아키텍처 홀드아웃** |

1. **일반화 검증** — 안 본 형상/dtype/아키텍처. 선행연구에 없다.
   FunSearch에는 과적합 개념 자체가 없다 (찾은 프로그램이 그 문제에서
   좋으면 끝).
2. **피처/규칙 분리** — 도메인 구조를 반영한 설계. ablation으로 가치 증명.
3. **재사용 가능한 산출물** — Helion과 다른 문제를 푼다.

**세 개 다 GPU 두 대 이상을 요구한다.** 한 대면 "FunSearch를 GEMM에
적용"과 구분되지 않는다.

### 16.3 프레이밍 — 약한 주장과 강한 주장

```
약한 (아마 실패)  "우리 휴리스틱이 CUTLASS보다 정확하다"
                 NVIDIA가 수년 투자한 것을 이기겠다는 것. 승산이 낮고
                 이겨도 몇 %다.

강한 (해볼 만함)  "휴리스틱을 만드는 비용을 낮춘다"
                 사람 몇 주 -> 하룻밤. 새 아키텍처가 나왔을 때 벤더
                 휴리스틱이 성숙하기 전 공백기를 메운다.
```

두 번째가 검증도 명확하다. **A6000+4090으로 만든 규칙이 H100에서
얼마나 하는가.** 기존 휴리스틱과 동점만 나와도 "사람 몇 주 대신
자동으로"라는 주장이 성립한다.

그리고 이 프레이밍이면 **NVIDIA와 경쟁하지 않아도 된다.** 커스텀 융합
커널, 사내 DSL, 새 양자화 포맷, 국산 가속기처럼 **벤더 휴리스틱이
존재하지 않는 곳**이 진짜 시장이다.

### 16.4 결과가 나쁠 경우의 선택지

정적 top-k가 어려운 절반에서도 1.05면 방향을 바꿔야 한다:
- **후보군 밖으로** — 벤더 큐레이션이 놓치는 영역
- **융합 커널로** — epilogue 융합이 붙으면 최적 config가 달라지고
  벤더 휴리스틱이 커버 안 하는 조합이 급증한다
- **문제를 바꾸기** — 컴파일 시간 최소화, grouped GEMM(사전 튜닝 불가)

```
[0] 표 확보 — kernelTab 번들
     |
[1] PerfTable + regret + 난이도                    GPU 불필요
     |
[2] ★ 관문: 정적 top-k (난이도 층화)               ← 여기서 계속할지 결정
     |   1.02 근처면 방향 재검토
     |   어려운 절반이 1.10 이상이면 진행

     |
[4] 진단 리포트 생성기                              ← ★ 사람이 직접 읽어본다
     |   "나라면 뭘 고칠까"가 안 떠오르면 리포트를 고쳐라
     |
[5] Optimizer만 붙여 수동 1라운드                   ← 프롬프트가 통하는지 눈으로
     |
[6] 루프 자동화 (아카이브, 채점, 정적 검사)
     |
[7] Diagnostician 추가                             ← ablation 핵심
     |
[8] Instrumenter / Auditor 추가
     |
[9] GBDT, LLM-as-searcher 베이스라인
     |
[10] 4090 번들 확보 -> 전이 실험
```

**[2]와 [4]가 관문이다.** [2]에서 여지가 없으면 뒤가 무의미하고,
[4]에서 사람이 읽어 판단이 안 서면 LLM도 못 한다.

**[3]을 [5]보다 먼저 하는 이유:** 30줄이 regret 1.03을 찍으면 LLM이
다툴 여지가 3%뿐이고 그건 측정 노이즈와 비슷하다. 가장 싼 반증 실험이다.

## 18. 알려진 측정 한계 — 규칙 설계에 반영할 것

kernelTab이 확립한 조건과 남은 한계다. **`BUNDLE.json`과 `env.json`에
기록되어 있으니 반드시 읽어라.**

### 18.1 확립된 조건

```
SM 클럭     1350 MHz 고정, 스로틀 0%
메모리 클럭  7601 MHz 고정 (P2 상한. P0 8001은 컴퓨트에서 도달 불가)
실효        116.1 TFLOP/s / 729.7 GB/s / ridge 159.1
재현성      median 0.05% / p90 0.86% / max 0.35%
드리프트     세그먼트 500커널로 억제. 4096³ 프로브 52회 변동폭 0.07%
```

**재현성 0.05%는 regret 1.001 차이도 구분 가능한 해상도다.**

### 18.2 남은 편향

**작은 형상의 런치 오버헤드.** 빈 커널 런치가 3.2µs. 15µs급 커널이면
20%가 오버헤드다. 다만 층 A의 M=1/8 형상은 0.14ms라 오버헤드의 10배이므로
직접적 문제는 아니다.

**모듈 압력 편향 (생산 데이터에는 해당 없음).** 문턱(~1,200 모듈)을
넘으면 작은 타일 커널이 큰 타일보다 ~1.4배 불리하게 측정된다.
세그먼트를 500으로 유지해 문턱 아래에 있으므로 생산 표는 깨끗하다.
**다만 다른 출처의 표를 합칠 때는 이 조건을 확인해야 한다.**

**★ 작은 형상의 측정 노이즈 — 크기에 따라 35배 차이.**
33시간 캠페인의 앵커 12개 x 312회 재측정으로 확인:

```
> 1 ms   (1.50~2.92 ms)  상대 표준편차 0.044%   33시간 변동폭 0.11~1.41%
< 0.1 ms (14~56 µs)      상대 표준편차 1.541%   33시간 변동폭 1.82~7.14%
```

모델은 두 항의 **최댓값**이다 (§30.2):
```
noise_floor(t) = max( sigma_rel(t),  tick_pct(t) )
                 = a/t + b            = EVENT_TICK_MS / t
A6000: a=0.000374ms, b=0.00044, tick=0.001024ms
```

**절대 성분(a)** 은 타이머/런치 지터로 커널 시간과 무관하게
0.26~0.47µs 다. **분해능(tick)** 은 CUDA 이벤트 타이머의 양자로,
이보다 작은 차이는 **측정으로 구분할 수 없다** — 같은 눈금에 떨어진
두 config 는 시간이 문자 그대로 동일하게 기록된다.

**분해능이 지배하는 구간이 넓다.** 14µs 에서 통계 노이즈는 2.7% 인데
눈금은 7.3% 다. 경계는 약 1.5ms 이고, 그보다 짧으면 분해능이 지배한다.

**A6000 표에서 66형상 중 45개가 최적시간 0.5ms 미만이다.**
그 아래에서는 1% 이내 순위를 신뢰하지 마라.

이것은 **런치 경로에 붙는 고정 비용**이 이 시스템에서 반복되는
세 번째 형태다:
```
모듈 누적 드리프트   런치당 상수  42~50 µs / 1,000 모듈
노이즈 절대 성분     런치당 상수  0.26~0.47 µs
forward-compat 계층  런치당 상수  50 ns
```

**순위가 흐릿한 형상.** 최적 대비 1% 이내 config가 7개, 5% 이내가 45개인
형상이 존재한다 (M=1/8의 메모리 바운드 구간). 그 형상에서는 규칙의
선택이 실질적으로 무의미하고, 이는 결과의 일부로 보고할 사실이다.

### 18.3 물리적 사실 — 규칙이 배워야 할 것

표에서 확인된, 규칙이 알아야 할 도메인 지식:
```
- alignment 1 형상은 cp.async를 못 써서 stages=2만 가능
- serial split-K는 파티션마다 fp16 왕복 -> split_k에 비례해 오차 증가
  parallel split-K는 fp32로 한 번 합산 -> 오차 0
- stages=2(MmaPipelined)와 stages>=3(multistage)는 다른 커널 계열
- 스필 커널은 최적으로 뽑힌 적이 없다 (전수 확인. 격차 0.572, 최적 0회)
- ★ `warp_m=128` 이 100% 오답 축이다 (`warp_n` 이 아니다 — warp_n 에는
  128 이 애초에 없고 32/64 뿐이다). 66형상 중 최적 **0회**,
  중앙 rel 0.061. warp tile (128,64) 는 스필 100% 이며 같은 것을 가리킨다.
  형상별 최적의 `ext_warp_m` 분포는 `{64: 48, 32: 10, 16: 8}` 이다.
- ★ "SM 84 = 2^2 x 3 x 7 이므로 3의 배수 split-K가 유리" 가설은
  **전수에서 기각됐다.**
  - waves<1 형상 15개: sk=3 이 최적인 경우 **0개** (sk=1 이 11개)
  - 전체 66형상: 3의 배수(3,6,12)가 최적 23개 = 34.8%.
    축에서 3의 배수 비율이 3/8 = 37.5% 이므로 **농축이 전혀 없다.**
  음성 결과로 보고한다.
- 형상별 최적의 `split_k_mode` 는 **66/66 이 serial** 이다.
  parallel 은 40만 줄을 쓰고 최적 0회 — 다른 GPU 에서 뒤집히지
  않으면 제외 후보다.
- waves>40 형상에서 sk=16 이 빠르다는 리허설 관찰도 **표본 편향이었다.**
  전수에서 3개 형상 전부 sk=1/serial 이 최적.
```

마지막 항목은 **가설이지 확정이 아니다.** 리허설 표본(커널 20개)에서는
미지지였다. 전수 데이터에서 재검증하고, 결과가 어느 쪽이든 그대로
기록하라.

전수 표가 나온 뒤에 정한다.

1. **프로젝트 진행 여부** — 정적 top-k와 C/A 격차를 보고 결정.
   난이도 상위 절반에서 여지가 5% 미만이면 방향 전환.
2. **주 타겟 형상 집합** — 전체 66개인가, 난이도 상위 절반인가,
   a888 61개인가.
3. **LLM 모델 선택** — Helion 실험에서 모델 간 차이가 몇 % 이내였다.
   하나로 고정하고 시작한 뒤 ablation으로 비교.
4. **채점 축소 표 필요 여부** — 채점 속도가 병목이면 만든다.
   처음부터 하지 않는다.
5. **regret@k의 k** — 배포 시나리오에 따라. 런타임 즉시 결정이면 k=1,
   빌드타임에 몇 개 측정 가능하면 k=5~10.
6. **연속성 제약의 강도** — wave quantization으로 인한 실제 불연속과
   암기로 인한 불연속을 구분할 임계값.

## 부록 A. 용어

| 용어 | 정의 |
|---|---|
| **regret** | 규칙이 고른 config의 시간 / 그 형상의 최적 시간. 1.0이 완벽 |
| **regret@k** | 규칙이 고른 상위 k개 중 가장 빠른 것 기준 |
| **난이도** | 중앙값 시간 / 최적 시간. 무작위 config가 몇 배 느린가 |
| **덮개(coverage)** | 정적 top-k에서 그 config 집합이 측정된 형상의 비율 |
| **waves** | 그리드 타일 수 / SM 수. GPU를 몇 번 채우는가 |
| **tail_waste** | 마지막 wave에서 노는 SM 슬롯 비율 |
| **ridge point** | roofline의 무릎. peak_flops / bandwidth |
| **C/A** | 벤더 휴리스틱 1등 / 전수 최적. 개선 여지의 상한 |
| **앵커** | 세그먼트 간 계통 오차 검증용 고정 커널 (kernelTab) |
| **env_hash** | 측정 조건 식별자. 조인 키가 아니라 **격리 경계** |
